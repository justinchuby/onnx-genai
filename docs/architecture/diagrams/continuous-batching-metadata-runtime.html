Architecture explainer · portable semantics vs runtime policy

Continuous batching without hidden scheduler semantics

A manager-friendly guide to what a model package can prove, what an execution backend can implement, and what the runtime may decide at the moment work arrives.

CAN
Metadata says CAN; runtime decides WHETHER/WHEN.

Support means shared live-row execution is semantically legal. It is an optional optimization—not a requirement to co-batch every compatible request. When isolated execution is semantically valid, lack of a shared forward declines only that optimization; it does not reject the package.

Backend reality

A backend may offer a shared forward, selected-row gather/scatter, both, or neither. If it cannot preserve the declared shared semantics, the runtime takes the isolated path before mutation. The package remains loadable whenever that isolated execution is valid.

Boundary: metadata carries portable legality and ABI facts. The runtime owns request identity, physical slots, queues, admission, fairness, active-row selection, padding/packing choice, memory placement, graph capture, resource budgets, capacity, backfill, and the performance/latency policy that chooses shared or isolated execution.

The essential split

One semantic contract, three owners

The model/package makes row behavior observable; metadata makes it portable and checkable; the runtime turns the proof into a safe execution plan. None of those layers needs to name a model family, operator, vendor, request ID, or scheduler policy.

A · model / package

Make row semantics explicit

  • Give each request-visible input, state carrier, effect carrier, and output a structurally derivable row relationship—with no hidden cross-row coupling.
  • Expose cross-invocation state through typed contracts; do not hide it in a singleton or global side channel.
  • Ensure select, duplicate, reorder, compact, and release preserve row-local meaning—also for companions.
  • Either define safe inactive-row behavior or permit exact active-row execution.
B · metadata

Declare legality and dataflow

  • Declare request axes, row-scoped carriers, state/output/effect behavior, and companion relationships.
  • Declare positional selection semantics, including legal repeated source positions for clone/fork operations.
  • Describe valid inactive rows and legal compaction/release behavior.
  • Describe semantic backend requirements—never a scheduling instruction.
C · runtime

Plan and execute work

  • Map logical requests to transient rows/slots, admit work, select compatible live rows, and choose a path.
  • Build one canonical row plan; gather, transfer, execute, scatter, and stage output from that plan.
  • Commit successful rows independently; restore cancelled/failed rows without poisoning healthy siblings.
  • Release, backfill, cache, capture, and allocate only as policy permits.

What changes in the declaration

Metadata describes row semantics, not a scheduler

The current S6 surface already has stable layout vocabulary such as shared, request_aligned, token_packed, and runtime_sequence_state; stateful row-scoped components use row_scope. The examples below distinguish those real terms from a portable conceptual contract. They intentionally do not propose a new continuous_batching: true flag.

Per-contribution declaration: no shared grouping permission

Current vocabulary excerpt; request_aligned says where rows are, not that independent work may be grouped.

# No batch_capacity assertion: invoke once per contribution.
components:
  encoder:
    implementation: { kind: onnx, artifact: encoder.onnx }
    # batch_capacity intentionally absent
    ports:
      inputs:
        features:
          dtype: float32
          rank: 3
          batch_layout: { kind: request_aligned, axis: 0 }

The row axis is still valuable: it keeps inputs and eventual outputs attributable. But the safe interpretation is isolated invocation unless a separate, valid grouped-execution contract is present.

Continuous-batching-capable declaration

Conceptual map using stable current vocabulary where available; labels such as “companion group” are explanatory, not proposed field names.

# Conceptual, portable contract map — not a new schema.
row-scoped carriers:
  tokens / positions / active / RNG:
    batch_layout: { kind: request_aligned, axis: 0 }
  KV + recurrent state:
    state_service: typed, row-local update contract
  logits / emitted tokens / effects:
    positional behavior: row-aligned; publish after commit

component grouping assertion:
  # Current schema calls this batch_capacity. It expresses
  # grouped-vs-solo equivalence constraints, never a queue width.
  same output semantics: yes
  selection: positional; reorder / shrink / duplicate allowed
  companions: follow the same RowPlan exactly once
  inactive rows: neutralized or excluded exactly
  release: legal after per-row commit / abort

For a grouped component, the current batch_capacity spelling is an artifact equivalence/bounds assertion. It is not a fixed deployment batch size, queue limit, fairness rule, or performance threshold.

Strict exclusion

Never serialize scheduler identity or policy into metadata

These are runtime-private facts. They vary per deployment and per iteration, so putting them in a portable package would make its semantics accidentally depend on one scheduler.

request_id physical slot queue fairness batch capacity backfill scheduler performance thresholds deployment batch size

Conceptual code trace

From package load to row-local completion

This timeline gives ownership and ordering, not a claim that every backend has the same implementation. The RowPlan is transient and positional: destination row i selects a source position. It may reorder, shrink, or repeat a position; it never carries a request ID or physical slot.

  1. 0 · load once

    Parse, version, and resolve plans

    Parse metadata, check schema/version, validate contracts, and resolve generalized state, output, effect, and loop plans. A package cannot be accepted by guessing hidden semantics.

  2. 1 · preflight

    Admit before mutation

    Validate axes, carriers, companion closure, inactive-row semantics, and backend requirements. A true unsupported semantic requirement fails before allocation or mutation; lack of shared optimization capability does not.

  3. 2 · per request

    Prepare one request exactly once

    Preprocess prompt/media, capture the S3 committed baseline, initialize or restore semantic state, and reserve state/output journals. Run the authored loop.setup exactly once at loop entry—not “only when it is empty.”

  4. 3 · policy

    Form compatible live rows

    The runtime schedules compatible work and chooses shared or isolated execution according to backend capability, workload, resources, latency/performance policy, and current compatibility.

  5. 4 · transient plan

    Build one canonical RowPlan

    Map logical rows to selected source positions. The plan supports reorder, duplicate, and shrink. Immutable prepared inputs remain authoritative, so retry/abort never depends on a partially rewritten working buffer.

  6. 5 · movement

    Gather and move every carrier once

    Allocate destination views/buffers; select row-scoped input, state, effect, output, RNG, and constraint carriers exactly once; apply the same plan to companions; transfer explicitly to device. Capture/replay is optional and only when eligible.

  7. 6 · forward

    Execute shared or isolated

    Run one shared forward or one isolated forward per row. Inactive rows obey their declared neutral/freeze behavior, or are absent from an exact active-row invocation. No other row’s state or output may change.

  8. 7 · provisional results

    Scatter, update, and stage

    Map outputs and state updates back to logical rows. Stage effects and S4 output publications in per-row journals; do not expose an uncommitted token, media result, or effect to transport.

  9. 8 · row transaction

    Commit or abort independently

    Via S3, successful rows commit. A failed or cancelled row restores its own committed baseline and discards provisional S4 work. Healthy sibling rows remain eligible to continue.

  10. 9 · lifecycle policy

    Emit, release, and optionally backfill

    Publish committed results to transport, release EOS/completed rows, clear ownership, then optionally admit new work or reuse storage. Backfill and slot reuse are runtime policy only.

  11. 10 · next turn

    Continue from semantic state

    A multi-turn request reuses committed semantic state. A prefix cache may accelerate reconstruction, but it is a separate optimization—not session identity, request identity, or proof of batching.

Why “gather every carrier exactly once” matters

Applying different permutations to an attention mask, position input, RNG state, grammar constraint, LoRA selection, K/V state, or emitted output is a silent cross-request corruption bug. A canonical row plan gives every row-scoped carrier the same positional basis; preflight verifies extents before a partial move.

Positional movement, not request identity

RowPlan moves every companion together

This concrete selected-row example uses RowPlan = [2, 2, 0]. It reorders source row 2 before source row 0, duplicates row 2 with defined clone/fork behavior, and shrinks the current live selection by leaving source row 1 out. It does not make a physical slot part of metadata.

Per-row atomic turn

Staged output crosses transport only after each row commits

Three concurrent live rows can reach different outcomes without leaking state or output. The boundary is per logical row: an abort restores that row’s S3 baseline, while healthy siblings commit independently. A completed physical slot becomes reusable storage only after ownership is cleared.

What model authors actually change

Checklist: prove the structural properties

The ONNX graph math sometimes already has these properties. In that case the change can be metadata/exporter work only. Other packages need graph-signature or state-layout changes before their behavior is row-separable and safely portable.

  • Use dynamic/request batch axes and row-aligned inputs/outputs wherever requests contribute independently.
  • Expose position, mask, valid-length, and state inputs when they are semantically necessary; do not reconstruct them from a hidden slot convention.
  • Expose all cross-invocation state as typed state. There must be no hidden singleton/global state that makes one row influence another.
  • Make state updates row-local. A batch-wide reduction or cross-row attention needs an explicit safe structural contract, not an assumption that it will be harmless.
  • Neutralize padded/inactive rows, freeze them as declared, or allow runtime selection of only exact active rows.
  • Keep companions together: lengths, masks, positions, offsets/owners, routing, RNG, constraints, and state/output/effect carriers must follow the same selection.
  • Support deterministic positional select/reorder/duplicate/compact/release. Repeated selection must have defined clone/fork behavior.
  • Ensure the backend/component accepts selected or compacted rows; otherwise the runtime must select the isolated path before mutation.
  • Demonstrate that grouped execution is deterministic and equivalent to isolated execution for each request’s declared results.
Practical implication

A dynamic batch dimension alone is not enough. It permits a larger tensor shape, but it does not establish row-local state, companion alignment, inactive-row behavior, transaction isolation, or an implementation that can safely select live rows.

Guardrails

Common misconceptions

“Metadata schedules.”

No. It proves what can be moved and executed safely. Queuing, admission, fairness, and timing stay runtime-private.

“Batching capability means a fixed batch size.”

No. Structural legality is distinct from a deployment’s current capacity, resource budget, or chosen width.

“Padding is continuous batching.”

No. Padding is one possible representation. It does not prove state isolation, live-row compaction, or safe output publication.

“A prefix cache is batching.”

No. It is a reuse optimization. It neither defines session identity nor proves that two live requests can share a forward pass.

“loop.setup must be empty.”

No. Authored setup may establish real state; it runs once at loop entry, including before a zero-trip loop, rather than once per iteration.

“Physical slots are semantic row IDs.”

No. Slots are runtime storage. Metadata operates on positional row relationships; runtime maps those positions back to logical requests.

Shared vocabulary

Glossary and legend

Logical row
The request-local semantic row a client observes. It survives compaction even if its physical storage changes.
Physical slot
Runtime-private storage position. It is not serialized and has no package-level identity.
RowPlan
A transient positional mapping from destination rows to selected source rows. It may repeat a source for a clone/fork.
Companion
A value such as a mask, length, offset, owner, position, or constraint whose row semantics must move with its primary value.
S3 baseline
The per-row committed semantic checkpoint used to restore a cancelled or failed turn.
S4 journal
Provisional outputs/effects staged until the associated row commits; never exposed as a committed result early.
Shared forward
One backend invocation advancing more than one compatible live row while preserving each row’s independent semantics.
Isolated path
One valid execution per request/row. It is a correct fallback, not evidence that metadata failed.
Inactive-row behavior
The declared neutral/freeze semantics for a retained inactive row, or the guarantee that exact active-row selection is used instead.
