# EP Plugin Export ABI Gap Analysis

**Author:** Nabil (ORT Plugin EP Engineer)
**Date:** 2026-08-10
**ORT version:** 1.27.0 (`ORT_API_VERSION = 27`)
**Scope:** What must be built so that nxrt EPs are loadable by upstream ORT as genuine plugin EPs.

## 1. ORT Plugin-EP ABI Version

Bindings are generated by `bindgen` at build time from the ORT 1.27.0 `onnxruntime_c_api.h`
header, downloaded from `https://github.com/microsoft/onnxruntime/releases/download` with
SHA-256 verification.

- **Source:** `crates/onnx-genai-ort/ort-sys/build.rs:17-19`
- **Constant:** `ORT_VERSION = "1.27.0"`, `ORT_API_VERSION = "27"`
- **ABI:** This IS the "autoep"/plugin-EP API introduced in ORT 1.22+.

**UNVERIFIED** whether ORT 1.27 is the latest upstream release. If upstream has
shipped 1.28+ with breaking plugin-EP ABI changes, those would be missing from
these bindings. The vendored header is not checked into the repo — it is
downloaded at build time. No way to diff without building or fetching the header.

## 3. Outbound Entry-Point Requirements

For upstream ORT to load a plugin EP `.so`/`.dylib`/`.dll`, the library must export:

| Symbol | Required? | Calling convention |
|--------|-----------|-------------------|
| `CreateEpFactories` | **Yes** | `extern "C"` |
| `ReleaseEpFactory` | Optional but recommended | `extern "C"` |

**Signatures are in §2.1.** When ORT calls `CreateEpFactories`, it passes its own
`OrtApiBase` and `OrtLogger`. The plugin uses the `OrtApiBase` to obtain the
`OrtApi` vtable for all host callbacks (graph inspection, tensor access, status
creation, `GetEpApi` for `EpGraphSupportInfo_AddNodesToFuse`). The returned
`OrtEpFactory` must have all function-pointer fields in §2.2 populated.

**Confidence:** HIGH. The inbound loader in `abi/runtime.rs:57-61` and
`abi/mod.rs:648-651` resolves exactly these two symbols. ORT's own
`RegisterExecutionProviderLibrary` resolves the same `CreateEpFactories`.

## 4. Lifecycle Mapping Table

### Direction key
- **Inbound (current):** nxrt HOSTS foreign plugin → nxrt CALLS these callbacks
- **Outbound (needed):** upstream ORT CALLS our callbacks → our code IMPLEMENTS them

| # | ORT Plugin Callback | nxrt Rust Trait Method | Mapping | Notes |
|---|--------------------|-----------------------|---------|-------|
| 1 | `CreateEpFactories` (dylib export) | *None* | **MISSING** | New adapter crate: `cdylib` exporting this symbol. Must store the `OrtApiBase` ORT passes for later graph/tensor access. |
| 2 | `ReleaseEpFactory` (dylib export) | *None* | **MISSING** | Drop the adapter-created factory. |
| 3 | `OrtEpFactory.ort_version_supported` | *None* | **DIRECT** | Hardcode `ORT_API_VERSION` (27). |
| 4 | `OrtEpFactory.GetName` | `ExecutionProvider::name()` | **DIRECT** | Return static CStr. |
| 5 | `OrtEpFactory.GetSupportedDevices` | `ExecutionProvider::device_type()`, `device_id()` | **ADAPTABLE** | Must create `OrtEpDevice` via host's `OrtEpApi.CreateEpDevice`. Need to map `DeviceType` → `OrtHardwareDeviceType`. |
| 6 | `OrtEpFactory.CreateEp` | `ExecutionProvider::initialize()` | **ADAPTABLE** | Construct the Rust EP, call `initialize`, wrap in an `OrtEp` vtable struct. Must capture `OrtApiBase` from step 1 for graph/tensor access in later callbacks. |
| 7 | `OrtEpFactory.ReleaseEp` | `ExecutionProvider::shutdown()` + drop | **ADAPTABLE** | Call `shutdown()`, then drop the Rust EP. |
| 8 | `OrtEp.GetCapability` | `ExecutionProvider::supports_op()` via `OrtGraphView::query_capabilities()` | **ADAPTABLE** | **Key gap:** Must translate ORT's real `OrtGraph` → nxrt `Graph`/`GraphView` by calling host's `OrtApi.Graph_*`/`Node_*` accessors, then run `query_capabilities()`, then report results via `OrtEpApi.EpGraphSupportInfo_AddNodesToFuse`. This is the exact inverse of the inbound host bridge. |
| 9 | `OrtEp.Compile` | `ExecutionProvider::get_kernel()` | **ADAPTABLE** | For each claimed subgraph ORT passes, extract the fused-node boundary shapes, call `get_kernel()` for individual nodes or a subgraph-compile path, wrap the resulting `Box<dyn Kernel>` in `OrtNodeComputeInfo` callbacks. |
| 10 | `OrtEp.ReleaseNodeComputeInfos` | Drop kernels | **ADAPTABLE** | Drop the Vec of kernels. |
| 11 | `OrtNodeComputeInfo.CreateState` | Kernel warm-up / state init | **ADAPTABLE** | Allocate per-session state. May be a no-op for stateless kernels. |
| 12 | `OrtNodeComputeInfo.Compute` | `Kernel::execute()` | **ADAPTABLE** | **Key gap:** Must translate ORT's real `OrtKernelContext` → `TensorView`/`TensorMut` by calling host's `OrtApi.KernelContext_GetInput/GetOutput`, `GetTensorData`, `GetTensorTypeAndShape`, etc. This is the exact inverse of `HostKernelContext`. |
| 13 | `OrtNodeComputeInfo.ReleaseState` | Drop state | **ADAPTABLE** | |
| 14 | Allocator / data-transfer | `ExecutionProvider::allocate/deallocate/copy` | **MISSING** | ORT plugin-EP ABI has optional allocator callbacks not yet inventoried. For CPU EP this is unnecessary (host memory). For CUDA EP this is a hard blocker (§6). |
| 15 | `EpContext` (save/load compiled cache) | `ExecutionProvider::save_context/load_context` | **MISSING** | ORT's `Compile` can return `ep_context_nodes`. nxrt has `EpContext` but no outbound serialization path. Not a launch blocker — can be added later. |

### Summary counts
- **DIRECT:** 2 (rows 3, 4)
- **ADAPTABLE:** 9 (rows 5–13)
- **MISSING:** 4 (rows 1, 2, 14, 15)

### Reusable

| Component | Location | Outbound use |
|-----------|----------|-------------|
| `UnionFind` | `abi/mod.rs:50-84` | `query_capabilities()` uses it to fuse supported nodes into convex partitions. The adapter's `GetCapability` calls `query_capabilities()` which uses `UnionFind` internally. **Fully reusable as-is.** |
| `SubgraphClaim` | `abi/mod.rs:87-103` | The output of `query_capabilities()`. The adapter translates these claims into `EpGraphSupportInfo_AddNodesToFuse` calls. **Fully reusable.** |
| `OrtGraphView::query_capabilities()` | `abi/mod.rs:401-524` | Core capability-discovery logic. **Fully reusable** — the adapter builds a `GraphView` from the ORT graph, then calls this. |
| `OrtGraphView::merge_preserves_convexity()` | `abi/mod.rs:531-540` | Convexity check, used by `query_capabilities()`. **Reusable transitively.** |
| `dtype_to_ort` / `shape_to_ort` | `abi/host.rs:491-500` | Dtype/shape conversion helpers. **Reusable for outbound tensor conversion.** |

### Inverts (need new code in the opposite direction)

| Component | Location | What inverts |
|-----------|----------|-------------|
| `HostGraph` / `HostNode` / `HostValueInfo` | `abi/host.rs:159-494` | Inbound: projects nxrt `Graph` → fake ORT C types. Outbound: must READ ORT's real `OrtGraph` via `OrtApi` → build nxrt `Graph`. Completely new code. |
| `HostKernelContext` | `abi/host.rs:103-145` | Inbound: wraps nxrt `TensorView/TensorMut` as fake `OrtKernelContext`. Outbound: must READ ORT's real `OrtKernelContext` via `OrtApi.KernelContext_GetInput/GetOutput` → build `TensorView/TensorMut`. New code. |
| Host `OrtApi` vtable | `abi/host.rs:536-582` | Inbound: nxrt PROVIDES this vtable to the plugin. Outbound: nxrt CONSUMES ORT's vtable. Dead weight for outbound. |
| Host `OrtEpApi` vtable | `abi/host.rs:585-591` | Same: inbound provides, outbound consumes. |

### Dead weight for outbound

| Component | Reason |
|-----------|--------|
| `PluginRuntime` | Loads *foreign* dylib; outbound has no foreign dylib to load. |
| `PluginKernelShared` / `PluginCompiledKernel` | Wraps foreign plugin callbacks; outbound wraps *our* `Kernel` trait. |
| `HostStatus` | Our fake OrtStatus for plugins we host; outbound uses ORT's real status. |
| Weight mmap cache (`weights.rs`) | Serves initializer data to plugins we host; outbound receives initializers from ORT. |

## 6. Hard Blockers Per EP

### 6.1 `onnx-runtime-ep-cpu`

| Blocker | Severity | Detail |
|---------|----------|--------|
| **Not a `cdylib`** | Must fix | `Cargo.toml` has no `[lib] crate-type = ["cdylib"]`. A new adapter crate (e.g. `onnx-runtime-ep-cpu-plugin`) must be a `cdylib` that depends on the CPU EP rlib. |
| **No `CreateEpFactories` export** | Must fix | No `#[no_mangle] pub extern "C"` entry point exists anywhere. |
| **ORT graph → nxrt Graph translation** | Must build | The adapter must read ORT's real `OrtGraph` using the `OrtApi` callbacks from `OrtApiBase`, build an nxrt `Graph`, and create a `GraphView` for `query_capabilities()`. |
| **`OrtKernelContext` → `TensorView/TensorMut`** | Must build | The `Compute` callback must extract tensors from ORT's `KernelContext` via `OrtApi.KernelContext_GetInput/GetOutput`, `GetTensorData/GetTensorMutableData`, `GetTensorTypeAndShape`. For CPU, all pointers are host-accessible, so this is mechanical. |
| **Allocator** | Low risk | CPU EP uses host `malloc`. ORT already allocates host memory for CPU tensors. No cross-EP allocation needed — the `Compute` callback just operates on ORT's host buffers. |
| **Estimated effort** | **Mechanical** | All blockers are adapter glue. No architectural changes to the CPU EP itself. |

### 6.2 `onnx-runtime-ep-cuda`

All CPU blockers above apply, PLUS:

| Blocker | Severity | Detail |
|---------|----------|--------|
| **CUDA context/device ownership** | Hard | nxrt `CudaRuntime` creates its own CUDA primary context. ORT also creates/manages CUDA contexts. Must share the CUDA context or the device pointers from ORT's allocator are invalid in nxrt's context. The adapter must either (a) adopt ORT's CUDA context via `cuCtxSetCurrent` before calling any nxrt CUDA kernel, or (b) use ORT's allocator for all device memory and translate pointers. |
| **Stream ownership** | Hard | nxrt CUDA EP creates its own compute/transfer streams. ORT provides its own stream to the plugin via `OrtKernelContext`. The adapter must ensure kernels run on ORT's stream, not a private stream, or synchronize between them. |
| **cuBLAS/cuDNN handle binding** | Hard | nxrt creates cuBLAS/cuDNN handles bound to its own stream/context. These must be re-bound or re-created for ORT's context/stream. |
| **Device memory in `OrtKernelContext`** | Hard | ORT passes device pointers via `KernelContext_GetInput`. These are allocated by ORT's CUDA allocator. The `Compute` callback must use them directly (they're just `CUdeviceptr` values valid within the shared context) rather than copying to nxrt-allocated buffers. Requires the shared-context solution above. |
| **Weight paging / offload** | Blocked | nxrt's `CudaWeightResidency` manages its own VMM pool. In the outbound plugin model, ORT owns weight memory. The paging system cannot operate. Must be disabled or redesigned for the plugin case. |
| **Device graph capture** | Blocked | nxrt's segmented CUDA graph capture assumes ownership of the stream. In the plugin model, ORT may have its own graph capture semantics. Must be disabled or coordinated. |
| **VMM allocator** | Blocked | nxrt's CUDA VMM allocator (`cuMemCreate`/`cuMemMap`) manages its own address space. In the plugin model, ORT provides device memory. Must either share VMM or forgo the VMM allocator. |
| **Estimated effort** | **Significant** | Requires a CUDA context/stream sharing design. The minimum viable path is: (1) adopt ORT's CUDA context, (2) create cuBLAS/cuDNN handles on ORT's stream, (3) disable weight paging and graph capture, (4) operate directly on ORT's device pointers. |

## 7. Recommended Implementation Order

1. **Adapter crate scaffold** (`onnx-runtime-ep-plugin-adapter` or per-EP cdylib): `CreateEpFactories`/`ReleaseEpFactory` exports, `OrtEpFactory`/`OrtEp` vtable construction.
2. **ORT graph reader**: read `OrtGraph` → nxrt `Graph` using the `OrtApi` host callbacks. This is the inverse of `HostGraph::new()`.
3. **Capability bridge**: `GetCapability` → `query_capabilities()` → `EpGraphSupportInfo_AddNodesToFuse`.
4. **Compile bridge**: `Compile` → per-node `get_kernel()` → `OrtNodeComputeInfo` wrappers.
5. **KernelContext bridge**: `Compute` → `OrtKernelContext` tensor extraction → `Kernel::execute()`.
6. **CPU EP plugin**: wire steps 1–5 for `CpuExecutionProvider`.
7. **CUDA EP plugin**: CUDA context/stream sharing design, then wire steps 1–5 for `CudaExecutionProvider`.
