fix(scheduler): cap the admitted ceiling instead of refusing the request

Justin hit "scheduler did not admit the session generate request" on the
ORT backend with CUDA, running a reasoning model for several turns, right
after the shared GQA KV allocation.

Root cause: PR #277 changed the CLI default max_new_tokens from 128 to the
remaining context window. The scheduler reserves the worst-case footprint
prompt + max_tokens up front, deliberately, so an admitted sequence can
never push the shared cross-session KV budget over its ceiling
(DESIGN.md 26.4/26.11). That was fine when the ceiling was 128 and becomes
unsatisfiable when the ceiling is the whole window.

The conservative reservation is kept, because it is what guarantees an
admitted sequence can run to completion. Instead the admitted ceiling is
capped to what the budget can actually serve, so the request is served
with a smaller bound rather than refused outright. The invariant holds:
the ceiling was reduced to fit, not the reservation weakened.

The cap is observable rather than silent, which was the harder half. It is
reported on stderr, exposed as GenerateResult.budget_cap, and carried into
the stats and profile output in both text and JSON. Callers can therefore
distinguish "the model finished" from "we shortened your budget" -- which
matters because this CLI is used for benchmarking, and an invisibly
shortened token budget corrupts a measurement without ever looking wrong.
No new FinishReason variant: budget_cap carries the distinction, which is
proportionate and keeps the enum stable.

Also confirms an asymmetry Justin observed: the native backend never hits
this because native generate bypasses scheduler admission entirely, while
ORT generation goes through it. Both load paths do set bytes_per_token, so
the difference is the code path rather than configuration.

Adds cancel cleanup so a failed admission cannot leak queued or running
entries, and rewrites the admission error to name the cause, the numbers,
and a next step, per RULES.md rule 1.
