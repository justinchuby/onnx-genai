feat(engine): session checkpoint and KV rewind, with fork reserved behind a capability

Justin asked for session fork and KV rewind to be drivable from the REPL.
The capability inventory found both need new runtime APIs rather than CLI
wiring. This lands rewind, and reserves fork behind a type-level gate that
no backend currently opens.

Rewind is real and usable: SessionCheckpoint, checkpoint_session,
restore_session, rewind_session_by, rewind_session_to. It supports the ORT
runner, static-cache and shared-buffer paths, and paged materialized KV
within retained-position constraints. Native persistent sessions are not
supported and say so.

Fork is deliberately NOT enabled. fork_session requires a
SessionForkCapability, and every backend currently yields None, so the
unsupported call is not expressible at a call site rather than failing at
runtime from deep inside decode. Enabling it needs DecodeState runner
clone/import to be provably safe; shipping a fork that silently deep-copies
or aliases KV would be far worse than shipping none. The boundary is
documented in docs/research/cli/06-fork-rewind-api.md so the REPL work has
an accurate contract to code against.

The API uses distinct types -- SessionPosition, RewindTokenCount,
SessionForkCapability -- rather than bare usize, so a position and a token
count cannot be transposed at a call site.

Adds proptest as the workspace's first property-based test dependency, used
for randomized fork/rewind/append/remove sequences against the page
refcount model, where hand-written cases cannot cover the interleavings.

Miri was not applicable: none of the touched KV code uses unsafe or raw
pointers. No TLA+ spec was written -- the page refcounting is single
threaded and already covered by proptest, so a spec would have added an
unmaintained artifact rather than a guarantee the type system does not
already give.
