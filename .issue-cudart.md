@justinchuby — you asked whether we should treat cudart as a dependency. Short answer: **yes, take the dependency — but on the wheel for its *headers*, not on `cudart64_*.dll`.** We currently gate on the DLL, which is the one part we do not need. Everything below is measured on this machine, not recalled.

You were right to push back on my earlier framing. I had said "this machine has no cudart", which was wrong: it is not in `System32`, but it *is* in the pip wheel layout, which is exactly the layout `dynamic_library.rs` already knows how to search.

## 1. Is `cudart64_*.dll` needed? No.

You said we default to cuBLASLt and NVRTC, so cudart comes along. That is the reasonable assumption, and it turns out not to hold. Import tables (`dumpbin /dependents`, NVIDIA cu12 wheels):

| library | imports |
| --- | --- |
| `cublasLt64_12.dll` | `KERNEL32.dll` |
| `cublas64_12.dll` | `cublasLt64_12.dll`, `KERNEL32.dll` |
| `nvrtc64_120_0.dll` | `USER32`, `KERNEL32`, `ADVAPI32`, `ole32`, `SHELL32` |

None of them import `cudart64_*.dll`. NVIDIA statically links the runtime into its redistributables. They do not import `nvcuda.dll` either — they `LoadLibrary` the driver on demand.

And on our side, no cudart symbol is ever looked up. Every `cudaXxx` occurrence in the repo is a comment; `CudaLibrary::Runtime` appears only in the filename table, the wheel-component map, two unit tests, and one line:

`crates/onnx-runtime-ep-cuda/src/runtime.rs:257` lists `CudaLibrary::Runtime` among the hard preconditions of `CudaRuntime::new`.

That line is the whole cost. The comment above it says the intent is to preload cuBLASLt's dependency chain so we do not need a system CUDA install — a good intent, but the chain is `Cublas -> CublasLt`, and `Runtime` is not in it. Gating on it separately adds no safety, because `require(Cublas)` already fails loudly if cuBLAS cannot load whatever it needs. It only converts "works" into "fails" on machines that could run us fine.

## 2. Is the cuda-runtime *wheel* needed? Yes — for headers.

This is the real dependency, and it is not the one we gate on. NVRTC compiles our f16/bf16 kernels from source, and that source includes `cuda_fp16.h` / `cuda_bf16.h`. Those ship in `nvidia/cuda_runtime/include/`.

Demonstrated, same machine, same commit — only `CUDA_PATH` differs:

```
# DLLs on PATH, no CUDA_PATH
matmul_f16_gemv_on_gpu_matches_cpu_reference ... FAILED
  f16/bf16 NVRTC kernels require cuda_fp16.h and cuda_bf16.h
test result: FAILED. 4 passed; 1 failed

# CUDA_PATH=<site-packages>/nvidia/cuda_runtime
test result: ok. 5 passed; 0 failed
```

Our own error message already says the right thing. The gate does not.

So the dependency is real, it is on `nvidia-cuda-runtime`, and what we consume from it is `include/`, not `bin/`.

## 3. What this cost us: the GPU suite was silently unavailable

There are **44 `*_gpu.rs` test files** in `onnx-runtime-ep-cuda`. On this machine they were all skipping, and a skip reads like a pass.

The cause is a plain gap: `set_wheel_search_paths()` has exactly one caller, `crates/onnx-runtime-python/src/lib.rs:1514`. The Python bindings discover NVIDIA wheels. **Nothing in the Rust path does.** So `cargo test` finds `nvcuda.dll` (ships with the display driver) but not cuBLAS/NVRTC/headers, and every GPU test skips.

Putting three wheel `bin` directories on `PATH` and setting `CUDA_PATH` was enough to bring the suite up — including `matmul_f32_gemv_matches_cublaslt_bitwise`, which genuinely exercises cuBLASLt. So the hardware and libraries were here the whole time; only the discovery was missing.

## Proposed decisions

1. **Take the `nvidia-cuda-runtime` dependency, and say it is for headers.** Document it as the NVRTC f16/bf16 header source.
2. **Stop gating `CudaRuntime::new` on `CudaLibrary::Runtime`.** Preload it opportunistically if present — it is genuinely in the chain on some platforms and I have only verified Windows — but do not fail construction on its absence. `require(Cublas)` still fails explicitly if cuBLAS cannot load, so no failure becomes silent; it just gets attributed to the library that actually could not load.
3. **Give the Rust path the wheel discovery the Python path has.** Today only `onnx-runtime-python` calls `set_wheel_search_paths`. A shared discovery step, used by both, would stop 44 GPU test files from skipping on a machine that can run them.
4. **Make the skips loud.** Separately worth doing regardless: a skip that is indistinguishable from a pass is how this stayed invisible.

## Not verified

- Only Windows import tables were inspected. `libcublas.so.12` may link `libcudart.so.12` on Linux; NVIDIA statically links there too as far as I know, but I have not run `ldd` on it. Recommendation 2 is deliberately written to be safe either way.
- cu13 wheels: `nvidia-*-cu13` failed to build here, so this used the cu12 wheels already present. `dynamic_library.rs` accepts both, so this is not a blocker, but the cu13 story is unconfirmed.
