evidence(goldens): run the pinned packages against a clean main baseline

The previous `REAL_MODEL_EVIDENCE.md` was captured at `5a58eafa`, described a
lowering step that no longer exists, and compared nothing to `main`. It has been
replaced with a matrix produced by running one probe against two builds — a
clean `origin/main@cb81745b0` worktree and this branch — on the same machine
against the same bytes.

**The load-bearing result.** `justinchuby/qwen3-0.6b-onnx-genai@a89c02d3` decodes
16 greedy tokens byte-identically on both:

    3988,0,358,2776,773,12035,311,387,1588,0,358,2776,773,12035,311,387

Those are not the same code path. `main` loaded this package from its
`genai_config.json` and ran it on the fused decode core, *ignoring the
`pipeline.workflow` it ships*; head reads the declared workflow — eleven ONNX
components, an in-graph sampler, an in-graph termination predicate — and runs it
through the interpreter. Same weights, different execution, same tokens.

**Two packages `main` cannot run at all.**
`onnx-genai-example-gemma4-e2b@b1189a9b` fails before generating
(`cannot resolve decoder state from tensor shapes`) and
`onnx-genai-example-gemma4-e2b-speculative@3e5d3b6a` fails to *load*
(`declared kv_outputs port 'present.4.key' is not exposed by the graph`). Both
load on head and open sessions. That is also why the composite paths have no
baseline comparison: there is nothing on `main` that runs them.

**Two behaviour changes, reported rather than summarised away.** Seeded sampling
differs, because head uses the sampler the package declares instead of
substituting the runtime's. And multi-turn continuation is *lost* for
`qwen3_0_6b`: `main` carried KV across turns through the decode core, head
executes the package as declared and its workflow declares no `scope: session`
state, so each turn is independent and `prefix_cache_hit_len` is honestly `0`.
That is a real regression for this package, called out as one, with both possible
fixes named and neither taken here.

**Two defects the pinned packages found, fixed here.** `generate_in_session` on a
package with no decode core reached `require_tokenizer()` and failed, because
only the `_with_callbacks` wrapper had been routed to the interpreted session
path — every variant now routes through the same place. And a text prompt against
a package declaring a `prompt_tokens` input was refused with "use a tokenizer
adapter for text" *even when the package shipped `tokenizer.json`*; the runtime
now encodes with the package's own tokenizer. Without that second fix, result one
above could not have been measured at all.

**A gap, stated.** Both Gemma4 packages declare `request.active`/`done`/
`accepted_len` as required application inputs with no default, so
`Engine::generate` with a bare prompt cannot seed them. Composite speculative
generation at widths 1/2/4 against *those two packages* therefore has no
measurement here, and the hermetic `gemma4_chained` fixture is not substituted
for it — that fixture is covered separately, including the CUDA
propose/verify/reject/rollback gate, and conflating the two would be the kind of
evidence that reads as coverage without being it.

`capture_pinned.sh` prints `COVERED=`, writes `MISSING_DIR` for an absent package
and the probe's error for a failing one, and has no allow-empty escape hatch: a
corpus that quietly emptied would diff clean.

Also: the FIM streaming case asserted its headers arrived within 100 ms. That
budget measures the machine, not the ordering property — it fails on a saturated
box under `--test-threads=$(nproc)` while the request itself takes milliseconds.
Measured end-to-end (load plus six 64-token generations) head is 115 ms against
the baseline's 109 ms, so the budget is now two seconds, which still separates
"after admission" from "after generation" by orders of magnitude.

Verified: 241 server tests, engine suites, fmt, clippy `-D warnings`.
