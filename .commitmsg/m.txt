test(pipeline): measure which executor an authored body selects

The convergence's central claim is that a package's declared body — not Rust
inspecting the package — decides which loop algorithm runs. That claim was true
after the previous commit and entirely unmeasured: every existing test asserts
that tokens came out, and tokens would keep coming out if a `match` on package
shape quietly came back.

So the interpreter now counts, inside its own node dispatch, how many nodes it
routed to a registered executor per contract id. Three packages declaring three
different bodies are driven through **one** entry point and the counters differ:

* `tiny-llm` names `autoregressive-decode` and `token-policy`, and shows exactly
  five of each for five tokens — one declared node per step, and nothing else.
* the `decoder` fixture authors its sampler and termination predicate as ONNX
  components, and shows **zero** contract executions. That negative is the more
  interesting half: a non-zero count there would mean the runtime had supplied a
  step the package shipped a graph for, which is precisely how a declared
  document becomes decorative.
* the `speculative` fixture authors a proposer, a verifier and grammar adapters,
  and runs those.

What varies across the three is the *request* — a prompt for a package that
takes one, declared tensors for a package whose inputs are tensors — never the
method. `generate_with_pipeline_request` resolves a prompt-only request to the
session-aware path, so a caller with a plain prompt still gets scheduler
admission, prefix reuse and the fused decode executor rather than quietly giving
up all three by having chosen the "pipeline" call.

**Composite HTTP sessions.** `/v1/sessions` used to reject a package the
interpreter drives, on the grounds that it owns no decode-core KV sequence. That
conflated two things: a session is the conversation a client is having, and
where the runtime keeps it is not something a client can act on. A client that
opened a session against one package and got a 400 against another would have to
know which kind it was talking to — the caller-side split this work removes. The
new server case opens and closes one against an interpreted package.

**Docs.** `WORKFLOW_RUNTIME_UNIFICATION.md` described two executors picked by
`WorkflowShape` and a `canonical_workflow` guard on every decode entry point.
Neither exists. It now states what landed, including why the missing-workflow
state is unrepresentable rather than guarded, and points at the counter test as
the thing that measures the selection claim.

Verified: engine and server suites; the new selection cases; the shape-dispatch
gate at zero; fmt; clippy `-D warnings`.
