fix(engine): multi-EOS on the batched routes; seal the test seam; drop the PR-local fixture guard

Addresses review B1 and the contained N-items. B2 (making the interpreter own
the AR loop) and B3 (baseline-from-main evidence) are **not** in this commit;
see the PR discussion for the blocker.

**B1 — batched routes resolved their own EOS.** `ContinuousBatchManager::submit`
and `generate_batched_static` each set `eos_token_id` from the tokenizer's
*first* id and never saw the package's declaration. That is the server's default
route for a fixed-capacity package, so a multi-EOS model stopped correctly in
single-row generation and ran past its end under serving — invisible from the
API. Both now resolve the full set from the same source the single-row path
uses, through one shared `apply_eos_policy`; the manager carries the resolved
set because it holds a tokenizer, not the engine, and cannot reach the workflow
once it holds a mutable session borrow.

`generate_batched_static` also checked "is this a static-cache model" *before*
the canonical guard, so an unloadable package was reported as a batching
capability problem. The invariant is now the prior question.

**The batched test is deliberately in-crate.** No CPU fixture in this repository
can batch — a shared KV buffer needs an EP reporting fixed-capacity present
binding, and `batching_capability` asserts exactly that absence. An end-to-end
batched case would therefore *skip*, and a skipped test reporting success is
worse than no test. `batched::tests::
a_continuous_row_stops_on_a_non_first_declared_end_token` drives a real
`ContinuousBatchManager` row loop over a scripted decode and requires the row to
end at a **non-first** declared id; with the old code the row runs to the
budget. The `multi_eos` module header records why the end-to-end case is absent
rather than pretending it ran.

Investigating this surfaced that `Engine::generate` on a fixed-capacity package
has never worked end-to-end: `tiny-llm-scatter-workflow` fails on a contract/graph
mismatch (`key_cache.0` axis 2 declares 4, the graph exposes 16). Pre-existing
and pre-dating this branch — the static-cache fixtures are only ever driven
through `StaticCacheDecodeSession` directly. Recorded, not silently worked
around.

**Malformed EOS declarations now error.** `literal_token_ids` used `filter_map`,
so a package declaring `[2, -1]` silently kept one id — the package says "these
tokens end me" and the runtime quietly keeps a subset. It returns `Result`, and
`apply_eos_defaults`/`fim_options` propagate it.

**`forget_canonical_workflow_for_test` is `#[cfg(test)] pub(crate)`.** It
produces a state no public API can reach, which is the whole point of the
refusal it supports; exposing it made that state reachable. The refusal tests
move in-crate to `canonical_refusal_tests` and gain a fifth entry point
(`generate_batched_static`).

**The PR-local fixture guard is deleted.** Main's repository-wide, zero-allowlist
`onnx-std/tests/fixture_ir_opset_guard.rs` supersedes it, and my own guard's doc
said to replace it when that landed. It passes on this branch's fixtures.

I tried extending that guard to inline model literals in `.rs` sources and
reverted it: raising `opset_import` from 13 to 24 without porting the ops
produces *invalid* models (`ReduceMax` moved `axes` from attribute to input in
opset 18, and the bumped fixture was rejected by ORT). Many inline literals are
also deliberate legacy-IR *parser* inputs — a loader must still parse IR 8 to be
tested for it. Committed fixture files have generators and are the right scope;
inline literals are not fixtures. This branch's own inline models are at the
floor.

Verified: 73/73 engine targets; downstream metadata, scheduler, CLI, C API,
onnx-std green — the one server failure is the known
`fim_stream_returns_headers_before_generation_finishes` load-flake, 3/3 in
isolation; fmt; clippy `-D warnings`.
