perf(speculative): narrow and score where the tensors already are

A chained proposal's per-token work is supposed to stay on the device that
produced it. Whether it does was, until now, unmeasurable from inside the
process — a reintroduced copy shows up months later as "it got slower",
attributed to anything but the line responsible.

**The measurement first.** `WorkflowRuntime` counts every device→host
materialization it performs. The count lives in
`materialize_workflow_value_copy`, which is the one place such a copy can
happen, so a future caller is counted without having to remember to count
itself. `chained_speculative_proposal_parity_native_cuda` reads it across a
propose/verify/reject/rollback decode on an H200.

That measurement is what makes the rest of this honest. The count today is
**16** for `speculative_decode(8, 4)`, and the assertion is a ratchet at that
number rather than a zero, because 16 is what the remaining work costs and
claiming otherwise would be a lie the tokens would not catch: a chain that
staged everything on the host produces byte-identical output.

The two remaining sites are named in the assertion. Both are the *folded carry*:
its seed, once per proposal, and the carry itself, once per draft token. Both
exist because the fused proposer input is assembled on the host —
`concat(embed(token), carry)` — so the carry has to come down to be
concatenated and the whole fused input goes back up. Removing them needs the
fused input built in device memory, which is a device-side scatter this seam
does not have; faking it with a staging copy would satisfy the counter and
change nothing.

**What did move.**

*Narrowing happens where the value is.* A borrowed proposer binding used to be
copied to the host in full and then narrowed to one position, discarding every
byte of the copy on the next line. `ResidentTensorOps::last_along_axis` narrows
in place: on a device value whose sequence axis is outermost this is a pointer
view via the new `Value::alias_with_offset`, and on an inner axis it refuses
rather than staging — a strided device copy belongs to the provider that owns
the stream.

*Argmax reads four bytes, not a vocabulary.* The per-draft-token argmax copied
a `[1, 1, vocab]` row down to find one token id — ≈300 KiB at vocab 151936 in
f16, per token. `device_argmax_rows` runs the same kernel the decode fast path
already uses, directly on the ORT device pointer, with the same lowest-index
tie-break and NaN handling as `Value::argmax_last_row` so no token changes.

*The embedding table is read once.* A `[vocab, hidden]` initializer was read off
disk on every `propose_chained`. A loaded package's artifact cannot change under
it, so it is now cached for the runtime's life.

**Fail-closed.** `tensor_ops_for` returns host ops for a host value and CUDA ops
for a device one; a device value in a build with no device implementation is an
error naming both remedies — select the host backend, or build with `ort-cuda` —
never a quiet copy.

`Value::alias_with_offset` takes an *element* offset rather than a byte offset,
because a byte offset invites exactly one mistake — forgetting the dtype width —
that a device pointer will not diagnose until a kernel reads garbage.

Verified on H200: all 12 `native_workflow_parity` cases including both chained
parity gates; 9 `gemma4_chained_workflow` cases; the alias-offset cases; engine
and ort suites; fmt; clippy `-D warnings`.

Note: `onnx-genai-ort`'s `selected_non_dense_candidate_fails_explicitly` fails
identically on `origin/main@cb81745b0`, checked in a clean worktree. It is not
from this branch.
