fix(engine): address the Opus rubber-duck review

An Opus 4.8 review challenged three claims. Two were right and are fixed here;
one was wrong and the docs now state what is actually true.

RIGHT — the lowered workflow was decoration. `lowered_workflow` was stored and
only ever read as `.is_some()`; the contract ids were validated at load but
nothing dispatched on them, so a bespoke Rust loop ran while the spec sat unused.
`run_canonical_decode` now resolves its loop body *from the workflow*
(`resolve_body`) and dispatches each step by contract id. Reorder the emitted
steps, name a contract this runtime does not implement, or omit the policy, and
execution changes or fails accordingly. The spec is executed, not attested.

RIGHT — the fail-closed guard covered one entry point. It sat in
`generate_with_callbacks`, so `generate_in_session*` -- the path the server
actually uses -- and `generate_with_sampler` reached decode without it. The check
now lives where the loop resolves its workflow, which every decode entry point
must pass through, and the test drives all three rather than only `generate()`.

WRONG — "batched decoding is a second sampling implementation". It is not:
`batched.rs` and `speculative/mod.rs` both call the shared
`select_next_token_with_rng` / `logprob_for_token` / `commit_selected_token` /
`ensure_constrained_finish` / `finish_result`. What they have is a different
iteration shape -- N rows per forward pass, and a proposed block rather than a
token -- which is inherent to what they do, not duplication. The module doc and
the design note now say exactly that instead of claiming one loop reaches every
request, which was overstated.

Also from the review:

* `canonical_lowering_corpus` passed silently on a weightless machine, which its
  own doc said it must not. Its cases now fail when they covered nothing unless
  `ONNX_GENAI_ALLOW_EMPTY_CORPUS=1` acknowledges the run.
* `one_runtime_e2e::session_lifecycle_is_one_api` tolerated the very behavior it
  claimed to enforce -- an `Ok` from a workflow package's `create_session()` fell
  through the `if let Some(error)`. It now requires the refusal.
* Stale `run_decode_loop` references in `native_speculative.rs` and
  `profile_native.rs` fixed; the function is gone.

The review also confirmed, by diffing against main, that the `forward_step` /
`select_and_commit_step` split preserves the old `step_decode_loop` exactly:
device-sample `Ok(None)`-stays-armed vs `Err`-latches-off, the single RNG draw
reused by the host fallback, logprob capture only on the host branch, and
`commit_token` before `commit_selected_token`. Goldens agree -- the same 5 real
models remain byte-identical to the c58eb5b2 baseline.

Verified: engine 72 targets green under `native-backend`; downstream 30 green
(one timing-sensitive server streaming test flaked under full-suite load and
passes 3/3 in isolation, same class as the earlier stalled-output flake); H200
native-cuda green (canonical_execution_parity 8, native_workflow_parity 12,
one_runtime_e2e 5, fixture floor 3); fmt clean; clippy `-D warnings` clean apart
from a `too_many_arguments` lint on `engine/placement.rs` that arrived with main.
