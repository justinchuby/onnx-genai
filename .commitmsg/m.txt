fix(engine): route the prioritized drive through the canonical body

The Opus verification pass found the last caller that still owned its own
iteration. `drive_prioritized_requests` / `drive_prioritized_arrivals` went
`prepare_active_generate` -> `step_active_generate` -> `step_decode_loop`,
never resolving the canonical workflow. So the claim "every single-row
autoregressive request executes the lowered workflow" was true of the
run-to-completion paths and false of the scheduler's per-step drive — which is
the path the server actually uses under load.

Rather than add a second guard, factor the loop so there is one body:

* `CanonicalBody::resolve` binds the spec's loop body once, and
  `step_canonical_body` runs one iteration of it. `run_canonical_decode` is now
  that same body run to completion, so "run" and "step" are not two policies.
* `ActiveGenerate` carries the resolved body, so the scheduler resolves the
  workflow when it prepares a request instead of re-reading the spec per token.
* `step_decode_loop` is **deleted**. With `run_decode_loop` already gone, no
  loop in the crate can decode without a canonical workflow to read.

Also from the review:

* The guard is hoisted above admission and KV mutation in
  `generate_in_session_with_priority_and_callback`, so a package without a
  canonical workflow is refused before it can mutate session state, and the ORT
  speculative branch can no longer return ahead of it.
* `BodyStep::Emit` is load-bearing: it carries the output it targets,
  resolution rejects an emit into an undeclared output, and a body that never
  emits the tokens output is refused. Previously `Emit` resolved to a no-op, so
  the spec could say "emit nothing" and the loop would still stream tokens.
* Seven `resolve_body` unit tests pin those refusals, each mutating the real
  lowering into a spec that would still load but describes something this
  runtime cannot honestly execute.
* `canonical_execution_parity` gains a fourth refusal case covering the
  prioritized drive, so the fail test now proves all four entry points.

Docs: §1 is marked as the pre-change measurement, §6 is rewritten from
"remaining code" to what actually landed, and the stale `run_decode_loop` /
`step_decode_loop` references are corrected. §6 also states plainly why
`batched.rs` and the speculative propose/verify block remain: they are
different iteration shapes over the same policy primitives, not second copies
of the single-row loop.

Verified: 72/72 engine targets (native-backend); downstream server/CLI/CAPI/
metadata (the one failure, `fim_stream_returns_headers_before_generation_
finishes`, is the known load-flake and passes 3/3 in isolation); H200 CUDA —
canonical_execution_parity 8, canonical_lowering_corpus 5, gemma4_chained_

fmt --check; clippy -D warnings. All five real foundry models are
