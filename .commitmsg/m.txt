feat(engine): the declared loop semantics become load-bearing, fail-closed

B2 checkpoint 3, and the review's "no ignored declared semantics" item.

The interpreter's `Loop` node already honours everything a workflow declares —
`continue_when`, `max_iterations`, `termination`, `carried`, `iteration`, and
`service_group` cells whose buffers the runtime owns. The decode executor did
not: it read the body's *steps* and supplied the loop itself, taking the
iteration bound from the request's `max_new_tokens` and the stop from the
runtime's token policy.

That is faithful only if the workflow declared those same things. A package
saying `max_iterations: package.some_literal`, or `termination: predicate`, or a
`continue_when` naming a cell the token policy never writes, describes a loop
this executor would silently override — the tokens still come out, and they are
the wrong tokens for the workflow as written. A reader of the YAML could not
detect that, and neither could a test that only checked token counts.

`validate_loop_semantics` now checks each declared field against what the
executor actually does and refuses a mismatch, naming the field:

* `termination` must be `generation_eos`. A predicate-terminated loop states its
  stop condition in the graph, which is a different kind of workflow and belongs
  to the generic interpreter.
* `max_iterations` must name a declared input carrying a `max_iterations` /
  `max_output_tokens` role, because the executor bounds generation by the
  request — a bound it cannot see is a bound it would ignore.
* `continue_when` must be the serving contract's `active` cell, because that is
  the cell the token policy writes; any other predicate would never be updated
  and the loop would never stop.
* every carried cell must be declared state.

Five tests, one per field, each mutating the real lowering into a workflow that
still parses and validates but describes something this executor does not
implement.
