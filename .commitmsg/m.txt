fix(engine): a model with several end tokens stops on any of them

Multi-EOS was broken in three independent places, and the failure was silent:
generation ran past its end and emitted control tokens as ordinary text, which
reads like the model rambling rather than like a runtime dropping a
declaration. Muse-Glimmer needs both `<|eot|>` and `<|eom|>`.

**1. A package could not express the set.** `literal_shape` resolved every
symbolic axis to 1, so a `[eos_count]` contract with a two-element literal
failed with "declares 2 elements but its contract holds 1" — a package
describing itself correctly was unloadable. The singleton guess is right for a
*scalar* literal, which nothing else sizes; an **element list carries its own
extent**, and discarding it threw away the only information available. When
exactly one axis is symbolic the list now divides out the fixed axes to size it.
With more than one unbound axis the split is genuinely ambiguous, so the guess
stands and the caller gets the element-count error, which names the real
problem.

**2. The declaration was dead.** `package.eos_ids` was a name a fixture used;
nothing read it. There is now a semantic role, `eos_token_ids`, so a package
declares its stop condition where it declares everything else, and
`declared_eos_token_ids` reads it into the stop policy. A package shipping no
tokenizer side-files still stops correctly. The package's ids and the
tokenizer's are merged (package first) so neither source can silently drop the
other's.

**3. The policy compared one id.** `options.eos_token_id == Some(token)`
appeared in three places — the processor path, the no-chain fast path in
`decode_loop`, and the constraint processor's `is_eos`, which decides whether a
grammar may finish. Each was a separate answer to the same question, and a
grammar treating a model's second end token as ordinary text while the loop
treated it as terminal is exactly the kind of disagreement that is impossible to
debug from the output. `GenerateOptions::terminates` is now the single decision
and all three call it.

`eos_token_id` keeps its meaning as the id a result *reports* and a caller's
addition to the set — it does not narrow it. A model's end tokens are facts
about the model; a request cannot make the runtime emit one as text.

An earlier attempt routed the extra ids through `stop_sequences`. That stopped
generation but reported `FinishReason::StopSequence`, which tells a caller
"you hit a stop string" when the model ended its own output. Reusing an
adjacent mechanism produced the right control flow and the wrong answer, so the
policy carries the set instead.

The importer and the migration tool both carry every id across:
`genai_config.json` already normalizes a scalar or an array, and the converter
reads the package's generation defaults.

**Tests** (`tests/multi_eos.rs`, 4 cases): a package can declare several ids at
all (the `literal_shape` regression); each declared id stops generation, once at
the first generated token to exercise prefill and once at a later token to
exercise cached decode; a request naming one id does not disarm the others (the
Muse-Glimmer shape); and the declaration survives a session.

Also: the last stale `model_io` identifiers are renamed
(`derive_model_io_spec_from_graph` → `derive_decoder_abi_from_graph`, and the
locals in `engine/load.rs`). No `io:` key exists anywhere in the repository, and
the only remaining mentions of the retired block are the rejection that explains
it and the migration guidance that names the conversion.
