fix(engine): close the guard gaps the final review found

The final rubber-duck review confirmed the two carried findings resolved but
found the ordering fix had not been applied uniformly, and that two claims in
the module docs were simply false. Both are fixed here.

**The guard ordering was fixed on ORT only.** Both native paths still resolved
the canonical workflow *after* scheduler admission and workspace prep
(`generate_native_cold_with_callback`, `generate_native_in_session_with_callbacks`),
and on failure returned via `?` without `scheduler.complete(..)` — leaking the
admission, unlike the workspace-prep error immediately above which unwinds it
explicitly. Both guards now run before admission, so a refusal cannot consume a
slot or disturb session state and there is nothing to unwind.

**Batched and continuous decode were not guarded at all.** They advance N rows
per pass rather than one, so they are deliberately not the canonical single-row
body — but they are still this runtime producing tokens, and they would have
decoded happily with no canonical workflow present. That is a real hole in "no
package decodes without a canonical workflow", not a technicality.
`generate_batched_static` and `continuous_batch_manager` (the single admission
point both continuous entry points funnel through) now resolve the guard, and
`batching_runs_through_the_canonical_loop` — which asserted only token counts
and so could not have caught this — is rewritten as
`batched_generation_is_held_to_the_canonical_precondition` and asserts the
refusal.

**Two docstrings claimed more than the code delivers.** `canonical.rs` said a
lowered decoder and an authored workflow "share a single implementation" of the
token policy, and `canonical_decode.rs` said they "reach the same runtime
instead of two". Neither is true: the contracts are dispatched only on the
lowered path, and an authored workflow runs the general interpreter with
in-graph sampling. Both now state what is actually unified — one single-row
autoregressive loop and one Rust next-token policy — and why the lowered path
has its own executor at all (the rich sampler, paged KV, sessions and
speculative decode have no in-graph representation).

Also: `NATIVE_WORKFLOW_BACKEND.md` and the July benchmark note still described
`run_decode_loop` as live; they now name the symbol that exists and mark the
"specialized AR executor" follow-up as delivered.

Verified: 72/72 engine targets (native-backend); 32/32 downstream
server/CLI/CAPI/metadata, exit 0; H200 CUDA — canonical_execution_parity 8,
native_workflow_parity 12, one_runtime_e2e 5, gemma4_chained_workflow 8,
fixture floor 3; fmt --check; clippy -D warnings. All five real foundry models
remain byte-identical to the pre-change baseline, which matters here because
this commit changed the native decode paths.
