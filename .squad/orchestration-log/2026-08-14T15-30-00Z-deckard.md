## Deliverables / Findings

- **Phase-0 capture-stability probe (#948):** by the strict "PASS = all three" rule → **(b) PASS, (a) FAIL,
  (c) UNMEASURED → NO-GO** to an unconditional multi-week commit. Capture machinery is stable (994/1000
  replays, 3 invalidations, 90.3 tok/s captured M=1), but the raw M=K forward is `NotCapturable`
  (`[1,K,vocab]` logits materialized + ~722 transient workspace allocs — the missing Increment-0 work,
  not a kernel veto). Eager proxy M=1 13.5 / M=2 80.4 / M=8 91.5 ms = **6.77×**, a step function
  (M=1→M=2 cliff 66.9 ms) whose composition was the pivotal unknown → gated re-test on Increment-0.
- **Increment-0 capture-enablement overlay (#949) — DECISIVE:** built the three fixes (persistent
  `[1,K_max,vocab]` logits binding + alloc-free captured region via pre-capture warm forward + KV-symbol
  pin). M=8 now captures (`captured=true`, `capture_alloc=(0,0)`), but **captured M=8 replay = 87.2 ms =
  8.58× captured M=1 (10.2 ms)** — the ~80 ms floor PERSISTS under capture (captured M=8 ≈ eager M=8 90.9 ms).
- **Root cause (smoking gun):** `segments=41` at M=8 (vs 1 at M=1). The M=K forward does NOT whole-graph
  capture — `GroupQueryAttention[KernelCaptureUnsupported]×40`, `MatMulNBits[…]×240`,
  `SkipSimplifiedLayerNormalization[…]×80` advertise capture only at the M=1 decode shape, so the
  "captured" M=K forward degrades to ~361 eager relaunches.
- **Decision:** NO-GO for Lever B; **promote Lever A (Marlin int4 relayout, unconditional ~1.3–1.6×,
  ~4–6 eng-weeks)** to primary. Lever B is gated behind a deep kernel-capture-support program (make GQA /
  MatMulNBits / SkipSimplifiedLayerNormalization capture-safe at M>1), NOT the "reuse existing machinery"
  the design assumed. This SUPERSEDES the #938 "build Lever B first" recommendation.
