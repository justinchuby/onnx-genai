# Hybrid execution (GPU prefill / CPU decode): premise FALSIFIED, KV-handoff prototype PROVEN

**By:** Batty (Engine Dev)
**Date:** 2026-07-13
**Machine:** Apple M1 Max, macOS 25.x
**Repo:** `onnx-genai` (engine + ort only). Model: `models/qwen2.5-0.5b-cpu-recipe`
(fp32 GQA, 169 MatMulNBits, 24 GQA). Metal EP plugin:
`../onnxruntime-mps/build/libonnxruntime_mps_ep.dylib` (`ONNX_GENAI_METAL_EP_LIB`).
**No commit — coordinator commits.**

## TL;DR

The proposed hybrid — **prefill on the Metal EP (GPU), decode on the CPU EP** — has
**no benefit on the current Metal EP** because the core premise is false: **Metal does
NOT win prefill.** Metal prefill/TTFT is **~1.5–2× SLOWER than CPU at every prompt
length, and the gap grows with prompt length** (the *opposite* of the premise).
Root cause is structural: the Metal `MatMulNBits` kernel is a **decode GEMV replicated
once per prompt token** (`grid.y = M`), with no `simdgroup_matrix` GEMM tiling and no
weight reuse across the M prompt rows — so prefill re-streams the entire int4 weight set
**M times** and is M×-weight-bandwidth-bound, the GPU's weakness, not a compute-bound
GEMM.

The **KV-handoff mechanism itself works and is essentially free** (0.2–2.8 ms on Apple
unified memory), produces **coherent output**, and is now a reusable primitive. So the
prototype is a *mechanism* success and a *premise* failure. **Recommendation: do NOT
productionize the hybrid now.** The real lever is a **prefill GEMM kernel on the Metal
EP** (Mariette: `simdgroup_matrix`, reuse weights across M). If/when Metal wins prefill,
the hybrid path is ready and the handoff is proven.

## 1. Premise validation (does Metal win prefill?) — NO

Measured with the new `hybrid_prefill_decode` example (real ChatML prompt, padded by
token-repeat to reach long context; both sessions run back-to-back so the **within-run**
ratio is the reliable signal — absolute cross-run numbers drift with M1 thermals).

| prompt tokens | CPU prefill/TTFT | Metal prefill/TTFT | Metal ÷ CPU |
|---|---:|---:|:--:|
| 26   | ~43 ms   | ~66 ms   | **1.5× slower** |
| 256  | ~289 ms  | ~525 ms  | **1.8× slower** |
| 512  | ~604–699 ms | ~1128–1225 ms | **1.9× slower** |
| 1024 | ~1376 ms | ~2756 ms | **2.0× slower** |

Metal prefill loses in **every** run, and the deficit **widens** with M. Decode (for
reference, confirming prior notes): Metal ~30–68 tok/s vs CPU ~58–170 tok/s depending on
context depth — Metal loses decode too. The hybrid end-to-end is therefore **always worse
than pure-CPU** (e.g. 512-tok prompt + 48 decode: hybrid ~1536 ms vs pure-CPU ~1144 ms).

**Contention note:** a peer agent's `profile_decode` (457% CPU) overlapped the first
sweep. That only slows the **CPU** side, so solo CPU is *faster* → Metal's prefill deficit
is if anything **larger** solo. Re-measured solo (contender gone); the relative conclusion
is unchanged.

### Root cause (confirmed in the kernel)

`onnxruntime-mps/src/kernels/matmulnbits.metal` header, dispatch contract:
`grid.x = N*32 (simdgroup per output column); grid.y = M (one row per y)`. Each of the M
prompt rows is an independent GEMV that re-reads the full packed int4 weights; there is no
`simdgroup_matrix` tile and no cross-row activation/weight reuse. `mariette-matmulnbits-
bandwidth.md` already flagged "`simdgroup_matrix` tiling for large-M prefill" as
**unimplemented future work**. So prefill traffic ≈ M × (whole weight set) ≈ M × ~350 MB;
at ~46 GB/s effective that is seconds for M≈1024 — exactly what we measure. The premise's
"prefill = compute-bound GEMM where GPU parallelism pays" does not apply to a GEMV-per-row
kernel.

## 2. Hybrid design + KV-handoff (built and proven)

Two ORT sessions on the **same model**: a Metal-EP session for prefill and a CPU-EP
session for decode, both driven by `DecodeSession` in `ZeroCopyRebind` KV mode. Handoff:

1. Metal `DecodeSession::step(prompt, mask, positions)` runs the whole prompt in one
   forward pass → `present.*` KV (`[1, 2, P, 64]` per layer) + last-position logits →
   first token.
2. **`DecodeSession::export_kv()`** (new) materializes each `present`/`past_key_values.*`
   tensor onto host-owned Rust buffers (cheap `memcpy`; on Apple unified memory the Metal
   output is already CPU-addressable). The returned `Value`s are session-independent.
3. **`DecodeSession::import_kv(len, kv)`** (new) adopts them into the CPU decode session and
   sets the logical KV cursor to `P`. Dtype and per-tensor sequence-axis length are
   validated against the model.
4. CPU decode continues: step `t` feeds one token at absolute position `P+t`, mask
   `[1; P+t+1]` — identical to the engine's existing `DecodeBackend::decode` contract, so
   position/seqlen continuity across the EP boundary is automatic.

Both new methods are `ZeroCopyRebind`-only (shared-buffer mode owns fixed max-length
device buffers that are not portable across sessions). This is the natural, minimal seam;
no engine changes were required for the prototype.

## 3. Prototype coherence + measurements

- **Coherence (real 26-tok "capital of France" prompt, greedy):** pure-CPU, pure-Metal,
  and hybrid all produce fluent, correct English — `"The capital of France is Paris.\n..."`
  — token-identical for the first **14** tokens, then each diverges at token 14. That is
  the **known pre-existing fp32 reduction-order drift** (Metal fp32-dequant vs CPU int8
  `accuracy_level=4` MatMulNBits — `sebastian-accuracy-level-debug.md`,
  `mariette-gqa-kernel.md`), **not** a handoff defect. The hybrid tracks the Metal-prefill
  numerics through the boundary, then decodes on CPU; output stays coherent.
- **KV handoff cost:** 0.19 ms (P=26) → 1.4 ms (P=512) → 2.8 ms (P=1024). Negligible; the
  unified-memory copy is not a bottleneck.
- **Decode recovery:** hybrid decode runs at **CPU speed** (e.g. 188 tok/s vs pure-Metal
  123 tok/s at P=26; 123 vs 68 at P=512) — the one thing the hybrid does well is avoid
  Metal's slower decode. But it cannot offset the slower Metal prefill.
- **Regression test:** `exported_kv_handoff_continues_decode_identically` (CPU↔CPU handoff
  via the same API) is **bit-identical** to a single-session run — proving the export/import
  path is numerically exact.

## 4. Is it a real win? Worth productionizing? — NO (not yet)

No. Given the current Metal EP, the hybrid is **strictly worse** than pure-CPU on total
latency at every prompt length, because it is forced to eat a prefill that is ~2× slower
than CPU. The premise required Metal to win prefill; it loses prefill and the deficit grows
with context — so the hybrid's intended win (better long-context TTFT) is exactly inverted.

**What would make it worthwhile (the real lever):** a **prefill-specialized Metal
`MatMulNBits` GEMM kernel** — `simdgroup_matrix` tiling that loads each weight block once
and reuses it across a tile of M prompt rows (llama.cpp `mul_mm`-style), turning prefill
from M× weight-bandwidth-bound back into the compute-bound GEMM the premise assumed. This
is Mariette/Coco kernel work in `onnxruntime-mps`, not onnx-genai. **When Metal prefill
beats CPU, revisit the hybrid — the KV-handoff seam (`export_kv`/`import_kv`) is already in
place, coherent, and effectively free.** Until then, keep prefill and decode both on CPU.

# Decision: Control-flow ops (If / Scan / Loop) in the MLX plugin EP

**Author:** rem (Metal/MLX EP)
**Branch/worktree:** `rem/controlflow` @ `/Users/justinc/Documents/GitHub/onnxruntime-mlx-cf`
**Date:** 2026-07-14
**Status:** Implemented (static/foldable forms) + feasibility documented. No commit.

## Feasibility verdict — plugin EPs CAN access subgraph bodies

**YES.** The ORT 1.27 plugin-EP C ABI exposes a control-flow node's body subgraphs to a compiling
plugin EP. Concretely:

- `OrtEpApi`/`OrtApi`: `Node_GetNumSubgraphs` + `Node_GetSubgraphs` (since 1.23) return each body as
  an `OrtGraph` together with its attribute name (`then_branch` / `else_branch` / `body`).
- C++ wrappers used here: `Ort::ConstNode::GetSubgraphs()` →
  `std::vector<Ort::AttrNameSubgraph{attr_name, ConstGraph sub_graph}>`, plus
  `ConstGraph::GetNodes/GetInputs/GetOutputs/GetInitializers`, `ConstNode::GetImplicitInputs()`,
  and `Graph_GetParentNode` to detect that a graph is a CF body.

**Empirical proof (Model A).** ORT partitions control flow **bottom-up**: `GetCapability` is called
on the body subgraphs FIRST (with a non-null parent node), then on the parent graph. By default ORT
offloads translatable body ops independently and runs the If/Scan/Loop node itself on ORT CPU
("Model B"). To own the whole construct ("Model A") the EP must, in `GetCapability`, **decline all
body nodes** when the enclosing CF node is itself claimable, and **claim the CF node** in the parent
graph. At `Compile` time the EP then receives the CF node with `Node_GetSubgraphs` returning the
bodies with their original ops intact (verified: `then_branch[Add] else_branch[Sub]`,
`Scan body[Add Identity]`, `Loop body[Add Identity]`). So If/Scan/Loop are **feasible** in the
plugin-EP compiling model. (There is also a separate 1.24 kernel-EP path — `CreateIf/Loop/ScanKernel`
— which this compiling EP does not use.)

## What was implemented

`src/ep/ops/controlflow.cc` → `RegisterControlFlowOps` registers `If`, `Scan`, `Loop` with
conservative claim predicates; a claimed node is translated by unrolling its body inline via the new
`TranslationContext::RunSubgraph`. Claim predicates recursively require every body op to be
MLX-translatable, so a claimed CF node can never contain an untranslatable op.

- **If (runtime/foldable cond):** both branches must be translatable at claim time. Each forward the
  eager path reads `cond` host-side (`RawHost`) and translates ONLY the taken branch — no `mlx_where`
  needed because the graph is rebuilt per forward. Compiled-decode fast-path is disabled for CF plans
  (`has_control_flow`) since branch structure is data-dependent.
- **Scan (static trip):** trip count = scan-input axis-0 length (must be statically known, ≥1).
  Forward direction, axis 0 only (non-zero `scan_*_directions`/`scan_*_axes` → unclaimed). Unrolls the
  body, threads carried state, stacks scan outputs along axis 0.
- **Loop (constant M + pass-through cond):** requires explicit int64 `M` and bool `cond` inputs
  (host-read) and a body whose cond output is a pass-through of the cond input (direct alias or an
  `Identity` copy) — the provable `for i in range(M)` idiom. Unrolls exactly `M` iterations
  (`cond0 ? M : 0`). MVP: carried-state-only (no per-iteration scan outputs).

### Plumbing (kept minimal, existing flat-graph path untouched)
- `ep.cc` `GetCapability`: decline body nodes when inside a translatable CF body; force CF nodes into
  singleton clusters so cond/M and implicit inputs resolve host-readably from the fused boundary.
- `ep.cc` recursive `BuildSubgraphs`: captures each body as a `NodeDesc::SubgraphDesc`
  (topo-ordered body `NodeDesc`s, implicit-input resolution, nested-CF recursion).
- `mlx_backend.h`: `SubgraphDesc` + `NodeDesc::subgraphs`; `TensorRef` gained an owning
  `init_owned` buffer.
- `mlx_engine.h` / `mlx_backend.cc`: `RunSubgraph` (scoped env save/restore); `BuildPlan`
  recursively validates body ops and disables the compiled fast-path for CF plans.

### Bug found + fixed during bring-up
Body initializers are reached through the subgraph handle that ORT **releases once the body walk
returns**, so a borrowed `GetTensorRawData()` pointer dangled (manifested as an `If` else-branch
subtracting ≈1.000002 instead of 1.0 — nondeterministic). Fix: **copy** body-initializer bytes into a
`shared_ptr<vector<uint8_t>>` owned by the `TensorRef` (fused-graph initializers still borrow
session-owned memory). Correctness now deterministic.

## What was deferred to ORT CPU (unclaimed — runs correctly on fallback)
- **Loop** with dynamic / data-dependent (non-pass-through) cond → trip count not statically known.
- **Loop** scan outputs (per-iteration accumulation) — carried-state-only in this MVP.
- **Scan** with non-forward directions or non-zero axes; scalar (rank-0) scan inputs.
- Any body containing an op the flat path can't translate (recursive claim guard).

Declined CF nodes still let their translatable body ops offload to MLX via the ordinary flat path;
only the CF node runs on CPU. Verified with a data-dependent `Loop` case (`Loop` on CPU, body `Add`
fused to MLX, output correct).
