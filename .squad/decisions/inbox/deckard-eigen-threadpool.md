### 2026-07-29: Eigen-style decode pool prototype and gate
**By:** Deckard
**What:** ORT's CPU threadpool is not a per-op thread spawn: `onnxruntime::concurrency::ThreadPool` owns persistent workers backed by ORT's modified Eigen `NonBlockingThreadPool`. Workers spin, periodically steal, then block only after the spin window; each worker owns a `RunQueue`, idle workers steal from active workers' queues, and `TryParallelFor` maps to `ParallelForFixedBlockSizeScheduling` where a small set of tasks dynamically claim batches from sharded `LoopCounter`s. That avoids the fixed-SPMD hard static-shard barrier and avoids Rayon's per-scope/deque/epoch/join overhead for every decode projection.
**Why:** `crates/mlas-sys/vendor` does not contain Eigen `unsupported/Eigen/CXX11/ThreadPool` headers; standalone MLAS only forward-declares `MLAS_THREADPOOL` and our current shim routes MLAS threading to Rayon. I therefore prototyped the smallest usable Rust-side equivalent in `mlas-sys`: `WorkStealingThreadPool::new(n)` plus `parallel_for(begin, end, grain, closure)`, with persistent spin-then-park workers, per-worker atomic queues, caller participation, and stealing. Windows ARM64 gate (`ONNX_GENAI_FAST_BENCH=500 cargo bench -p mlas-sys --bench pool_microbench`): dispatch p50/p90 was 2.3/2.6 µs vs fixed-SPMD 29.2/65.9 µs and Rayon 49.8/87.7 µs. Simulated-contention tail was better than fixed-SPMD/Rayon, but fixed still had lower mean/p50 in this synthetic: p90 518.8 µs vs fixed 543.7 µs / Rayon 557.2 µs; p99 555.4 µs vs fixed 564.0 µs / Rayon 609.2 µs. This clears the dispatch-latency gate, but decode integration should still validate real-token median before replacing fixed-SPMD.
