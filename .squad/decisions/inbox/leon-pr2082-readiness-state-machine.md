### 2026-08-26: Provider artifacts gate execution by readiness epoch
**By:** Leon
**What:** PR #2082 now uses one explicit per-executor state machine for static build and symbolic/dynamic specialization: bind and resolve inputs, precompile every currently resolved leaf kernel under the executor scope, advance a monotonic compilation-readiness epoch, require provider finalization to return an honest terminal outcome, and only then execute or enter capture/replay. `Pending` and finalization errors are typed, block all execution, and are cached for that epoch; retry requires a concrete new kernel specialization. A later specialization re-confirms the provider outcome idempotently without reinstalling executor-owned artifacts. Cancellation/drop drains only that executor, including unpublished static builds and pending sessions.
**Why:** The earlier `execute`-then-retry lifecycle could run or capture a plan while required QMoE producers/install state were still pending. The old Slice 7E decision text describing a one-shot build hook or post-execution retry is superseded by this readiness-epoch contract. Shared EP, base/MTP siblings, failures, and teardown remain isolated by `ExecutorInstanceId`.

The development API change is intentionally clean: `finalize_executor_artifacts` now receives a typed readiness epoch and returns `Result<ExecutorArtifactFinalization>`, while `Pending` carries a typed reason. All in-repo callers/tests use the new signature; no overload, default-field substitute, or compatibility shim was added for the already-breaking CUDA registry/QMoE factory APIs.
