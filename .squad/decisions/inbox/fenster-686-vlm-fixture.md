# Decision: Working VLM compat fixture graphs + re-enable server CI (#686)

**Author:** Fenster (Rust)
**Date:** 2026-08-11
**Issue:** #686 — `onnx-genai-server`'s sidecar-free VLM compatibility fixture
(`vlm-executable`) had no executable ONNX graphs, so its test was red and the
server crate was deny-listed from CI.

## Root cause

The split-VLM compatibility synthesizer had two paths that differed for the
decoder's sequence source:

- The **text-only fallback** (`to_strict_text_only_pipeline_metadata`)
  correctly declared `sequence_source: "inputs_embeds"`, because the decoder is
  driven by the embedding graph's `inputs_embeds` (rank-3), not by token ids.
- The **full VLM path** (`to_strict_pipeline_metadata`) did **not** declare it.

With `sequence_source` unset, decode I/O resolution
(`crates/onnx-genai-engine/src/decode/resolved_io.rs`) defaults to `TokenIds`
and tries to structurally resolve a rank-1/2 token input. The `inputs_embeds`
decoder exposes no such port, so loading failed with:
`cannot resolve decoder token input from tensor shape; declare model.io.token_input`.

## Fix (resolution route: b — explicit metadata, in production synth)

Real split VLMs (Mobius Gemma4, onnxruntime-genai) drive the decoder with
`inputs_embeds`, and the fixture's `genai_config.json` faithfully declares
`model.decoder.inputs.inputs_embeds` with no `input_ids`. Rather than distort
the fixture graphs to expose a fake token input (route a — unfaithful), the
correct fix is to make the full VLM synthesizer declare the sequence source it
already relies on, mirroring the text-only fallback:

```rust
// crates/onnx-genai-genai-config/src/compatibility.rs  (to_strict_pipeline_metadata)
decoder_io.insert("sequence_source".into(), json!("inputs_embeds"));
```

This is a genuine synthesis bug the fixture exposed; the fixture graphs and
`genai_config.json` were already correct.

## Fixture graph interfaces (`crates/onnx-genai-genai-config/tests/fixtures/vlm-executable/`)

Generated by `scripts/build_vlm_executable_fixture.py` (tiny identity graphs,
reproducible — bit-identical on regen):

- `vision.onnx`: `pixel_values[num_patches,768] f32`, `image_grid_thw[img,3] i64`
  → `image_features[num_patches,768] f32` (flat `[num_image_tokens, hidden]`).
- `embedding.onnx`: `input_ids[batch,seq] i64`, `image_features[num_image_tokens,768] f32`
  → `inputs_embeds[batch,seq,1] f32` (raises token ids into the embed stream).
- `text.onnx`: `inputs_embeds[batch,seq,1] f32`, `attention_mask[batch,total] i64`,
  `position_ids[3,batch,seq] i64`, `past_key_values.0.{key,value}[batch,2,past,64] f32`
  → `logits[batch,seq,1] f32`, `present.0.{key,value}`.

## CI

Removed the `onnx-genai-server` deny-list entry in
`.github/scripts/workspace_test_packages.py` and added `onnx-genai-server` to
`ORT_BACKED` (it loads ONNX Runtime at runtime, so it belongs in the ORT lane,
not the offline lanes). Coverage guard passes: 40 tested, 5 denied.

## Test evidence

- Target test **PASSES**:
  `sidecar_free_compatibility_package_builds_server_pipeline_and_preprocesses_image`.
- `cargo test -p onnx-genai-genai-config`: all pass (33).
- `cargo test -p onnx-genai-server`: 178/180 pass. Two failures are **not**
  tied to #686:
  - `registry::tests::production_load_path_shares_device_authority_and_metrics_ledger`
    — passes in isolation; load-driven flake under parallel test load.
  - `registry::tests::failed_runtime_shrink_preserves_policy_and_ledger_limit`
    — **pre-existing, GPU-dependent**: expects a "committed bytes" VRAM-ledger
    error that only arises with a CUDA device. Fails identically with my changes
    stashed (verified), so it is environmental, not a #686 regression.
