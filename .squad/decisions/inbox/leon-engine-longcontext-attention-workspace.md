### 2026-08-18: Engine decode re-prepares Attention workspace on KV capacity growth
**By:** Leon
**What:** Fixed the Engine/native CUDA single-token decode path to re-run governed workspace preparation when `ensure_capacity` grows the KV/mask bucket. The re-prepare uses the already-updated persistent decode bindings, so default-domain `Attention` reserves against the new deterministic physical context capacity before eager execution or CUDA-graph warm/capture/replay resumes.
**Why:** `Engine::generate` prepared workspace at admission/prefill time with the initial V2-Lite bucket (prepared `16904` B). Around 320 generated tokens, KV capacity grew to the next bucket and `Attention`'s score/control workspace requirement became `33288` B, but `workspace_preparation_required` correctly prevented opportunistic execute-time growth, producing the invariant mismatch in both eager and capture. `NativeDecodeSession` decode-lock coverage did not hit this because it did not hold the stale Engine admission preparation across the same bucket-growth path. After the fix, real V2-Lite Engine/profile_native runs 340 tokens in both eager and capture with identical token IDs (prefix includes the locked `...207,16,24,1012` stream); capture records `captures=2 replays=336 fallbacks=0` and no under-plan. Session lib tests remain green, and the Qwen3 dense CUDA lock still passes.
