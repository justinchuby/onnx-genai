### 2026-08-12: bf16 norm-into-GEMV-prologue fusion — measured NO-GO (kill-gate CLOSED)
**By:** Sebastian (Performance/Systems)
**What:** Prototyped the bf16 analogue of `CudaSkipRmsNormMatMulFusion` — a throwaway bf16-only optimizer pass that folds `x → SimplifiedLayerNormalization(x,γ) → MatMulNBits` (Gemma3 pre-norm seams) into the following int4 GEMV's in-kernel RMS prologue, so the RMS reduction rides the GEMV's full-device (132-SM) occupancy instead of a standalone launch. Intended as the distributed-reduction fix for why #903's standalone skip-RMSNorm fold regressed −1.5%. Kernel needed NO change (bf16 GEMV stages through fp16 in `run_bf16`, reusing the existing fp16 prologue kernel). 104 foldable pre-norms/model (2/layer × 52). **The prototype was measured then discarded — this PR is finding-only (docs + this drop); NO production `src/` change, no flag, no dead code lands.**
**Numerics (artifact for Chew):** NOT byte-exact. Greedy 128-token stream on Muse-Glimmer-30B diverges at ≈token 38 (`…2963,38,9520…` → `…2963,38,8323,2481,9520…`). Cause: the fp16 `warp_half4` prologue reduction tree differs from `rmsnorm_bf16`'s block-tree by ~1 fp32 ULP, and the fused path skips the intermediate bf16 rounding of the normalized activation.
**Measured (H200, `CUDA_VISIBLE_DEVICES=0`, `ONNX_GENAI_CUDA_GRAPH=1`, `--pipeline`, interleaved A/B):** baseline 47.9 tok/s → fused ON 45.7 tok/s = **−4.6% REGRESSION**. Op-timer mechanism: folding saved only ~1.8 ms of standalone norm (106.55→104.78 ms) but added **+180 ms** to the GEMVs (368.91→548.81 ms, +48%). Default-OFF re-verified == baseline (48.15 tok/s, byte-identical stream) → no production regression.
**Why:** Inverse of the fp16 skip case. bf16 standalone norm (`rmsnorm_bf16`, block-tree parallel) is already cheap; the available fp16 prologue reduction (`skip_rmsnorm_f16_warp_half4`) is **single-warp-serial** over H=6656, re-run once per fan-out follower GEMV (≤4), and it lands on the critical GEMV path. The `fusion_benefit_is_positive` gate was calibrated for the fp16 assumption (standalone skip = ~24% of decode), which is FALSE for bf16. The kernel-level distributed-reduction idea is sound but needs a NEW genuine multi-CTA cooperative-reduction prologue kernel — out of scope for this bounded gate.
**Verdict:** **NO-SHIP / NO-GO.** Prototype **not landed** (finding-only) — no opt-in flag, no dead code, no `src/` change; default binary unchanged. Kill-gate CLOSED: decode remains at its launch-amortized latency floor (~47.6–48 tok/s) — the **fourth** independent confirmation (megakernel, glue-under-replay, standalone skip-fold, and now this); do not pursue norm→GEMV-prologue on H200 without a true multi-CTA cooperative-reduction prologue first.
**Validation:** Docs-only PR — `git diff origin/main` touches only `docs/research/dense-decode-megakernel-feasibility.md` (§8.7) and this drop; `cargo fmt --all -- --check` clean; no `crates/`/`src/` change (no build/clippy needed). fp16 `CudaSkipRmsNormMatMulFusion` byte-exact path untouched.
