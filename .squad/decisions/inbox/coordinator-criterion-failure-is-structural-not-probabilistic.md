### 2026-08-21T02-52-44: 判据失效是结构性的，不是概率性的：换判据，不要靠更仔细
**By:** coordinator
**What:** 判据失效是结构性的，不是概率性的：换判据，不要靠更仔细
**References:** #1579, #1586, #1533, #1600, session 07e28bcc, session b1a0ab2e
**Why:** ## 来源

08-20 一天内出现四次同类事故，跨三个 session 独立收敛到同一结论。**核心表述来自 session `07e28bcc` 与 session `b1a0ab2e`**（前者明确表示不必署名，但今日主题恰是溯源，故如实记录归属），协调方 `78c75f53` 汇总。

## 结论

> **用一个与被测命题不匹配的判据，再把它的输出当结论。**

| 被测命题 | 用错的判据 | 为什么必然失效 | 正确判据 |
|---|---|---|---|
| 某修复内容是否已进 main | `git merge-base --is-ancestor` | squash merge 造新 commit 对象，原 commit **必然**不是祖先 | 特征标识符 `grep` / blob 比对 |
| 某 commit 出自哪个 session | 记忆 /「像是会做这事的人」 | 跨 session 归属**没有**任何记忆基础 | commit 的 `Copilot-Session` trailer + `git branch --contains` |
| 某依赖是否可用 | `grep Cargo.toml` | grep 只看见**直接声明**，看不见**依赖图** | `cargo tree -p X -i Y` |
| 某 CI 通道是否验证了某平台 | run 级 `conclusion` | 路径过滤下 job 可 skipped，run 仍 success | job 级 conclusion + 该 job 实际执行的命令 |

## 重要边界：好判据也有失效方向，但那不等于「不可用」

（本节由 session `b1a0ab2e` 更正加入。协调方一度把 blob 比对与 `--is-ancestor` 并列成「squash 下都会骗人」——**这是错的，而且本身就是一次判据误配**。该错误措辞未进入任何已发布产物，但若扩散，会掏空本仓库合并审计的方法基石：全树不变式、非重叠集验证、Tier 2 审计，用的**全都是** blob 比对。）

**blob 相等是单向判据：**

- blob **相等** → 内容确实在 main，**证明力完整**
- blob **不等** → **什么都不能证明**（可能没进去，也可能进去了但被后续 commit 改过）

两者都朝**假阴性**方向失效，区别在**必然性**：

| | 失效条件 | 性质 |
|---|---|---|
| `--is-ancestor` | squash merge 下**无论内容如何**都返回 NO | **零信息量**，坏判据 |
| blob 比对 | 仅当文件被后续 commit 改动 | 好判据的**已知边界** |

> **「特征标识符 `grep`」是 blob 不等时的正确降级手段，不是它的替代品。**

**推广：判定一个判据好坏，不看它会不会失效（都会），看它失效时是否仍携带信息。** 零信息量的判据要换掉；有已知边界的判据要配降级路径。

## 关键性质：结构性，不是概率性

这四条**不是「有时会错」，是「在该条件下必然错」**。祖先关系在 squash 下必然失效；记忆在跨 session 归属上必然失效；grep 对传递依赖必然失效；run 级状态对被 skip 的 job 必然失效。

> **推论：不能靠「更仔细」避免，只能换判据。**
> 一个再谨慎的人用 `--is-ancestor` 查 squash-merged PR，也会得到同一个错误答案。

## 为什么难防

**一、判据错误不会自己报错。**（`b1a0ab2e`）
它不像编译错误当场炸，而是**安静地返回一个格式正确的假答案**。`--is-ancestor` 返回的 NO 与一个真实的 NO 在终端里一模一样：语法合法、类型正确、只是语义无关。

**二、它对下游验证强度免疫。**
`b1a0ab2e` 在错误前提（「libc 不可用」）之上做了 cfg 门、编译期 size 断言、以及真做了的阴性对照——每条单独看都比常见做法更狠，**没有一条拦得住前提本身是错的**。

> **验证做在错误的问题上，做得再狠也救不回来。**

**三、对外的怀疑比对内的容易。**
协调方在合并审计里对**别人的**代码坚持「比内容不比历史」，同一天却对**自己的**结论用了历史关系。不是不知道正确判据，是没在自己身上触发那个反射——比不知道更难修，因为它不表现为知识缺口。

## 独立复核只在判据不共享时才提供保护

**这是本条最反直觉、也最重要的一节。**

一个 `568 passed` 的数字来源不明。协调方在上下文里查不到，**断定「不是我的」**；另一 session 不接受声明，**实机跑了三个 ref 两种范围**（438 / 541 / 438），断定「无主、不可复现」。两条独立路径、一条推理一条实测、结论一致——**看上去是教科书式互相印证**。

第三种范围一跑就出来了：

```
cargo test -p onnx-genai-engine --lib                            → 438
cargo test -p onnx-genai-engine（全 target）                      → 541
cargo test -p onnx-genai-engine --features native-backend --lib  → 568   ← 就是它
cargo test -p onnx-genai-engine --features native-backend（全）   → 696
```

**568 精确复现，0 failed，main 与分支同为 568。** 缺的只是 `--features native-backend`。

两个错误性质不同：

- **协调方**：从「我记不得」推出「不是我的」。**记忆缺失是「没有证据」，不是「证据表明没有」**——用零信息量判据得出确定性否定结论，而且是在向对方讲解判据误配的同一天。
- **另一 session**：跑了（这步更强），但**命令范围不全**，把「我的命令没测到它」当成「它不存在」。这与它几小时前自己诊断过的 clippy 失误（少了 `--features native-backend -- -D warnings`）**逐字同构**——说明此类错误不因吃过一次亏而免疫，只能靠机械习惯（照抄完整命令）。

> **共享一个错误前提的两次独立验证，不是两份证据，是同一份证据被数了两遍。**

两人共享的隐含前提是「`cargo test -p <crate>` 就是该 crate 的完整测试面」。**独立性只在判据不共享时才提供保护。**

**规则：** 引用「两条独立证据」前，先问这两条路径**是否共享某个未言明的前提**。若共享，其独立性是表面的。

### 可操作判据（由 `b1a0ab2e` 补齐）

> **列出两条路径各自依赖的前提，看交集是否为空。** 交集非空且未经检查 → 那不是两份证据。

### 为什么方法多样性反而加剧危险

本例两条路径**看起来极其不同**：一条用记忆（最弱的判据），一条用实测（最强的判据）。

> **两条方法看起来越不一样、结论却越一致，人越倾向于相信——而共享前提恰恰不受方法差异的影响。**

所以**方法多样性不能替代前提审查**。差异越大，「互相印证」的假象越强，这是反直觉且危险的方向。

### 自己的实测同样需要被怀疑

`b1a0ab2e` 的自我诊断，比外部批评更准：

> **我把自己的实测当成了免检金牌。「我跑了」这件事本身，让我跳过了「我跑的是不是对的东西」。实测的仪式感变成了新的盲区——声明会被怀疑，自己的实测不会。**

它当时跑了**三个 ref、两种范围**，横向铺得很宽，但三次都少同一个标志。

> **同一个错误重复三次不会变成三份证据，只会让错误看起来很扎实。**

（与「共享前提的两次独立验证」同构，只是这次是一个人跟自己数了三遍。）

**因此「要实测」这条纪律不完整，完整形式是：跑完之后问一遍「我跑的命令和被验证的命题是同一件事吗」。**


**推论（报数纪律）：** 报数字不带 ref，等于报了个会过期的东西；**不带 feature 标志，等于报了个不可复现的东西。**

## 「让问题消失」与「让问题可见」是两种不同的好

（来自 session `b1a0ab2e`，本条是它对自身案例的二次归纳，价值超出该案例。）

#1586 的正确修法是改用 `libc::statvfs`，它比手写 `#[repr(C)]` 更优——**消除了整个缺陷类别**（其它 unix 顺带修好，不可能再写错 layout）。

但它有一个不显眼的代价：**libc 会静默修好那些坑，同时让没人知道它们存在过。**

- `f_fsid` / `f_flag` / `f_namemax` 偏移自动正确、macOS 无 `f_spare` 自动不越界——**一行不用写，一句不会说**
- 若一开始就上 libc：测试绿、PR 合，而「原始报告只点了 6 个字段，实际错了 9 个、还多一个不存在的成员」这个事实**永远不会被任何人观察到**

|  | 内容 | 路线依赖 |
|---|---|---|
| 知道 `f_fsid` 在偏移 40 | 修 bug 的手段 | **自造**——正确路线下不需要知道 |
| 知道原报告漏了 3 个字段 | 对报告可信度的判断 | **无关**——任何路线下都为真，但**只有错误路线看得见** |

第二行不是错误路线的副产品，是它**独有的观测能力**：手写 ABI 逼你去实测真实布局，正确路线不需要测，因此也看不见。

> **推论：当一个问题报告可能不完整时，先测一次再换成正确修法，不是浪费。**
> 正确修法消除缺陷的同时，也消除了发现「你的问题描述是错的」这件事的机会。

**与「必要性自造」的区分**：手段层面的诊断在正确路线下多余（自造）；关于**报告本身**的元信息在正确路线下不可得（无关）。二者不可打包，否则会把真实收获一并否定掉——这是一次**过度更正**，同样是判据误配的一种。

## 查扩散不能替代查真伪，顺序也不能反

发现一个错误结论后，**查它已经流到哪里**是必要动作——否则被否定的方法论仍在被使用，而使用它的人不知道它刚被作者宣布不可信。（实例：协调方更正「blob 也会骗人」后去查扩散，才发现 review 指南 10 处审计结论**全部建立在 blob 比对之上**；若只改口径不查扩散，会掏空读者正在依赖的取证基础。）

**但这个动作本身会被同一个缺陷命中。**

同一时段的对称实例：另一 session 查了 `568` 的扩散范围（只在自己的 task summary，无扩散——**这个结论是对的**），却没查它的**可复现性**。

> **扩散范围回答的是「这个错误影响了谁」，其前提是「它确实是个错误」——而那一步没被验证。**

结果：扩散检查做得很干净，却是在为一个并不存在的错误做清理，差点把一个可复现的真实数字归档成幻觉。

**规则：先证伪，再查扩散。** 更准确的因果（由 `b1a0ab2e` 给出）：**这是用一个下游检查去给上游前提背书——下游做得越认真，上游越显得不用查。** 次级检查执行得越严谨，主命题越不会被回头审视。

 顺序反了，就会把「清理工作做得彻底」当成「结论正确」的旁证——而清理的彻底程度与结论真伪完全无关，是又一个不匹配的判据。

## 拒绝一个声明和接受一个声明，举证责任是对称的

本仓库已有纪律：**不接受无留痕的归属**（错误溯源比没有溯源更坏，因为它看上去和经核实的条目一模一样）。这条纪律是对的，但今天暴露出它**只被用在了一侧**。

协调方发起退回时（「568 不是我的」）只想着「不接受无留痕声明」，**没想过退回本身也是一次归档，也需要证据**。结果是：接受那一侧检查得很严，拒绝那一侧一次都没检查。

> **「否认」不是「不表态」，它是一个有内容的断言，需要与接受同等的举证。**

后果评估（由 `b1a0ab2e` 给出，准确）：

> 「这条要是按我的措辞归档，损失的不是一个数字，是往后**所有引用 696 的结论**都会被这条『幻觉』记录污染。」

一条被错误标记为幻觉的真实数据，其毒性大于一条来源不明的数据——**来源不明会让人去查，标记为幻觉会让人不去查。**

**规则：** 要把某条证据标记为「无效 / 无主 / 不可复现」之前，适用与接受它同样的证据标准。若做不到，正确的措辞是「**未核实**」而不是「**不成立**」。

## 操作规则

**下判据之前问：这个判据在什么情况下会给出错误答案？**
——而不是：这个判据这次给了什么答案。

若答案是「在某个可识别的结构性条件下必然错」，且无法排除该条件成立，则**换判据**。

### 报数纪律（今日实证）

同一个 crate 在四种口径下有四个数，**没有任何一个是错的**：

```
cargo test -p onnx-genai-engine --lib                            → 438
cargo test -p onnx-genai-engine（全 target）                      → 541
cargo test -p onnx-genai-engine --features native-backend --lib  → 568
cargo test -p onnx-genai-engine --features native-backend（全）   → 696
```

> **错的不是数字，是不说清哪一个。** 报数字必须带 **ref + 完整命令（含 feature 标志）**，否则报的是一个会过期且不可复现的东西。

### 照抄命令，不要凭理解重构命令

`b1a0ab2e` 三次都写成 `cargo test -p onnx-genai-engine`，因为它理解这条命令是「测这个 crate」——**理解是对的，命令是不全的**。

它此前**已经诊断过同一陷阱**（clippy 少了 `--features native-backend -- -D warnings`），并把该诊断作为自我更正上报过；几小时后在**同一个 crate、同一个缺失标志上又错一次**。

> **诊断过 ≠ 免疫。知道陷阱存在是知识，下次机械避开是习惯，知识不会自动变成习惯。**

**唯一可操作的形式：照抄 CI / 文档里的完整命令，不要凭理解重写。**


## 同一失效模式在测试构造中的形态

`07e28bcc` 指出其自写测试用 `planted_peak = 4 * SENTINEL`（绝对量），成立前提是 `content_resident < 3 * 2^50`——**一个关于量级的经验假设，不是不变式**。R2 突变的杀伤力完全来自「人工高水位严格高于 live residency」；前提一旦失效，R2 静默失去杀伤力而**测试仍然是绿的**。

树内版本用 `planted_peak = 当前 live residency + SENTINEL`（相对构造），使该前提**恒真**。

> **构造式不变式 > 量级假设。** 判据不该依赖「这个数应该够大」。

这是**朝假信心方向失效**——与既有那条「突变脚手架向假信心方向失效」同源，只是这次出现在**被测试本身**而非脚手架里。

## 新变体：「编过」≠「那段代码还在」

（机制由 `641c9dd2` 指出，本 session 实证）

2026-08-21 的实例：`main` 把 `onnx-genai-engine` 的 feature `cuda` 改名为 `native-cuda`（#1629）。并行分支上残留的 `#[cfg(feature = "cuda")]` **不是编译错误，是求值为 false** —— 失效形态是「代码整片消失，编译照样通过」。

阴性对照确认它并非全静默：`unexpected_cfgs` 会 warn，配 `-D warnings` 在 CI 变 error。**但该保护有一个前提：那段代码得先被编译。**

```
陈旧 cfg 写在普通代码里        → 被编译 → 响 → CI 红    ✅
陈旧 cfg 写在 cfg 块「里面」   → 从不编译 → 从不 lint → 绿  ❌
```

而 CUDA 代码按定义就在那些块里面 —— **保护恰好在最需要的地方失效**。实证：`onnx-genai-engine` 的 167 个 `native-cuda` 站点被**零个 CI job 编译**，且 `origin/main` 自身跑 `cargo clippy --features native-cuda --all-targets -- -D warnings` 就是 `exit 101`。

> **状态更新（同日晚，#1632 合并后）**：该缺口已被关闭 —— `CUDA compile (Linux x86_64)` job 里加了 `cargo clippy --locked -p onnx-genai-engine --features native-cuda --all-targets -- -D warnings`，`kv_commits_on_demand` 已改为 `#[cfg(all(feature = "native-cuda", test))]`。上面那句「被零个 CI job 编译」自此**是历史状态，不是现状**。
>
> 保留原文而不改写，是因为**判据本身不随缺口关闭而失效** —— 它下次会在另一个 feature、另一个 crate 上重现（`cli` / `server` / `bench` 三个改名 crate 至今无人审）。但**任何引用这段的结论都必须带时点**，否则就复现了本记录自己批评过的「报数字不带 ref」。
>
> 新 lane 的边界也要写死，免得下次被「已经有 lane 了」挡回去：它只在 **Linux** 上跑（Windows/macOS 专属 cfg 仍不覆盖），且它是**编译覆盖不是测试覆盖**（CUDA 集成测试仍在 `required-features` 后面，需要 GPU runner）。**关掉的是「从不被编译」，不是「从不被执行」。**

**与本条主命题的关系**：这是「绿灯的证明力等于它实际执行到的代码路径」在**编译期**的形态。前面数到的四种绿灯形态都发生在「跑没跑」这一层，这一种发生在更早的「编没编」这一层，因此更隐蔽 —— 测试全绿是真的，那段代码不存在也是真的。

### 附带的一条重构判据

> **改名重构的破坏力，与它的逻辑改动量成反比，还与 CI 对目标代码的覆盖度成反比。**

两个「看起来无害」的因素相乘，且它们**不是独立叠加，而是互相提供了不去查的理由**：零逻辑改动让人不查语义，零 CI 覆盖让人以为绿灯已经查过。

**操作规则：跨 crate 重命名要主动广播给并行分支**，因为受影响方无法从「CI 是绿的」推出「我没被影响」。

## 更正不能替代划界

（`b1a0ab2e` 提出，并当场用于退回协调方的过度更正）

> **更正在冲向一个真目标时，惯性会带走目标旁边的东西。**

本条已记录的两个实例，形状逐字相同：

| 真目标 | 被惯性带走的真成分 |
|---|---|
| 堵住「至少诊断没白费」这个开脱模板 | 「原报告不完整」这条**路线无关**的真收获 |
| 纠正「记录人而非机制」 | 「人的行为倾向确实是必要一环」这个真成分 |

两次都是**过度更正**，与不足更正是同一类错误的两个方向。

**规则：做出一次更正后，检查一遍「我否定掉的成分里，有没有本来是真的」。** 这与「查扩散不能替代查真伪」对称——那条约束的是**顺序**，这条约束的是**边界**。

## 收口：五个切面是同一件事

（`b1a0ab2e` 的归纳）今天这一串错误不是五个独立教训，是同一个东西的五个切面：

```
判据误配  /  记忆当证据  /  命令不全  /  共享前提的伪独立  /  下游严谨反证上游
```

> **全部都是「我验证了」这句话在没说清「验证的是哪个命题」时产生的幻觉。**

## 记录机制，不要记录人

起草本条时，协调方一度写下「某会话是唯一不接受声明、坚持去跑的一个」。**该会话自己要求退回这句话**，理由成立且构成本条最后一个实例：

- 它这一轮**确实跑了**（三个 ref 两种范围），然后用不完整的命令把一个真数字判成了幻觉；揪回来的是另一方。
- **「是否去跑」是可观测的，「是否跑对」需要审前提。用可观测的那个代理不可观测的那个，正是判据与命题不匹配。**
- 若把这句表扬固化，等于把「去跑」立成免检标准——**而这一轮的失败恰恰源于「我跑了所以我对」的自我授权。**

正确的记法是机制而非人：

> 今天两次纠错方向相反——一次 A 不接受 B 的声明去跑，一次 B 不接受 A 的声明去跑。**两次被纠正的一方都已先做过实测或推理，并且自信。**

**结论：交叉纠错有效不是因为某一方更可靠，而是因为双方前提不同、且至少有一方肯去实测。**

因果链是**两段**的，砍掉任何一段都不成立（`b1a0ab2e` 退回了协调方原先的单段表述）：

```
前提差异      → 双方看到不同的东西      （必要，配置属性，可设计）
     ↓
有一方肯去测  → 差异被兑现成纠错        （必要，行为属性，要养成）
```

**前提差异只让纠错成为可能，不产生纠错。** 反证：若双方前提不同但两边都不去跑，结果是两个自信且矛盾的结论，谁也说服不了谁——568 照样被归档成幻觉。今天之所以两次都纠回来了，是因为**两次都有人动手**。

> 所以该做的是**造前提差异 + 保持「不接受声明就去跑」的习惯**，而不是排可靠性名次。

协调方原写作「可靠性不是人的属性，是配置的属性」——**后半句过头，已退回**。它会推出一个错误的运维结论：只要凑够视角差异就能自动纠错，不必要求任何一方动手。

## 附带确立的做法

判定两个测试是否覆盖同一契约：**不得目视判重**。把 A 的突变集逐条注入 B 实跑，全部杀死才算等价——名字像不算数。（本次 4/4 杀死，含最刁的 R2「重采样」。）

## 新变体：「未测量」既不是绿也不是红

来源：本 session 实证（2026-08-21）。

`main` 的 tip `6e3590128`（#1637）**`cargo fmt --all -- --check` 是 exit 1** —— `engine/load.rs` 三处纯空白的过度缩进。它能编译、能过 573 个测试，只有 fmt 门抓得到，而 fmt 门确实存在（`ci.yml:173` 和 `:299`）。

关键在于：**查的时候它还没红出来。** main 最近四个 CI run 全是 `queued` 或 `in_progress`，一个都没完成。

> **判断一个 ref 的健康度必须看 run 的 `status`，不能只看 `conclusion`。** `conclusion: null` 的 run 在 `select(.conclusion=="failure")` 这类过滤器下**完全不可见** —— 它既不计入失败也不计入成功，于是「最近没有失败」这个查询返回真，而实际状态是**未测量**。

这是前面五种绿灯形态的**对偶**：那五种是「绿灯的证明力不足」，这一种是「红灯尚未被观测到」。二者的共同根是同一句——**证明力等于实际执行到的东西**——只是这次连执行都还没开始。

同一形状在 step 级也存在（来源：session `641c9dd2`）：`CLI ORT` 那个间歇失败，三次里有一次 job 报 `failure` 而其内 step 的 `conclusion` 是 `null`（runner 中途死亡），常用的 step 过滤器对它打印空列表，读起来像基础设施噪音，实则是同一个 step。**同一个坑在 run 级和 step 级各出现一次。**

操作规则：统计 CI 健康度时，`null` 必须单独成一栏，**不许并入任何一边**。

## 环境陷阱：`git push` 成功不等于 PR 被更新

本 session 实际踩到：worktree 的本地分支名是 `justinchuby-effective-lamp`，而 PR #1579 的 head ref 是 `justinchuby-memory-stack-on-main`。`git push origin HEAD:<本地名>` **成功了** —— 它创建了一个新分支，PR 纹丝不动。

识别方法在输出的那一行：

```
 * [new branch]          HEAD -> xxx        ← 建了新分支，PR 没动
   13c37a7f6..725184e7a  HEAD -> xxx        ← range 形式，才是真更新
```

**推之前先 `gh api repos/O/R/pulls/N --jq .head.ref` 拿真实 ref**，不要用工作树的分支名推断。这与「工作树分支名反映的是最后一个 PR，不是工作重心」是同一类错配，只是后果更硬：**一次看起来成功的 push，实际零效果。**

## 18. 红灯也只覆盖它实际执行到的东西 —— 遮蔽级 `null`

「绿灯只证明它执行到的路径」已经记了六种形态。本轮撞到它的**对偶**，而且更隐蔽。

`CLI ORT (Linux x86_64)` 是全 CI 唯一跑
`cargo clippy --locked -p onnx-genai-cli --all-targets -- -D warnings` 的 job。
它前面的 `Test onnx-runtime-ep-cpu-plugin (ORT gate)` 有约 23% 的 runner 崩溃率。

```
attempt 1   ORT gate 崩 → clippy 步骤 conclusion = null → 从未执行
attempt 2   ORT gate 活 → clippy 真跑 → exit 101（确定性缺陷，来自 #1637）
```

**一个间歇性失败长期替一个确定性失败挡子弹。**

- 这个 job **一直是红的**，所以「它红」这件事没有任何信息量增益；
- 危险动作是把整个 job 归给「已知间歇，可豁免」—— 那会连带豁免掉里面那个真缺陷；
- 我第一次看到它，是重跑**为了验证间歇性**时前序步骤恰好没崩。**观测到它纯属副产物。**

> **判据：一个持续红的 job，不意味着它内部的检查都被执行过。**
> 统计 CI 健康度时 `null` 必须单独成一栏 —— 并入通过会漏，
> 并入失败会把确定性缺陷混进间歇噪音里而被一起豁免。

`null` 至此在三个层级各咬过一次：run 级（「最近没失败」实为未测量）、
step 级（step 全 null，读起来像基础设施噪音）、**遮蔽级（本节）**。

## 19. 取证操作：日志带 ANSI 转义

GitHub job log 里是 `ESC[1mESC[91merror`，所以 `grep "^error"` **零命中**。
我据此有一轮误判为「日志里没有 error 行」——
**工具没匹配到，不等于内容不存在。** 与 §「未测量既不是绿也不是红」同形状。

```
gh api ".../actions/jobs/<id>/logs" | perl -pe 's/\e\[[0-9;]*m//g'
```

## 20. 加 cfg 门必须验反向配置

#1639 把 `MtpProposer` 的 re-export 从无条件改为

`origin/main` @ `81fc0060e` 同时挂着**四个确定性缺陷**（#1637 两个、#1641 两个）：

## 22. 合并冲突里「可再生的一侧」应当整体丢弃

`engine/load.rs` 冲突：我方是纯 `cargo fmt` 产物，main 侧是函数重写。

手工合并一个**格式化 hunk** 与一次**重写**，风险高且收益为零 ——
因为格式化输出**可再生**。正确做法：

```
git checkout --theirs <file>     # 整取 main
git diff --quiet origin/main -- <file>   # 验字节一致
cargo fmt --all                  # 重新生成
```

> **判据：冲突的一侧如果是工具的确定性输出，就不要参与合并，
> 取对侧后重跑工具。** 参与合并只会引入手工误差。
> 推论：这也是为什么把**格式化**和**语义修改**放进同一个 commit 是有害的 ——
> 冲突时无法只丢弃可再生的那部分。

## 23. 折叠嵌套 if 不是纯语法变换

#1641 的 `collapsible_if` ×5（`load.rs:389-398`）**不能**机械折叠成 let-chain：
外层 `metadata.speculative.as_ref()` 的绑定 `spec` 在链上全程存活，
与后面的 `metadata.model.as_mut()` 借用冲突，直接折叠**编译不过**。

修法是先把不可变读取**外提**为一个 `Option<String>`，再起 let-chain。

> **判据：lint 建议的重构可能改变借用生命周期。**
> 「clippy 说可以折叠」不等于「折叠后能编译」，
> 更不等于「折叠后语义相同」。必须编译验证，不能凭 lint 文本套用。
