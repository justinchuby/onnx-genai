### 2026-07-29: MLAS standalone threading now uses the persistent work-stealing pool
**By:** Deckard
**What:** `mlas_set_threading` now registers a persistent `WorkStealingThreadPool` backend instead of Rayon. `MlasStandaloneMaxThreads()` reports that global pool's degree of parallelism, and `MlasStandaloneParallelFor()` runs MLAS partition IDs through `WorkStealingThreadPool::parallel_for(..., grain=1)`. The pool is created once on first use (`available_parallelism().clamp(1, 8)`, override `ONNX_GENAI_MLAS_THREADPOOL_THREADS`) and reused for all standalone MLAS calls.
**Why:** This lets a single full-width `MlasQNBitGemmBatch(..., multithread=true)` use MLAS's own internal N partitioning on the low-overhead pool instead of static Rust SPMD shards or Rayon scopes. Resch's call path is the existing `mlas_sys::sqnbit_gemm(&packed, 1, &a, bias, &mut out, true)` or `sqnbit_gemm_with_workspace(..., true)` with full-width `SQNBitPackedB`; no `MlasThreadPool` wrapper is needed. Microbench (`ONNX_GENAI_FAST_BENCH=10 cargo bench -p mlas-sys --bench pool_microbench`) showed `mlas-qnbit/internal` routing through the backend with `calls=10 iterations=640 pool_threads=8 fallbacks=0` and ~26.7 µs/call for the 1x2048x2048 qsi4 fixture. Validation: `cargo build -p mlas-sys`, full `cargo test -p mlas-sys --lib --release`, `cargo check -p mlas-sys --target x86_64-pc-windows-msvc`, and the pool microbench passed.
