## Root cause / justification — native is MORE accurate

- All **141 MatMulNBits nodes in this export carry `accuracy_level=1`** (block_size 32,
  4-bit). Level-1 = fp32-activation compute (no int8 activation quantization). Verified by
  loading `model.onnx` and enumerating node attributes.
- On the ORT **CPU** kernel, level-1 is the fp32 activation path, so ORT-CPU *is* the fp32
  oracle with no graph rewrite. (History: PR #158 also confirmed an explicit all-141
  level-1 rewrite leaves the oracle argmax unchanged.)
- **ORT CUDA's MatMulNBits does not honor the level-1 fp32-activation path the same way**
  and lands on `315`; native's CUDA kernel tracks the fp32 oracle and lands on `374`.
- So matching ORT CUDA here would be an **accuracy regression**. Per Justin's directive
  (correctness beats matching ORT; more-accurate-vs-fp32-oracle is acceptable), native is
  KEPT. This is the same class Ridley/Brass locked for qwen3-0.6b and Phi-3.5-mini
  (int8/lower-precision activation tips a near-race; native stays on the fp32-correct side).
- Note: the acc-4 per-K-block-32 int8 activation concern from the task brief does **not**
  apply to this model — it ships at acc-level-1, so native uses fp32 activations here.

The GQA (kv=2) correlation from the bench is incidental: the divergence is an int4
activation-precision near-tie surfaced by this export, not a GQA-kernel bug. The MHA
coder-1.3b stays byte-identical only because none of its ties fall on the flip side.

- Date: 2026-08-01

- Harness: `profile_native --steady --decode-skip 8 --warmups 2 --runs 3 --tokens 64`.

## Headline

**No native-vs-ORT tok/s headline is possible on this model today.** The premise that
qwen3.6-27b is a "dense int4 transformer, capture-eligible, not MoE/Scan" is INCORRECT.
It is a **hybrid linear-attention model with Scan control-flow**: 16 full-attention (GQA)
layers + **48 linear-attention layers** carrying `conv_state` + `recurrent_state` recurrent
KV (not key/value). Both backends fail to produce a decode number here:

| Config | Result |
|---|---|
| 1. native, capture default-ON | **BLOCKED at load** — native KV binder rejects the rank-3 `conv_state` |
| 2. native, capture OFF | same load block (never reaches decode) |
| 3. ORT reference (CUDA EP) | **CRASHES** — internal ORT assertion during graph optimization |

No token IDs to compare — neither backend reaches steady decode. Parity gate is therefore
N/A (nothing to compare), reported honestly rather than massaged.

## Root cause — precise

### The model is a Scan linear-attention hybrid (not dense)
Graph inspection of `model.onnx`:
- KV ports: 16 layers expose `key`/`value` (GQA); **48 layers expose `conv_state` +
  `recurrent_state`** (linear/recurrent attention). Layers with attention: [3,7,11,15,19,...]
  (every 4th); the other 48 are `linear_attn`.
- Ops: `MatMulNBits`×497, `GroupQueryAttention`×16. The linear_attn layers use
  `Scan` + `Conv` + `ReduceSumSquare` + `Softplus`/`Swish` (recurrent scan), confirmed by
  Mary's prior native placement log.

### Native decode — BLOCKED (two independent gaps)
1. **Metadata (#384 class):** stock `inference_metadata.yaml` has no `model.io` block, so the
   loader can't disambiguate token_input among input_ids/attention_mask/position_ids:
   `cannot resolve model.io.token_input ... 3 ports match`.
2. **KV-contract / executor gap (the real blocker):** after supplying a hand-authored `io:`
   overlay (128 kv_inputs/outputs in graph order), the native CUDA KV binder rejects the
   recurrent state tensor:
   `CUDA KV input 'past_key_values.42.conv_state' must be rank-4 f32 or f16, got
   Float16 [Symbolic, Static(10240), Static(3)]`.
   The native decode loop models KV as rank-4 append-along-seq key/value caches; a rank-3
   recurrent `conv_state` (a running state, not a growing cache) has no place in that
   contract. Even if bound, the loop's append semantics are wrong for a recurrent state.
3. **Placement decline (corroborating, from Mary's log):** the CUDA EP also declines the
   linear_attn `ReduceSumSquare` in fp16 ("input dtype Float16 unsupported; expected
   Float32", 96 nodes) and 6968 nodes fall to CPU; heterogeneous CUDA+CPU placement is
   unavailable so the whole session would be CPU. This is the parked Scan/linear-attention
   capture lane, independent of #571.

### ORT — CRASHES on this build
CUDA EP is selected (`ort_available_execution_providers: [Tensorrt, CUDA, CPU]`), then ORT
1.27 aborts in graph optimization:
`stl_vector.h:1130 ... Assertion '__n < this->size()' failed` (NodeArg vector out of range),
preceded by many "Could not find a CPU kernel ... can't constant fold Add" notices on the
linear_attn/layernorm subgraphs. So ORT-CUDA cannot serve this model in this environment
either. (`--backend ort` therefore yields no tok/s.)

## Conclusion (honest)

- This is NOT the capture-eligible dense 27B the task assumed. It is the **Scan / linear-
  attention hybrid** class that is explicitly PARKED for native capture — the native KV
  contract has no recurrent-state (`conv_state`/`recurrent_state`) support, so native decode
  cannot even load it, let alone capture it.
- ORT-CUDA also crashes on it in this build, so there is no ORT baseline to beat here.
- **#571 capture default-on is unaffected and unrelated** — it only helps capture-ELIGIBLE
  plain-GQA decoders. The already-measured native-vs-ORT wins stand on those:
  qwen3-0.6b native 636 vs ORT 440 tok/s (1.44×), byte-identical (see
  `cohaagen-bench-capture-default.md`).

## What a real big-model headline needs
No genuinely dense, capture-eligible large (>=7B) GQA export is on hand:
- qwen3.6-27b / roy-work onnx-27b → Scan linear-attention hybrid (this note).
- qwen3.x-35b-a3b → MoE (declines capture; residency-bound, see offload notes).
- glm-4-9b-int4 → GLM indexer (declines capture).
- deepseek-v2-lite-int4 → MoE (declines capture).
- gemma4-e2b → embedding-bound (5.5 GB/step), not a clean decode headline.

Recommended next action to actually get the 27B-class headline Justin wants: either
(a) convert a genuinely dense large GQA decoder (e.g. a dense qwen 14B/32B, NOT the
linear-attention "next"/27b variant) and re-run this exact 3-config bench, or
(b) land native recurrent-state KV support (conv_state/recurrent_state threading) — a large,
separate lane (the parked Scan/linear-attention work) — before this specific 27b can run
natively at all. (a) is the short path to a number; (b) is required to run THIS model.

## Q1 — Per-decode-step phase breakdown (built-in per-op timer, `ONNX_GENAI_PROFILE_OPS=1`)
Instrumented top-level step ≈ 230 ms (profiler inflates absolute time ~1.3×; **ratios hold** vs the 170 ms clean wall). One representative decode step:

| Phase | ms/step | % step | detail |
|---|---:|---:|---|

| **Scan — body COMPUTE** | **~58** | **~25%** | 48 child sessions; ~78% of each is **3 fp16 MatMuls** (≈45 ms total, M=1 GEMVs) + delta-net glue |
| **Non-Scan eager op swarm** | **~80** | **~35%** | Transpose 19.9 (624 calls) · Reshape 11.0 (897) · Concat 7.8 (385) · Cast 6.4 (338) · Constant 5.8 (888) · ReduceSumSquare 5.4 (96) · Slice 4.2 · Split 4.0 · Add 3.8 · Tile 3.6 · Shape 2.7 · Mul 2.6 · RMSNorm 2.0 · Sigmoid/Conv/Silu/Div/Sqrt/… — each eager, host-sync, capture-rejected |

| Embedding (Gather) + Rotary + misc | ~2 | ~1% | 27b embed is a small Gather — **NOT** embedding-bound (unlike gemma4-e2b) |

**Dominant phase: the LinearAttention orchestration (Scan dispatch 31% + Scan body 25% + non-Scan swarm 35% = ~91%).** The weight GEMV (MatMulNBits) is only ~2% and at roofline — this is NOT a memory-bandwidth or kernel problem. capture DOES engage (captures=2/replays≈21/run, fallbacks=0) on the straight-line GQA/MatMul portion; the 48 Scan blocks + their surrounding elementwise swarm run **eagerly**.

## Q2 — Scan overhead: dispatch vs compute (THE decomposition)
Isolated one decode step and summed the 48 Scan child-body session executions:
- Scan op wall (top-level) = **130.9 ms** (56.75% of step, 48 calls)
- Sum of the 48 child-body `node execution` = **58.4 ms** (median **1.205 ms**/layer; ~78% is the 3 body MatMuls)
- **⇒ Scan control-flow dispatch overhead = 130.9 − 58.4 ≈ 72 ms — ~55% of Scan time is NOT compute.**

Where the 72 ms goes (from `control_flow.rs::exec_scan` / `run_subgraph`): the child executor **is cached** (`subgraph_execs`, no per-call re-plan), so the cost is per-Scan **host-round-trip marshaling**, each with a stream sync:
- `prepare_subgraph` clones the body's outer-scope captures per layer,
- `scan_slice` copies the scan input **device→host bytes→device** (`Tensor::from_raw` on host bytes) every step,
- `finish_scan` + `store_output_tensor` marshal the 96 recurrent-state / scan outputs back out.

**A/B of the in-flight slice-1a flag `ONNX_GENAI_SCAN_INLINE_SINGLE_TRIP=1`: 170.5 → 171.1 ms/tok (noise, no win).** Expected and important: at decode `trip_count==1` the generic loop already runs the body exactly once, so inlining removes only loop bookkeeping — NOT the marshaling. **Slice-1a is the necessary scaffold, not the payoff.**

## Q3 — Tractable levers, ranked (yield vs risk)

1. **Inline the single-trip decode Scan body INTO the parent plan, then let it enter the existing capture — HIGH yield / MED-HIGH effort. RECOMMENDED FIRST.**
   Extends slice-1a: instead of running the body through a child session (`run_subgraph` + `scan_slice` host round-trip + per-layer `prepare_subgraph`), splice the single-iteration body ops into the parent executor's warmed fixed-shape context. This (a) deletes the ~72 ms dispatch marshaling and (b) makes the body's 45 ms of MatMuls + local glue eligible for the CUDA graph that already captures the GQA/MatMul portion. Keyed on **runtime** `trip_count==1` (slice-1a's design) so prefill (trip_count>1) is untouched — the "prefill/decode shared-plan trap" is handled by the runtime key, so this lane is *unbuilt, not blocked*. Byte-exact by construction (same `run_scan_body_step`). **Est: ~72 ms off → ~98 ms/tok (~10 tok/s), ~1.7×.**

2. **Capture-enable the non-Scan eager swarm (Transpose/Reshape/Concat/Cast/…) — MED yield / MED-HIGH effort.**
   ~80 ms/step of layout+elementwise ops are capture-rejected for per-call metadata reasons (Transpose uploads perm metadata + syncs → 19.9 ms/624 calls is the fattest single target; Cast/Constant/Slice similar). Cache the perm/descriptor metadata and match the warmed fixed-decode signature so they enter the graph and drop their host syncs. **Est: 80 ms → ~15 ms.** Touches capture internals broadly (many small ops).

3. **Alias / in-place the 96 recurrent-state swaps — LOW-MED yield / LOW-MED effort.** Bind present==past state buffer to skip a device copy per state per layer. Largely subsumed by Lever 1 (inlining removes the marshaling round-trip). Standalone yield modest.

4. **Fuse the gated-delta-net recurrence into one custom CUDA kernel — MED-HIGH yield / HIGH effort+risk.** Collapse each layer's Conv+ReduceSumSquare+Softplus+Silu+Div+Sqrt+Mul swarm into one kernel; attacks body compute AND launch count. Longest lane, new kernel + byte-exactness vs fp16 reference. Defer.

5. **"Full Scan-body graph capture" (the parked hard lever) — reframe.** Scan is control-flow and not directly capturable, BUT at decode `trip_count==1` it degenerates to a straight-line body — which is exactly what **Lever 1** captures without capturing the Scan node itself. So the hard lever is not needed for decode; Lever 1 is its tractable form.

## Q4 — Honest verdict: can a bounded lever beat ORT (17.38 tok/s, need ~3×)?
**Not with a single lever.** The captured-compute floor ≈ ORT's ~57 ms/tok (the M=1 GEMVs still cost their compute under capture). Path to parity/beat:
- **Lever 1 alone:** ~170 → ~98 ms/tok (~10 tok/s, ~1.7×) — closes most of the gap, still < ORT.
- **Lever 1 + Lever 2:** ~98 → ~55–65 ms/tok (~15–18 tok/s) — **reaches ORT parity / slight beat.**
The non-Scan swarm (80 ms) does NOT disappear when the Scan is inlined, so beating ORT requires both. This is an **M-sized 2-step lane**, de-risked by slice-1a already being merged.

**RECOMMENDATION:** Build **Lever 1 first** (inline single-trip decode Scan body into the parent plan + admit it to the existing capture) — largest single chunk (~1.7×), clear scaffold (slice-1a), byte-exact, prefill-safe via the runtime trip_count key. Measure; expected ~10 tok/s. Then dispatch **Lever 2** (non-Scan swarm capture, Transpose first) to cross ORT. Do **not** start with slice-1a's flag flip alone — measured no-op. Do **not** touch MatMulNBits/GQA — already at roofline.

## Root cause / classification

**STRUCTURAL / orchestration bottleneck — NOT a slow CUDA kernel.**
Decode is *not* memory-bandwidth-bound: the INT4 weight GEMVs (MatMulNBits) cost only
~4.4 ms/step (2%), i.e. already at the ~4.8 ms HBM roofline, and GQA is 0.6%. The
remaining **~95%** of the step is the **48 LinearAttention layers implemented as ONNX
`Scan` control-flow** plus an un-fused swarm of Transpose/Reshape/Concat/Cast/Reduce/
elementwise ops. `Scan` is not CUDA-graph-capturable, so each of the 48 blocks runs
**eagerly**, and its body ops each perform a **host-side stream synchronize** per launch
(624 Transposes/step alone, each syncing). At decode seq_len=1 the Scan iterates once,
yet still pays full eager-executor + per-op-sync latency. That serial host-bound dispatch
— not kernel bandwidth — is the 35–40x gap.

**Owner:** This is **native_decode control-flow / graph-capture + LinearAttention eager
op paths** (Scan lowering, Transpose per-call metadata sync, fixed-shape capture-signature
matching) — Justin's / pipeline-control-flow area. It is **NOT** a MatMulNBits/GQA kernel
fix in Cohaagen's lane (those are already at roofline; do not touch them for this).

## Highest-value optimization candidate (+ ceiling)

Make the LinearAttention **decode** block capturable/fused:
1. Lower the seq_len=1 decode `Scan` to a straight-line **fixed-shape** subgraph (the
   recurrence degenerates to a single step at decode), so it AND its surrounding
   Transpose/Reshape/elementwise glue match the warmed signature and enter the CUDA graph;
   **and/or**
2. Fuse the gated-delta-net state update (conv_state + recurrent_state) into a single
   custom CUDA kernel, removing the 48×(dozens of tiny eager launches + syncs).

**Ceiling:** ~95% of the step (Scan 56% + Transpose 9% + the layout/elementwise swarm) is
eager LinearAttention orchestration. Bringing it into capture / fusing it targets the
~5–10 ms weight-bound floor → an estimated **~15–30x decode speedup** (5.9 → ~90–170 tok/s

### 2026-08-01: Inc-1b DESIGN — decode-specialized inlined-body graph (capture-fold the single-trip LinearAttention Scan). DESIGN ONLY, for capture-team review.

**By:** Cohaagen (EP/runtime perf)
**Status:** Design for review by the capture owners (Mary / #443–#543). NO code, NO PR. Follows `cohaagen-27b-lever1.md` (why the bounded edit was STOPPED) and `cohaagen-27b-decode-perf.md` (phase breakdown).

**Problem recap (measured):** qwen3.6-27b hybrid decodes at 167 ms/tok native CUDA vs ORT 57 ms/tok. 48 LinearAttention layers each run their body through a **separate child `Executor` in `RunMode::Eager`** (`control_flow.rs:21` hard-codes Eager; child bodies can never capture). Per-step cost: ~55 ms eager body dispatch (`plan_eager.child`), ~23 ms child-output D2H→H2D (`collect_outputs.child`), ~7.5 ms child setup, ~6 ms finish/store. The ~55 ms eager chunk is removable only by folding the body into the parent CUDA graph — which the parent's segmenter cannot reach because the body lives in a **separate Graph/ValueId namespace**. Inc-1b removes that wall for the decode (`trip_count==1`) case.

## 1. GRAPH TRANSFORM — produce the decode-only inlined variant

**Core: a second `Executor`, not a mutated one.** Keep the loaded prefill Executor/graph **byte-identical** (zero prefill risk). Add a sibling `decode_inline_exec: Executor` built from a transformed graph, sharing the same `Arc<WeightStore>` and `Arc<dyn ExecutionProvider>` (exactly the multi-plan/shared-weights pattern `ChildExecutor` already uses). The native decoder routes prefill → main exec, decode steps → `decode_inline_exec`. Both bind the **same persistent KV/state device buffers** via `ExternalBindings`, so state continuity across the prefill→decode boundary is preserved (this is the key integration invariant — see §3).

**New pass:** `inline_single_trip_scan_bodies(&Graph) -> Graph` (onnx-runtime-ir graph transform; the IR `Graph` already supports `add_input`/adding values/nodes/initializers, used today in `ChildExecutor::compile`). For each `Scan` node:
- **Lower to one straight-line iteration** (valid ONLY because at decode the scan axis extent is 1 — hence a *decode-specialized* graph; the untouched prefill graph keeps the multi-trip Scan).
- **Scan input → body formal:** the scan input has scan-axis length 1 at decode; emit a `Reshape`/`Squeeze` dropping that axis and wire it to the body's scan-input formal ValueId (remapped, below).
- **Body node copy + ValueId remap:** clone every body node into the parent graph with **fresh parent ValueIds** (`remap: body ValueId → new parent ValueId`). Body formal state inputs map to the Scan node's parent state-input ValueIds; body formal scan input maps to the squeezed slice; body **lexical captures** (weights/constants) resolve by name to the values already in parent scope (same resolution `ChildExecutor::new` does via `capture_names`). Body-local initializers become parent initializers.
- **Body outputs → Scan outputs:** first `num_state` body outputs (present conv_state/recurrent_state) become the Scan node's **state outputs** (parent present-state ValueIds); scan outputs get an `Unsqueeze` re-adding the size-1 axis to match the Scan's declared scan-output shape.
- Delete the Scan node; run `InferenceRegistry::infer_graph` (Permissive) over the merged graph to re-resolve interior shapes (same call `ChildExecutor::compile` uses).

**Where it runs:** lazily at **first decode step** (not load) — we only pay the transform+compile once, and only for models that actually take the hybrid decode path; single-component dense decoders never trigger it. Guard: only lower Scans that are structurally single-trip-eligible (carry recurrent `state_pairs` per #573 io, i.e. LinearAttention), and at runtime **assert the scan-axis extent == 1**; if a decode step ever presents extent ≠ 1, fall back to the main (Scan) exec for that step. This makes the specialization safe by construction.

**Prefill vs decode = separate plans, NOT a conditional segment.** A conditional-segment approach (one plan, branch on trip_count) was rejected: it would put a data-dependent control decision inside the capturable region, defeating the fixed-decode signature. Two plans keep each plan's shape signature static.

## 2. CAPTURE INTEGRATION

Once inlined, the body's nodes are **ordinary parent-plan nodes**. `plan_capture_segments` / `run_plan_segmented` (run.rs) evaluate each for `CaptureSupport` exactly like any kernel — no special-casing. The straight-line body ops (the 3 MatMuls/layer, Conv, RMSNorm, elementwise that pass the warmed signature) fold into captured segments alongside the already-captured GQA/MatMul portion; the child-executor entry/exit and per-op eager syncs for them disappear.

**Honest scope of what captures:** body ops that currently decline for per-call-metadata/stream-sync reasons (Transpose perm upload+sync, dynamic Slice/Tile/ReduceSum host reads) **still seam** — that is Lever-2 territory and is orthogonal. So Inc-1b folds the *capturable subset* of the body (dominant: the MatMuls); the non-capturable body ops remain eager seams until Lever 2. This is why Inc-1b alone does not reach ORT (see §6).

**Warmed fixed-decode signature must now include the inlined interior.** The inlined body's interior ValueIds are new parent values; `capture_warm_shapes` / `capture_warm_seeded` (state.rs) already snapshot every resolved shape per warm step and retire the graph if a seeded shape re-resolves differently — inlined nodes are covered automatically by that mechanism. No new signature machinery; the inlined shapes just join the existing snapshot.

**#443/#543 invariants that MUST NOT change** (capture-team review focus):
- Persistent output binding requirement (KV **and** state device-resident + owned) — Inc-1b keeps state persistent (§3), so this holds.
- No stream-synchronize mid-capture — inlined ops that sync must still be quarantined to eager seams by the existing `capture_quarantine_ops` retry loop; the transform must NOT bypass that loop.
- "Recapture on any shape change; never replay a stale graph" — unchanged; inlined shapes ride the same warm-seeded retirement.
- Segment-count/seam accounting stays transparent (`capture_segmentation`) — inlined seams should surface with the same `SeamReason` classification, not a new opaque node.

## 3. RECURRENT STATE (96 pairs, #573 contract)

#573's `io.state_pairs` binds each `present.k.{conv,recurrent}_state` → `past.k.*` across steps as device-resident persistent buffers. Inlining moves the **state-update ops** from the child body into the parent plan, but does **not** change the binding contract: the Scan's state inputs/outputs become parent ValueIds bound to the same persistent state buffers `ExternalBindings` supplies. The decode-inline exec must bind the identical persistent state buffers the main exec used at prefill hand-off — verified by a continuity test (§4).

**Aliasing (in-place present==past): DEFER, do not do in Inc-1b.** A captured graph requires stable, distinct persistent bindings; aliasing present onto past across a recorded graph is a delicate WAR-hazard change (mirrors the weight-offload eviction-safety concerns). Keep present/past **distinct** device buffers as today. In-place state aliasing is a separate micro-opt with its own correctness pass, not part of the capture-fold.

# Cohaagen — #581 offload residency-hit fix — SCOPE (honest sizing)

2026-08-01 · By: Cohaagen · Requested by: justinchuby (autonomous) · READ-ONLY scope (no code changed)

Scoped against `origin/main` @ `70bac712` in a throwaway detached worktree.

## TL;DR / recommendation: **DEFER the build.**

Tracing the live path shows the residency cache **already has a correctly-wired,
copy-free hit path keyed by a stable per-weight id**. The #581 premise — "offloaded
weights re-page even when the budget could keep them resident" — **does not hold for the
27b**: its offloadable working set (~13.5 GB of INT4 `MatMulNBits`/MoE weights) **exceeds
any VRAM-saving budget**, and the access pattern is a *full sweep of every weight once per
decode step*. Under that pattern an LRU cache smaller than the working set evicts exactly
the page it will need next → **~0 % hit rate by construction**, not a missing-consultation
bug. That is why raising the budget 4→12 GiB moved resident VRAM (8.5→17 GB) but **not**
speed. So there is **no small "consult the residency map" fix** to build — the map is
consulted and hits are free. The genuine wins (per-miss cost reduction, async-prefetch
overlap, capacity-aware policy) are **M/L**, touch the async path (#572) and dispatch, and
**cannot reach fully-resident speed** when the working set doesn't fit. Details below.

---

## 1. Exact mechanism (call path, cited)

Per **every** node dispatch, for each offloadable weight input:

`executor/dispatch.rs:844` `self.ep.page_lazy_weight(vid.0 as u64, lazy)` — called inside
`build_input_bindings` (`dispatch.rs:752`), which runs on **every node, every decode step**
(the paged `Arc` is held in `InInfo.paged` only for that node's dispatch, `dispatch.rs:860`,
then dropped). Key = `vid.0` (the ValueId) — **stable per weight across steps**.

→ `provider.rs:196` `page_lazy_weight` → `residency.resident_materialized(key, weight)`
(`provider.rs:201`).

→ `weight_paging.rs:475` `resident_materialized`:
  - `get_hit(key)` (`:515`): `pages.get(&key)` in a `HashMap<u64, Arc<CudaWeightPage>>`
    (`:422`); on hit `record_hit` (LRU touch + `hits += 1`) and **return the cached Arc with
    NO copy** (`:460`). ← the "residency hit" already exists and is free.
  - On **miss**: `weight.materialize()` (`:483`) then `CudaWeightPage::upload[_async]` +
    `admit` (LRU insert, evict-to-fit).

**What decides "page now" vs "already resident":** purely `HashMap` membership of `key` in
`pages`. There IS a maintained residency map, and it IS consulted first. A page leaves the
map only via `evict_to_fit` (`:649`).

**Per-MISS cost (the real hot cost), each ~hundreds of times per step:**
1. `LazyWeight::materialize()` → the executor's closure (`build.rs:389`) does
   `store.bytes(&weight)` (returns a **borrowed mmap slice**, `weights.rs:558`
   `bytes<'a>(…) -> Option<&'a [u8]>`) then **`Arc::<[u8]>::from(bytes)` (`build.rs:396`) —
   a full fresh host alloc + memcpy of the whole weight, every miss.**
2. `CudaWeightPage::upload` (`weight_paging.rs:188`): `alloc_raw(len)` (**cudaMalloc**) +
   `htod` + on the sync path an implicit serialization (blocking copy). Async variant
   (`:225`) additionally allocs pinned staging and copies into it.
3. `admit`→`evict_to_fit` (`:649`) frees the LRU page's VRAM (**cudaFree**) to make room.

So each miss = host memcpy + cudaMalloc + H2D + cudaFree, serialized, × every weight ×
every step. That is the ~40× (measured 172 ms/tok resident → 6.9–8.4 s/step offloaded).

## 2. The minimal fix for the dominant win — **does not exist as scoped**

The hypothesized fix ("consult a residency set / device-ptr cache before the htod") is
**already implemented** (`get_hit`, `pages` map, LRU `order`, `resident_bytes` accounting,
`hits`/`page_ins`/`evictions` counters). There is no missing generation-counter or
un-consulted map. Empirically the 4→12 GiB budget bump not helping (and peak VRAM tracking
the budget) confirms the misses are **capacity/working-set**, not a stale-lookup bug.

Correctness hazards that a hit-path fix would normally face are **absent or already handled**:
- **Capture-stability** (a captured graph must not see a moved device ptr): **removed** —
  offload force-disables CUDA-graph capture (`native_decode/cuda.rs:45-56`), so no replay
  ever observes a paged ptr. This *simplifies* any future work here.
- **Eviction/WAR** (an evicted-then-reread weight must re-page): already correct —
  `evict_to_fit` only evicts pages with `Arc::strong_count == 1` (`:656`), i.e. not the
  in-flight one; the Arc pins the page for the consuming kernel's lifetime (`PagedWeight`
  keep-alive, `provider.rs:205`).

## 3. Eviction policy interaction

`ResidencyInner` is a **classic LRU** (`order: Vec<u64>`, front = LRU; `touch` moves to back
`:620`; `evict_to_fit` pops from front `:649`). For the decode access pattern (each weight
read exactly once per step, in the same layer order), **LRU is the pessimal policy when the
working set > budget**: by the time layer 0's weight is needed again next step, every other
layer has been paged in after it, so it sits at the LRU front and was already evicted →
guaranteed miss. No stock policy (LRU/MRU/FIFO) yields hits for a full single-sweep that
doesn't fit; only **budget ≥ working set** (≈ no saving) or **prefetch overlap** helps.
There is no working-set-aware / pin-hot-layers policy today — that would be new code.

## 4. Honest T-shirt size + staging

There is no bounded "hit-map" PR to build. The real levers, sized honestly:

| Lever | What | Size | Byte-exact? | Yield (27b) |
|---|---|---|---|---|
| A. Kill redundant host memcpy | H2D directly from the mmap `&[u8]` instead of `Arc::<[u8]>::from` (`build.rs:396`); optionally via a reused pinned-staging ring | **S** | yes (identical bytes) | modest — removes 1 full host memcpy/weight/step; does **not** remove cudaMalloc/free/H2D/sync; won't approach resident |
| B. VRAM page pool | reuse fixed-size device allocations across evict/admit to kill per-miss cudaMalloc/cudaFree | **S/M** | yes | modest — removes alloc/free driver churn |
| C. Async double-buffered prefetch | schedule layer K+1 page-in overlapped with layer K compute; needs a warm-host materialize cache so the copy is actually overlappable (my #572 A/B found sync > async under pure thrash precisely because nothing overlaps) | **M/L** | yes if fenced (existing `upload_async` fence path) | the real latency-hiding win, but caps at "hide the H2D behind compute", not eliminate it |
| D. Capacity-aware residency (pin hot set, evict cold) | only helps if some layers fit and repeat; for a uniform single-sweep it doesn't | **M** | yes | low for 27b's uniform sweep |

**Correctness bar for any of these:** byte-EXACT vs the resident run + CPU fp32 oracle —
the `[11751, 13, 271, 248068, 271, 248069, 271, 4639, 369, 4252, 13, 11751, …]` gate
(`native_autoderive_io_cuda_e2e`, plus a 27b offload-ON == offload-OFF token-parity test and
the 0.6b golden). All levers above keep the copied bytes identical, so parity is preserved.

**Expected speedup if the hot set fits budget:** for the 27b it *doesn't* fit any
memory-saving budget, so "close to 172 ms/tok" is only reachable by making budget ≥ ~14 GB
(≈ zero saving) — i.e. **not achievable as an offload win**. With overlap (C) the realistic
ceiling is bounding the slowdown from ~40× toward perhaps ~2–4× (H2D hidden behind compute),
still a memory-for-throughput trade, never a speedup over resident.

## 5. Bounded vs the L/XL long-term lever

- **Bounded, real, byte-exact down-payments:** Lever A (S) and Lever B (S/M). Neither is the
  "dominant win" and neither materially changes the 40× alone; they reduce per-miss constant
  factors. Worth doing only as prep for C.
- **The real optimization (M/L):** Lever C async-prefetch overlap + a warm-host materialize
  cache — this is where the yield is, but it is **not** a small hit-map patch: it touches the
  async page-in path (#572), dispatch scheduling, and needs a prefetch schedule keyed off the
  plan's weight order.
- **Separate L/XL "reconcile offload with capture":** capture the compute straight-line while
  paging weights around a stable capture (today they're mutually exclusive,
  `native_decode/cuda.rs:45-56`). Large, correctness-delicate (#443/#543 capture invariants).
  Keep parked and separate.

## 6. Strategic note (in-scope: "optimize the offloading feature")

The honest framing for Justin: **weight offload is a fit-in-VRAM enabler, not a throughput
optimization.** On the 143 GB H200 the 27b (~14 GB weights) fits resident trivially, so
offload only *costs* there. Its value is models that **don't** fit (large MoE / multi-model
co-residency / small-VRAM cards). The optimization worth funding is Lever C (overlap) so that
*when offload is required*, the penalty is ~2–4× not ~40×. I do **not** recommend spending a
PR chasing the 27b-on-H200 offload number, and there is **no bounded hit-map fix** to ship.

## Blast radius of any future work

Levers A/B: `weight_paging.rs` + `build.rs` materializer only; no capture, no dispatch
semantics, byte-exact. Lever C: adds async scheduling around dispatch — must not regress the
resident fast path (offload-off is untouched, `page_lazy_weight` returns `None`) and must keep
the fenced-copy WAR ordering. Lever D/capture-reconcile: touches #443/#543 — capture-team sign-off required.

## Verdict

**Do NOT build now.** The residency hit path is already correct and free; #581 as written is
a misdiagnosis for the 27b (working-set > budget → LRU 0 % hits is correct behavior). Recommend
re-scoping #581 to "async-prefetch overlap for weight offload (Lever C, M/L)" and closing the
"re-pages when resident" framing with this trace as evidence. Optional S down-payment: Lever A
(kill the redundant host memcpy) — cheap and byte-exact, but not the dominant win, so only if
you want an incremental commit ahead of the prefetch lane.

## 1. What `pipeline/mod.rs` does today for the multi-component path + the exact seams

### 1a. Two distinct "native" paths exist — only ONE bails

There are **two** ways a component runs natively today, and conflating them hides where GAP-3 actually is:

1. **Pure-native selection (BAILS).** `PipelineEngine::build` (`mod.rs:624`) picks one backend for the
   whole pipeline (`mod.rs:635-643`). `Auto` calls `resolve_auto_pipeline_backend` (`mod.rs:282-291`),
   which returns `PipelineBackend::Native` iff **some component model uses `pkg.nxrt::BlockQuantizedMatMul`**
   (`engine/decode_backend.rs::model_proto_requires_native_backend`: gated on opset `pkg.nxrt` v1 + a
   `BlockQuantizedMatMul` node). When `backend == Native` and the crate has `native-backend`, `build`
   returns **`Err(build_native_pipeline_and_report_gap(...))`** (`mod.rs:657`). That function
   (`mod.rs:318-341`) loads every component through the backend-neutral `ComponentSession` seam
   (`build_native_pipeline_components`, `mod.rs:347`) **and then throws** the
   *"native pipeline decode is not yet implemented"* error (`mod.rs:327-340`). **No decode loop is ever
   reached** — the engine cannot even be constructed. This is the GAP-3 hard blocker.

2. **Hybrid injection (WORKS TODAY).** With `backend == Ort`, the flat-AR driver drives *named*
   components natively inside the ORT-owned decode loop, selected by env flags:
   - `ONNX_GENAI_PIPELINE_NATIVE_STEP_COMPONENTS` → `native_step_component_set` (`mod.rs:378-389`) →
     `build_step_component_session` loads those every_step components as native nxrt `ComponentSession`
     (`mod.rs:422-462`).
   - `ONNX_GENAI_PIPELINE_NATIVE_DECODER` → `native_decoder_selected` (`mod.rs:400-412`) →
     `build_native_pipeline_decoder` (`mod.rs:472-507`) builds a `NativePipelineDecoder` whose KV is
     device-resident.
   The decode loop itself is **already backend-agnostic and already multi-component**: see §2.

## 3. The KV / present-state contract between components

**Two different edges, do not conflate them:**

**(a) Component→component *activation* routing (already works).** In the flat-AR pipeline the only
inter-component tensor is the embedding: `embedding.inputs_embeds → decoder.inputs_embeds`
(dataflow, e.g. `tests/fixtures/tiny-gqa-embeds-cuda/inference_metadata.yaml`). The producer's output is
written to the shared pool (`paged_decode.rs:168-173`) and re-read as a decoder `extra`
(`:183-200`), crossing the host seam as one token's `[1,1,width]` embedding per step. **KV does not flow
across this edge** — each component owns its own state. This is fully implemented for ORT and native.

**(b) Decoder present-KV → paged cache / shared-KV (the missing contract, S2).** Unlike the
single-session case where `run_decode_step_with_extra` returns `present.*` outputs that
`mirror_present_kv_to_pages` copies into pages (ORT path: `decoder_component.rs:122-139`), the native
decoder **keeps KV session-resident and exposes no host present tensor** (`decoder_component.rs:252-259`).
So:
- **Single-session ORT:** present-KV is a graph *output* every step → host `Value` → paged mirror.
  Windowed decoders convert absolute→retained index before mirroring (`paged_decode.rs:246-259`,
  `retained_kv_len`).
- **Native pipeline decoder:** present-KV lives in-session; there is no host tensor to mirror. To page
  it we must add a native "read present slice for tokens `[retained_past_len, +input_len)`" accessor,
  then feed `mirror_present_kv_to_pages` (whose fp16→fp32 widening + append-range semantics are already
  the engine's KV contract, `kv_bridge.rs:296-372`).
- **MoE / shared-KV (Qwen3.6-35B-A3B):** the *shared-KV group* contract (`SharedKvGroup`,
  `native_decode/mod.rs:163-200`; fixture `tests/fixtures/tiny-glm52-qmoe-indexshare`) means one
  component's key/value present is bound as *another* component's KV input (`target_key_input` /
  `target_value_input`). At 35B scale this must be **paged** (KV won't fit resident per request), so the
  MoE serving story is blocked on the same S2 present-KV export, generalized from "mirror to pages" to
  "mirror to pages **and** re-bind as a downstream KV input". The `mirror_last_present_kv` bail
  (`decoder_component.rs:256`) is the single choke point where both land.

**Contract summary Inc-A relies on:** activation routing (a) is complete; Inc-A stays on the *non-paged*
decoder path so it never needs (b). (b) is the whole of Inc-C.

- Emit `Squeeze` dropping the size-1 scan axis → body scan-input formal.

State formals bind to the Scan's parent state-input values; captures resolve **by name** in parent scope (same as `ChildExecutor::new` via `capture_names`); body-local initializers promoted to parent initializers.
- First `num_state` body outputs → parent present-state values; scan outputs get `Unsqueeze` re-adding the size-1 axis.
- Delete the Scan node + drop its `body` subgraph entry.
Non-eligible Scans (multi-trip / non-recurrent / nested control flow / unresolved captures) and dense graphs are left structurally unchanged (no-op). Input graph never mutated in place.

## Why Tile declines / syncs today (cite)

`TileKernel::execute` (movement.rs:1082) does **two** per-call host syncs:
1. `host_ints(&self.runtime, &inputs[1], "Tile")` (movement.rs:1091) reads the

2. `launch_metadata` (movement.rs:205) does `alloc_raw` + `htod` + `synchronize()`

## The fix (same PersistentMetadata pattern as Transpose/Expand + warmed repeats)

Key observation: the `tile_bytes` kernel metadata is `[output.shape, input.shape,
input_strides]` — it **never uses `repeats`**. `repeats` is read *only to validate*

output buffer from shape inference on the same `repeats`, a fixed
`(dtype, input_shape, output_shape)` signature mathematically fixes `repeats`

- Add `PersistentMetadata` + `warmed_signature: Option<{dtype, input_shape,
  output_shape}>` to `TileKernel` (mirrors Transpose/Expand exactly).
- Read+validate `repeats` via `host_ints` **only on the unwarmed eager path**
  (first sight of a signature) — preserving the original validation precisely.
  Once warmed, skip the device→host read entirely (steady decode + capture).
- Replace `launch_metadata` with `launch_persistent_metadata` (cached buffer, no
  per-call alloc/htod/sync/free). Metadata bytes are **identical**.
- Guard: error on signature change mid-capture; `capture_support` → `Supported`
  once warmed. `metadata` built from `output.shape` (== the previously-validated
  `expected`), so byte-identical launch.

**Byte-exact:** same `tile_bytes` kernel, identical metadata bytes; only the
metadata-buffer lifecycle and the *timing/gating* of the repeats validation change.

# Scope: weight-offload increment-2 (double-buffer look-ahead / #544 follow-up)

Date: 2026-08-01
By: Cohaagen
Lane: B (offload optimization) — READ-ONLY scope + instrumented micro-measurement
Base: origin/main 22a90a71 · worktree wt-cohaagen-inc2scope (removed after run)
HW: 1× H200 143GB (CUDA_VISIBLE_DEVICES=2)
Model: qwen3-0.6b int4 CUDA (543 MiB weights), native decode, 32-token non-steady runs
Instrumentation: THROWAWAY uncommitted timers in weight_paging.rs (materialize / pinned /
  h2d / wait / evict-drain) + a profile_native print. Worktree discarded — nothing committed.

## RECOMMENDATION (headline)
**DEFER inc-2 as a perf build.** Three grounded reasons:
1. **No on-hand ONNX model exceeds 143GB VRAM** (largest runnable is the 68GB A3B f16). Offload is
   never on a production critical path today — it is a CI / measurement forcing function
   (budget-cap), not a live speedup. Optimizing it wins nothing users see now.
2. **The #544 async look-ahead attacks the wrong term.** Measured page-in tax in the eviction
   regime is materialize (~48%) + pinned-staging alloc/copy (~48%); raw H2D is ~3% and
   eviction-drain <1%. A double-buffer that overlaps H2D can only touch that ~3%.
3. **Async page-in is already a NET REGRESSION in the thrash regime** (12.16 tok/s async-on vs
   15.84 tok/s async-off) because it adds pinned staging that CANNOT overlap (every admit evicts
   → drains). So "increment-1" (async page-in, default-on) is currently negative where eviction
   dominates. The honest 1-line win is to make async page-in **opt-in**, not to build inc-2.

If Justin still wants a build, the highest-yield first sub-increment is **NOT look-ahead** — it is
a **warm host cache of materialized canonical bytes** (amortize the ~48% materialize) plus
**dropping/ring-buffering the async pinned staging** (kill the ~48% + the async regression). That
turns page-in into ~pure H2D (~3%). But it still only helps the model-doesn't-fit regime, which we
can't hit on-hand.

## Q1 — Tax breakdown (instrumented) — THE key result
Env: `ONNX_GENAI_WEIGHT_OFFLOAD=1`, device budget via `ONNX_GENAI_WEIGHT_OFFLOAD_DEVICE_BYTES`,
async via `ONNX_GENAI_WEIGHT_OFFLOAD_ASYNC_PAGEIN`. (Note: a real device-VRAM budget env DOES
exist — corrects my earlier offload note that claimed none.)

| Config | tok/s | ms/step | page_ins | hits | evict | materialize | pinned | h2d | wait | evict_drain |
|--------|------:|--------:|---------:|-----:|------:|------------:|-------:|----:|-----:|------------:|
| resident (offload off)         | 83.27 | 12.0 | 0     | 0     | 0     | — | — | — | — | — |
| offload 256MiB async (no evict)| 6.91  | 144.6| 392   | 12152 | 0     | 50.2ms | 117.0ms | 2.1ms | 0.4ms | 0.0ms |
| offload 96MiB async (thrash)   | 12.16 | 82.2 | 12544 | 0     | 12387 | 791.0ms | 792.1ms | 46.4ms | 7.2ms | 15.1ms (7079 calls) |
| offload 96MiB SYNC (thrash)    | 15.84 | 63.1 | 12544 | 0     | 12387 | 743.7ms | 0* | 0* | 0* | 11.9ms |
(*sync `upload` path has no pinned staging and its blocking htod is not separately instrumented.)

Per-page (96MiB async, 12544 page-ins): materialize≈63µs, pinned≈63µs, h2d≈3.7µs, evict_drain≈2.1µs/call.
**Ranking (eviction regime): materialize (~48%) ≈ pinned-staging (~48%) ≫ H2D (~3%) > evict_drain
(<1%) > fence-wait (~0.4%).** #544's "materialize-bound" claim is HALF right: materialize is ~half;
the pinned-staging alloc+copy the ASYNC path itself introduced is the other half. Raw transfer
(H2D) and the eviction compute-drain are both minor in absolute ms.

Two structural facts the numbers expose:
- **Offload disables CUDA-graph capture** (resident run: cuda_graph enabled=true captures=1
  replays=30; all offload runs: capture off). Even the 256MiB no-eviction case (mostly hits, only
  392 page-ins) runs 6.91 tok/s vs 83 resident — a ~12× loss with almost no transfer. So the
  dominant offload cost for a fitting model is **losing capture + per-weight pager dispatch on the
  hot path**, NOT page-in. Inc-2 look-ahead does not touch this.
- **More budget was SLOWER** here (256MiB 6.91 vs 96MiB 12.16 tok/s): a large resident set makes the
  per-hit LRU bookkeeping (12k entries) expensive. A caveat/anomaly worth a follow-up, but
  orthogonal to inc-2's transfer-overlap thesis.

## Q2 — Increment-2 sub-levers, ranked against the Q1 breakdown
(a) **Double-buffer look-ahead overlap** (prefetch next layer's weight into a distinct slot while
    current computes): attacks H2D+wait ≈ **3.4%** only, and REQUIRES the no-eviction regime
    (≥2× working-set budget headroom) to avoid the drain — exactly the regime where offload is
    least needed. Expected yield: **near-zero**. Do not build first.
(b) **Bounded staging ring** (replace per-page `alloc_pinned`+copy with reused pinned buffers):
    attacks pinned ≈ **48%**. HIGH yield IF the async path is kept — but the sync path already
    pays 0 pinned, so the simplest fix is "don't stage when you can't overlap." Ring only matters
    if look-ahead (a) is also built. Medium value, coupled to (a).
(c) **Warm host cache of materialized canonical bytes** (keep the dequantized/reordered int4
    canonical bytes in a pinned host buffer; the `weight_offload_cpu` host cache, which stayed 0
    in all runs): attacks materialize ≈ **48%** directly, and once cached the page-in is pure H2D
    (~3%). HIGHEST structural yield; also helps the hits regime. This is the right first lever if
    building anything.

Net: the effective inc-2, if built, is (c)+(b) → "materialize once, stream pure H2D, no per-page
pinned alloc." Look-ahead (a) — the literal #544 double-buffer — is the lowest-yield piece and
must NOT be shipped alone (it would be a ~3% no-op, and re-enabling async without fixing pinned
keeps the regression).

## Q3 — Beneficiary regime (honest strategic check)
Offload only matters for model>VRAM or packing more concurrent state. On 143GB H200, NO on-hand
ONNX model exceeds VRAM (A3B f16 68GB, 27B f16 54GB, deepseek 9GB — all fit). A genuine
beneficiary would be a >143GB model (e.g. a 235B / gpt-oss-120b at f16 ≈ 240GB — but those are HF
safetensors, not ONNX) or high-concurrency KV packing. **Conclusion: today offload's value is
measurement/CI-forcing via budget-cap, not production speedup. Inc-2 is not worth building now.**
Defer until a real >VRAM ONNX target exists; then lever (c) first.

## Q4 — Blast radius / capture interaction
- Byte-identical preserved: all offload runs produced tokens identical to resident
  ([25,21018,11,1246,525,498,3730,3351,30,...]) — weight_paging §9 invariant holds; any inc-2 must
  keep offloaded bytes == resident bytes (levers b/c only change *where/when* canonical bytes live,
  never their value).
- WAR/eviction safety: the eviction compute-drain (`synchronize()` in `admit`, taken only on
  evict) is the correctness guard; a look-ahead into a DISTINCT slot must preserve it (no free of a
  page an in-flight kernel reads). Cost of the drain is <1% — cheap; do not "optimize" it away.
- Capture: offload ⊥ CUDA-graph capture (decode session declines capture when offload is enabled).
  Established + reconfirmed (capture off in every offload run). Inc-2 does not change this; the
  capture loss is a separate, larger fixed cost than any page-in term.

## Plain-text recommendation
DEFER inc-2. The #544 async look-ahead targets H2D (~3%) and is provably low-yield; worse, async
page-in is currently a net regression vs sync in the eviction regime (12.16 vs 15.84 tok/s). No
on-hand model exceeds VRAM, so offload is a CI/forcing tool, not a live perf path. If you want ANY
offload work now, the two honest, cheap wins are: (1) make async page-in **opt-in** (it regresses
the thrash regime), and (2) if a real >VRAM ONNX target appears, build sub-lever (c) warm-host
materialize cache FIRST (attacks the ~48% materialize term), not the double-buffer. I'd rather
defer than ship a ~3% no-op perf PR.

# Scope: native recurrent-state KV lane (#384 "missing recurrent_state")

- Date: 2026-08-01
- By: Cohaagen (EP/runtime)
- Mode: READ-ONLY static analysis on origin/main @ 25d41f40 (post-#572). No build.
- Target unlocked: qwen3.6-27b (and the qwen3.5/3.6 linear-attention "hybrid" class:
  16 GQA layers + 48 linear-attention layers carrying `conv_state` + `recurrent_state`).

## TL;DR — the lane is MOSTLY ALREADY BUILT; the real gap is metadata + a re-probe

The native decode path already models fixed loop-carried recurrent states end-to-end
(load, CUDA binder, CPU binder, per-step in/out swap). My prior 27b bench "native rejects
rank-3 conv_state" was a **self-inflicted overlay bug** — I authored the states into
`io.kv_inputs`/`kv_outputs` (the growable rank-4 KV list) instead of the dedicated
`io.state_pairs` list. Bound through `state_pairs`, the rank-3 states are accepted.

So this is **S–M**, not a new XL lane. The remaining work is (1) metadata plumbing so the
export declares `io.state_pairs`, (2) a re-probe to confirm op coverage after #420, (3)
confirm the Scan-body child session places on CUDA. No new decode loop and (likely) no new
kernels.

## 1. Contract gap — precisely (and what already handles it)

Growable KV (key/value): rank-4 `[batch, heads, seq, head_dim]`, appended along the seq
axis each step. Recurrent state (`conv_state` rank-3 `[batch, feat, window]`,
`recurrent_state`): fixed-size, replaced wholesale each step (state[t] = f(state[t-1], x_t)),
never appended.

Every append-along-seq assumption — and where recurrent states are already exempted:

- **CUDA KV binder** `DecodeCudaState::kv_bytes_per_token` (cuda.rs:816-824): the rank-4/f16
  check (`must be rank-4 f32 or f16`, cuda.rs:832) is **guarded by
  `if fixed_state_inputs.contains(past) { continue; }`** — recurrent states are skipped.
- **CUDA persistent alloc** `persistent_state_shapes(..., fixed: bool)` (cuda.rs:877-889):
  the rank-4 requirement is **only enforced when `!fixed`** (cuda.rs:887). `fixed=true`
  allocates the state at its full static extent; symbolic recurrent dims are rejected with a
  clear "export a static recurrent-state geometry" message (cuda.rs:920).
- **CUDA binding layout** (cuda.rs:1065-1137): `DecodeCudaState` carries an explicit
  `fixed_state_binding_range` (cuda.rs:131); pairs are sorted so fixed states are grouped
  (cuda.rs:1085), growable KV bound with `fixed=false`, recurrent with `fixed=true`.
- **Per-step swap / read_present**: CPU `cpu.rs:328-345` special-cases recurrent outputs —
  wholesale replace, **skips the growable-KV seq-length check** (`is_recurrent_state_shape`
  gate). CUDA replaces via the persistent-binding wholesale tensor swap (load.rs:397-401).
- **seed_prefix / capacity / stride**: load.rs:405-434 folds `state_pairs` into the paired
  lists with an explicit `present_to_past` mapping (`kv_pair_count = kv_inputs.len() -
  state_pairs.len()`), so growable-KV capacity/stride math only runs over the true KV pairs;
  states are seeded at full static extent by `make_empty_input_tensor`.
- **GAP-3 paged mirror**: paging only mirrors the growable KV cache; recurrent states are
  fixed-size persistent bindings (not paged) — no seq-append there to violate. (Confirm no
  paged path tries to page a `fixed_state_inputs` entry; static read suggests it filters
  them out, but this is one line to assert in a test.)
- **attention kernel dispatch**: unaffected — the 16 GQA layers use the normal
  GroupQueryAttention path; the 48 linear-attn layers do their recurrence inside a **Scan**
  body (see §2), not via the attention kernel.

Conclusion: there is **no rank-4 append assumption left unguarded** for declared
`state_pairs`. The contract is implemented; it just requires the states to be declared as
`state_pairs`, which the 27b export does not do.

## 2. Minimal viable support — what's actually missing

### (a) LOAD — metadata authoring / auto-derivation (the #384 gap)
The stock `inference_metadata.yaml` for qwen3.6-27b has **no `io:` block at all** → the
loader can't even resolve `token_input` (3 ports match). The recurrent binder path
(above) only fires when `io.state_pairs` is present (load.rs:406). Two fix options:

- **(a1) Export side (mobius):** emit the `io` block including `state_pairs`. genai-config
  already knows how — `strict_decoder_state` derives `state_pairs`, and
  `compatibility.rs:343,813,1091` writes `io.state_pairs` into the decoder io. So this is
  "route the 27b export through the compatibility path that already emits state_pairs."
- **(a2) Loader side (onnx-genai):** when the yaml omits `io`, auto-derive it from graph
  ports (reusing genai-config's `strict_decoder_state`, which already returns state_pairs).
  Today `native_decode/load.rs` consumes `io.state_pairs` but does NOT self-derive it.

(a2) is the more robust fix (any correctly-structured export just works) and is small —
it wires an existing genai-config derivation into the loader's io-resolution fallback.

### (b) DECODE one step — already correct
Thread state in→out per step, in-place, no seq-append: **already done** (CPU cpu.rs:328;
CUDA persistent fixed bindings + wholesale swap). No new decode code expected.

### Op coverage — LIKELY ALREADY RESOLVED, needs re-probe
The linear-attn math runs as ONNX ops our CUDA EP already covers: `Conv`, `Softplus`,
`Swish`, `Sigmoid`, `RMSNormalization`, `ReduceSum`, **`ReduceSumSquare`** are all in
`CUDA_COVERED_OPS`. Mary's Jul-30 probe hit `ReduceSumSquare: input dtype Float16
unsupported; expected Float32` (96 nodes → CPU → whole-session CPU). **That gap was closed
by #420 "CUDA: support f16/bf16 extended reductions" (landed 2026-07-29 18:50, i.e. around
Mary's build)** — current `reduce.rs:832` accepts `Float32|Float16|BFloat16` for extended
reductions. So the "heterogeneous placement unavailable → CPU" failure was an **op-dtype
gap, not a fundamental placement limitation**, and is probably gone on current main.

### Scan / control-flow — executor-driven, not an EP-claim blocker
`Scan` is NOT in `CUDA_COVERED_OPS` and does not need to be: control-flow ops (If/Loop/Scan)
are executed by the **session executor** (`onnx-runtime-session/src/executor/control_flow.rs`),
which compiles each Scan **body** to a child session/executor. The body's ops are what must
be CUDA-claimable — and (post-#420) they are. Remaining risk: confirm the Scan-body child

# Decision: gemma4 audio-export rank fix (onnx-genai #570)

**Author:** Mary (native-decode/executor + mobius model-export)
**Date:** 2026-08-01
**Scope:** mobius `src/mobius/models/gemma4.py`, `src/mobius/tasks/_gemma4.py`, test

## The rank contract
The gemma4 audio dataflow edge `audio_encoder.audio_features -> embedding.audio_features`
MUST be **rank-2 `[num_valid_frames, text_hidden_size]`** on both ends. onnx-genai
pipeline admission rejects a rank-3 producer against the rank-2 consumer:

```
'audio_encoder.audio_features -> embedding.audio_features' has incompatible ranks:
producer rank 3, consumer rank 2.
```

The `embedding` sub-model consumes rank-2 (`_Gemma4EmbeddingModel`, scatter expects
per-token rows), and the combined-model contract already documents rank-2. The image
edge is already rank-2 (`vision_encoder` flattens batch); no image-side fix needed.

## HF reference semantics
HuggingFace gemma4 selects `audio_features[audio_mask]` — a **boolean mask gather**
that both drops padding frames and flattens the batch axis, yielding rank-2
`[num_valid_frames, hidden]` rows that align 1:1 with audio placeholder tokens before
they are scattered into the language-model embeddings.

## Root cause
The shipped `/home/justinchu/gemma4-e2b-onnx` export (2026-07-22, **0 Compress ops**,
graph ends at the projector MatMul) emits rank-3 `[B, T//4, H]`. It predates PR #419,
which added a flatten+Compress in the **task builder** (`_build_audio`). Current
origin/main therefore already exports rank-2 — but the `_Gemma4AudioEncoderModel`
module itself still returned rank-3 and its docstring claimed rank-3, so the mask-
selection was an un-tested task-level patch that could silently regress, and it
duplicated the compress that `_Gemma4UnifiedAudioEmbedderModel` already does inline.

## Fix (DRY + general)
Moved the mask-selection **into the module** `_Gemma4AudioEncoderModel.forward`:
after the projector it flattens `[B, T//4, H] -> [-1, H]`, then reuses the shared
`_dtype_safe_compress(op, flat, flat_mask, axis=0)` helper (bf16-safe Compress) to
emit rank-2 `[num_valid_frames, H]`, and still returns the `downsampled_mask` for the
`audio_features_mask` diagnostic output. The task builder `_build_audio` now just
adds the module's rank-2 output. Docstrings updated to state rank-2.

This is general: all gemma4 Conformer-audio variants (E2B/E4B and any `-wp-a`) share
`_Gemma4AudioEncoderModel`, so the fix covers the whole class; it also matches the
encoder-free `_Gemma4UnifiedAudioEmbedderModel`, which already emitted rank-2.

## Test (non-vacuous, locks the regression)
`src/mobius/models/gemma4_test.py::TestGemma4AudioEncoderRank`:
- asserts exported `audio_encoder.audio_features` rank == `embedding.audio_features`
  input rank == **2**, and trailing dim == `config.hidden_size` on both ends;
- asserts a `Compress` node exists in the audio graph (the reduction is a real
  mask-select, not a bare reshape that would misalign rows).

## Evidence (code-cited, all in crates/onnx-runtime-session/src/)

1. **Body I/O is host-resident (device→host→device round-trip per step).**
   - `executor/control_flow.rs:270` — `value_tensor` materializes control-flow inputs via `self.ep.copy_to_host(&buffer, &mut bytes)` then `Tensor::from_raw` → a **host** tensor. Every Scan input/state is pulled device→host.
   - `tensor.rs:731-733` — `Tensor::as_bytes` asserts host-accessibility (`host_bytes`), so `scan_slice`/`finish_scan` operate on host bytes.
   - `executor/run.rs:296-302` — the child binds its inputs with `self.ep.copy_from_host(tensor.as_bytes(), buf)` → host→device copy back.
   - Net: the body boundary does device→host (input) + host→device (child bind) + device→host (child output) + host stack + host→device (store) **every decode step**. Each is a stream sync. Any such sync inside `cudaStreamBeginCapture` **aborts** graph recording.

2. **The body runs on a SEPARATE executor with a SEPARATE cache.**
   - `executor/control_flow.rs:197-199` — body executes via `self.compiled[cache_index].exec.run_scoped(&inputs, outer_scope, &ExternalBindings::default())`: a distinct `Executor` (`.exec`), driven with **host tensor `inputs`** and **empty device bindings**.

3. **Parent capture cannot enumerate the child's kernels.**
   - `executor/capture.rs:601-612` (`node_capture_reason`): even if I bypass the `plan_capture_region` structural decline (line 576-584) for single-trip Scan, control falls through to a `KernelKey{ node: plan.node_id, shapes }` lookup in **`self.cache.entries`** (the PARENT cache). A Scan node has **no warmed kernel of its own** → returns `KernelNotWarmed` → still a seam.
   - `executor/capture.rs:689-715` (`collect_segment_kernels`): the capture audit gathers one warmed kernel per plan node from the parent cache keyed by parent `node_id`. The child body's kernels live in the child executor's **own** cache under the **child plan's** node_id space — unreachable from here.

4. **Persistent-output precondition.** `executor/capture.rs:630-639` requires every captured graph output to be a persistent device binding; the child is run with `ExternalBindings::default()`, so its outputs are non-persistent host tensors — disqualified.

## Why this is deep surgery, not a narrow slice

# IMPLEMENTATION (nested child device-graph capture — build + STOP finding)

Built the approved nested-child capture on `feat/27b-scan-capture-1b`. Result: a
**second, deeper STOP** — nested per-node capture-once/replay is **structurally
infeasible with the existing device-graph API** because the graph facility is a
per-EP singleton. The build, evidence, and the safe landing are below.

## Shape-stability finding (STOP-gate #1 cleared — capture-once is viable)
Empirically confirmed (temporary `MARY_SCAN_SHAPE_PROBE`, 27B, removed after):
720 probe lines = **48 nodes × 15 decode steps**; distinct nodes (48) == distinct
(node+shape) combos (48). Every LinearAttention Scan body has ONE stable I/O
shape across ALL decode steps (recurrent state `[1,48,128,128]`; slices
`[1,48,128]×3, [1,48,1], [1,48]`). The recurrent state is fixed-size (O(1)); KV
growth lives only in the 16 GQA layers, not the 48 Scan bodies. So capture-once /
replay-per-step is shape-correct — the child body graph does NOT vary across
steps. (Stored as a repository memory.)

## Nested-capture mechanism (implemented)
Entirely inside the flag-ON, `trip_count==1` inline branch of `exec_scan`
(control_flow.rs) — **no** `plan_capture_region` / `node_capture_reason` /
`collect_segment_kernels` change; the parent Scan stays a structural barrier.
- New flag `ONNX_GENAI_SCAN_BODY_CAPTURE` (default OFF); master gate remains the
  1a `ONNX_GENAI_SCAN_INLINE_SINGLE_TRIP`.
- Per-`CompiledChildPlan` capture slot `ScanBodyCapture { phase, bindings, n_inputs,
  output_specs }` with a state machine `run_body_step`: host-discover geometry →
  allocate persistent `DeviceIoBinding`s (inputs + outputs) → device warmup
  (`run_with_device_bindings`) → `try_capture_with_device_bindings` → replay
  (`replay_device_graph`) thereafter; eager fallback on decline/branch-flip/err.
  Uses ONLY the existing bindings.rs:120-211 API (same one top-level decode uses).
- Observable counters `scan_body_captures/replays/fallbacks` on `ControlFlowStats`
  (+ `ChildExecutorStats`); env trace `ONNX_GENAI_SCAN_BODY_CAPTURE_TRACE`.
- Host-refreshed bindings (each step writes host inputs → replay → reads host
  outputs); NOT the zero-copy device-alias variant — see "why no win" below.

## STOP-gate #2 (the blocker): the device-graph store is a per-EP singleton
`CudaGraphLifecycle` (onnx-runtime-ep-cuda/src/graph.rs:114-122) holds a single
ordered `segments: Vec<CapturedGraph>` **per EP runtime stream**. All 48
LinearAttention child bodies share ONE `Arc<dyn ExecutionProvider>` — each child
`Executor` is built with `self.ep.clone()` (control_flow.rs:131). Therefore:
- `begin_device_graph_capture` **appends** a segment to that one shared list;
- `replay_device_graph` replays the **whole** list (every installed segment);
- `reset_device_graph` clears **all** segments.
There is no per-graph handle. So 48 independent per-node captured graphs cannot
coexist: each node's capture pollutes the shared slot, and whole-graph replay
runs the wrong (last/other-layer) graph. Because all 48 bodies have **identical
shapes**, the mismatch surfaces **no error and no fallback** — it **silently
corrupts** decode output.

### Proof (27B greedy, prompt "The history of computing began", 48 tokens)
Reference (1a) token ids: `[303,279,220,16,24,19,15,82,440,...,13017,13,4213]`.
| Config | flags | tokens | tok/s |
|---|---|---|---|
| A baseline | both OFF | **== reference** ✓ | 6.08 |
| B slice 1a | INLINE=1 | **== reference** ✓ | 5.90 |
| C 1b guarded | INLINE=1, BODY_CAPTURE=1 | **== reference** ✓ | 6.11 |
| C′ unsafe capture | + BODY_CAPTURE_UNSAFE=1 | **DIVERGES** at tok #5, degenerates to repeated `279` | 5.2–5.6 |

The unsafe capture path captured all 48 nodes with **0 fallbacks** (every
LinearAttention body op — Conv/Transpose/elementwise — IS individually
capturable), yet produced garbage — exactly the shared-slot corruption above.

### And it would not win anyway (host-refresh variant)
Even correct, the host-refreshed variant round-trips the recurrent state
(`[1,48,128,128]` ≈ 3 MB) in AND out per node per step: ~6 MB × 48 nodes ≈
**288 MB/step of PCIe traffic**, which dwarfs the per-op dispatch it saves
(C′ measured 5.2–5.6 tok/s, *below* the 6.08 baseline). A net win requires the
**zero-copy device-alias** variant (child I/O bound directly onto the parent's
persistent device buffers, no host round-trip) — which needs a new borrowed
`DeviceIoBinding` constructor + parent-buffer address-stability guarantees.

## Safe landing (what is committed)
The corrupting install/replay is gated behind an explicit, documented spike flag
`ONNX_GENAI_SCAN_BODY_CAPTURE_UNSAFE` (default OFF, "known-incorrect"). The
production flag `ONNX_GENAI_SCAN_BODY_CAPTURE` reaches the body-capture path,
counts a fallback, installs **zero** graphs, and runs the body eagerly →
**byte-exact with 1a**, no regression (6.11 vs 6.08). The full state machine is
retained behind the unsafe flag as the basis for the follow-up.
