### 2026-08-02: Inc-1b decode-inline is now the ONLY path (graph-property-gated); ONNX_GENAI_DECODE_INLINE_SCAN removed
**By:** Cohaagen (EP/runtime performance)

**Verdict up front:** **Size L, bounded, LOW default-path risk → BUILD.** The keep-as-op skip is a general, claim-driven loader hook (default = inline everything, byte-identical to today); dual-domain is additive registration. Supersedes Inc-1b for LinearAttention models. Details + citations below.

## 0. Problem confirmed against the real model (proto probe)
Stock `qwen3.6-27b-int4-cuda/model.onnx`:
- Declares `com.microsoft::LinearAttention` as a **model-local FUNCTION** (inputs `[query,key,value,past_state,decay,beta]`, outputs `[output,present_state]`); its body has **1 `Scan`** plus Transpose(11)/Reshape(7)/Concat(4)/Shape(5)/Tile(2)/Unsqueeze(2)/Constant(7)/Mul/CastLike.
- **48** top-level `LinearAttention` call-nodes. Each node: `q/k/v` dtype = **f16**, `past_state` = f16, attrs `scale=0`, `q_num_heads=16`, `kv_num_heads=48` (**inverse GQA**, kv=3×q), **no `update_rule`** attr (defaults to `gated_delta`).
- The graph's `value_info` (**4164 entries**) carries dtypes/shapes for the LinearAttention I/O boundary tensors.

The loader inlines EVERY model-local function unconditionally (`function_inline.rs:258` `expand_node` -> `instantiate`, driven from `graph_builder.rs:52`), so all 48 calls expand into their Scan-bodies before dispatch. The fused `LinearAttention` kernel — registered + ORT-parity + capture-eligible in ep-cpu (`kernels/mod.rs:516`) and ep-cuda (`kernels/mod.rs:733`, claim gate `provider.rs:332`) — is therefore **dead on this model**. It IS exercised on the Qwen3.5-0.8b split model, which exports LinearAttention as a raw op (no function), confirmed by `qwen35_0_8b_placement_lock.rs`.

## 1. Central design question — where does the keep-as-op decision live?
Constraint: the loader (`onnx-runtime-loader`) inlines at **proto level, before IR build and before EP selection**, and must not depend on ep-cpu/ep-cuda. Two facts unlock a clean, DRY hook:
- (a) The claim `unsupported_reason` for LinearAttention needs only **node attributes + q/k/v dtypes** (`ep-cuda/kernels/linear_attention.rs:235`; no shapes) — and those dtypes are in `value_info` at proto level.
- (b) The EP already exposes a node-level claim gate: `ExecutionProvider::supports_op(op:&Node, opset, shapes, input_dtypes, layouts) -> KernelMatch` (`ep-api/provider.rs:395`). LinearAttention's gate ignores `shapes`/`layouts`, so it answers correctly with `&[]` placeholders.

**No shape-inference risk.** `onnx-runtime-ir` has NO per-op shape-inference pass (`shape.rs` is just `Shape`/`Dim` types); Values are seeded from the export's `value_info`. Keeping LinearAttention as an op leaves its I/O shapes intact from `value_info` (the 0.8b op-path is the standing precedent). So downstream resolution, KV binding, and capture are unaffected.

### Chosen design (general, claim-driven, default-preserving)
**Loader (Part 1 hook):** add a predicate-carrying variant
`load_model_bytes_with_weights_filtered(bytes, dir, keep_as_op: Option<&dyn Fn(&ir::Node, u64 /*opset*/, &[DataType]) -> bool>)`
threaded into `inline_functions` -> `expand_node`. When a node matches a declared function AND `keep_as_op(node, opset, input_dtypes)` returns true, **emit the node unchanged instead of instantiating**; else inline exactly as today. The loader converts the proto call-node to a lightweight `ir::Node` (reusing existing node conversion) and resolves `input_dtypes` from `value_info` -> graph inputs -> initializers; **if a dtype is unknown, treat as NOT claimed -> inline** (safe fallback, preserves behavior). Default `load_model*` passes `None` -> inline everything -> **byte-identical to current main**. This is the general "keep-as-op iff a kernel claims it, else inline" policy — not hardcoded to any op name.

**Session wiring:** select the EP **before** load (EP selection is device-only, `lib.rs:739`; today it runs at `lib.rs:693` after load — the move is safe: `fp16_decode`/`optimize_graph` don't need the EP). Build the closure `|node, opset, dtypes| matches!(ep.supports_op(node, opset, &[], dtypes, &[]), KernelMatch::Supported{..})` and pass it into the new loader variant. Non-`from_dir` load paths keep passing `None`.

**Why not a post-build re-fusion / IR-level inliner:** re-fusing an already-inlined Scan is fragile and there is no IR-level function inliner. Deciding at proto time (before inlining) with the EP claim is strictly simpler and reuses the existing `supports_op` gate (DRY).

## 2. Part 2 — dual-domain (com.microsoft + standard ONNX, onnx/onnx#7689)
The registry normalizes domains (`ep-api/registry.rs` `norm_domain`), collapsing `""`/`ai.onnx`, but `com.microsoft` is distinct. To serve BOTH with the SAME kernel:
- **ep-cuda** `kernels/mod.rs:733`: add `reg.register(OpKey::new("LinearAttention", "", 1), LinearAttentionFactory{..})` alongside the `com.microsoft` entry; **claim gate** `provider.rs:332`: widen `op.domain == "com.microsoft"` to also match the default domain (`op.domain.is_empty() || op.domain == "ai.onnx"`) so `unsupported_reason` runs for both.
- **ep-cpu** `kernels/mod.rs:516`: add the `OpKey::new("LinearAttention","",1)` registration. CPU claims purely by registry (`provider.rs:128`, no per-config gate), so registration alone suffices.
- **Schema reconciliation:** the mobius header (`functions/linear_attention.py`) cites onnx/onnx#7689 as "same naming convention" — attrs `q_num_heads`, `kv_num_heads`, `scale`, `update_rule` and the `[q,k,v,past_state,decay,beta]`/`[output,present_state]` I/O are identical across domains; `scale=0` resolves to `1/sqrt(d_k)` in both. **One kernel serves both**; no attribute/opset divergence found. (If a future standard-schema revision renames an attr, reconcile in the claim/parse; none needed today.)

## Addendum — 2026-08-02: policy clarification from Justin (generalize Part 1) + Inc-1b composition

**By:** Cohaagen. **Status:** Confirmed the shipped design (PR #594) already satisfies the clarified policy; no code change required. Verification below.

### The rule, restated (Justin): skip inlining a model-local function call whenever the ACTIVE EP has a registered kernel that CLAIMS that node (factory registered for op+domain AND claim gate returns None for this node). Else fall back to inlining. General, DRY, registry-driven — LinearAttention is just the first beneficiary.

### The shipped hook is already exactly this — no op-name list in the loader
- The loader's keep-as-op decision is made by a caller-supplied predicate `KeepAsOp = dyn Fn(&ir::Node, u64 /*opset*/, &[DataType]) -> bool`, applied in `expand_node` to **every** node that matches a declared function (`function_inline.rs`), with no reference to any specific op name/domain. Verified: `git grep -n "LinearAttention|\"Scan\"|com.microsoft"` over `onnx-runtime-loader/src/` and `onnx-runtime-session/src/lib.rs` returns only pre-existing, unrelated code (EPContext handling; the pre-existing `If|Loop|Scan` control-flow helper at loader `lib.rs:592`). The keep-as-op path adds zero op-name gating.
- The session builds the predicate from the **active EP's own claim path**: `|node, opset, dtypes| ep.supports_op(node, opset, &[], dtypes, &[]).is_supported()` (`onnx-runtime-session/src/lib.rs` `build()`). `ExecutionProvider::supports_op` first checks the kernel **registry** (`registry.supports(op_type, domain, opset)` — is a factory registered?) and then runs that op's **claim gate** (`unsupported_reason`/equivalent). So the predicate returns true **iff a backend kernel is registered for the op+domain AND claims this node** — precisely the rule. Any fused op we register later automatically gets kept-as-op with no loader edit.
- **Fallback preserved:** predicate false (no kernel, unsupported config, or unresolved dtype -> `DataType::Undefined` -> gate declines) -> inline the function body, byte-identical to today. Default `load_model*` passes no predicate -> inline everything.

### Why this is the least-invasive general design (justification requested)
The loader inlines at **proto level, before EP selection**, and must not depend on ep-cpu/ep-cuda. Rather than move inlining after EP selection (large refactor, and shape/KV derivation assume post-inline IR) or build a separate op registry inside the loader (duplicates the EP's claim logic — not DRY), we **inject the EP's existing claim decision as a callback**. The loader stays EP-agnostic; the session (which already selects the EP) supplies the closure. This reuses the single source of truth (`supports_op` = registry + claim gate) and touches only the inline seam + one session wiring point.

### Inc-1b composition — CONFIRMED NO CONFLICT (Inc-1b inline-scan going DEFAULT-ON separately)
The two levers are orthogonal and compose cleanly:
- **On 27b (and any LinearAttention model):** after this change the 48 LinearAttention calls are kept-as-op and dispatch to the fused kernel -> **0 Scans** for those layers (verified: `stock_export_keeps_linear_attention_as_fused_op_with_zero_scans` prints `LinearAttention fused ops=48, Scan ops=0`). With no Scan to route, Inc-1b's `inline_single_trip_scan_bodies` / decode-inline sibling is a **structural no-op there** regardless of whether its flag is default-ON — nothing for it to transform. So flipping Inc-1b default-ON does not change 27b behavior post-this-change.
- **On genuine Scan/Loop models we have NO fused kernel for:** the keep-as-op predicate declines (no registered claiming kernel) -> the function/Scan inlines as today -> Inc-1b (now default-ON) still optimizes those single-trip decode Scans. Its benefit is retained exactly where it matters.
- **Ordering:** keep-as-op happens at load/inline time (before the executor); Inc-1b's inline-scan transform runs later in the session/executor over whatever Scans remain. Since keep-as-op removes only Scans that became fused ops (never leaves a partially-inlined Scan), Inc-1b sees a clean graph. No double-transform, no contention.

**Net:** keep-as-op (fused dispatch) and Inc-1b (generic single-trip Scan inline) are complementary — one removes Scans we can fuse, the other optimizes Scans we can't. Both can be default-ON without interference.

## Addendum 2 — 2026-08-02: architecture steer "inlining must be the EP's job" (defer inlining to EP/partition time). SCOPE-FIRST; verdict at end.

**By:** Cohaagen. **Steer (Justin):** the keep-vs-inline decision must be OWNED by the EP, ideally by DEFERRING function inlining to where the EP/assignment is known (session partitioning), not decided at loader proto-time. ### Where the pipeline actually stands (cited against main `1ba215ee`)
- Function inlining is **proto-level and EP-agnostic**, run inside the loader before IR build: `graph_builder.rs:52` `inline_functions(model)` (only inliner in the tree; grep confirms no IR-level inliner — `function_inline.rs` operates on `ModelProto`/`NodeProto`).

So function nodes don't crash it, but their outputs go **shape-unknown** unless a custom handler exists.
- **Load-time validation** (`validate_ir`, `validate_loaded_model`) also runs in the loader on the inlined graph.
- **Per-node EP capability** (`ep.supports_op`) is queried MUCH later, at **executor build / kernel-cache** time: `executor/build.rs:164,292`, `executor/kernel_cache.rs:130` — after load, after EP is known.

### The two designs
**(b) — SHIPPED in PR #594 (EP-decision via injected predicate at the existing inline seam).** The loader stays EP-agnostic; the session selects the EP first and passes `keep_as_op = |node,opset,dtypes| ep.supports_op(node,opset,&[],dtypes,&[]).is_supported()`. Claimed function-calls are kept as ops; everything else inlines exactly as today. Reuses the EP's existing claim machinery (registry + `unsupported_reason`), no duplicated op list, general to any fused op, default byte-identical, 27b oracle PASS. The *decision* is EP-driven; the *mechanism* remains one proto-level pass. For the single-EP session this IS "the EP owns the decision."

**(a) — Justin's steer (defer inlining to session/partition time, EP owns it structurally).** The loader stops inlining; function nodes survive into the session; at capability-query/partition time each EP claims the function-ops it implements and UNCLAIMED functions are inlined THEN, with shape/validation re-run on the exposed bodies.

### Layering issues for (a) — enumerated honestly
1. **No IR-level inliner exists.** (a) needs inlining to happen post-IR-build (in the session), so it requires a **new IR-level function inliner** reimplementing the proto inliner's subtle logic against `ir::Graph`: fresh `ValueId` minting, attribute/ref-attr binding, boundary `Identity` aliases, name-collision freshening (the "BUG 3/BUG 4" cases), nested-subgraph recursion, opset-import merging. This is itself M–L and correctness-critical.
2. **Shape inference is a loader stage, run pre-session.** Deferring inlining forces either (i) run shape-infer in the loader on the un-inlined graph (function outputs symbolic) and **re-run** shape-infer in the session after the fallback inline, or (ii) **move shape inference into the session** after inlining. Either restructures the load/session boundary — the session currently receives a fully-shaped IR graph and many downstream stages assume that.
3. **Validation** (`validate_loaded_model`/`validate_ir`) similarly assumes a post-inline graph; must be deferred or re-run on injected bodies.
4. **Kernel assignment assumes every node is a dispatchable op.** A surviving function node has no kernel; the session must inline unclaimed functions BEFORE kernel-cache build, then re-shape/re-validate the injected subgraph — a new session-side pass with ordering constraints.
5. **Multi-EP hetero (Justin flagged this).** A function claimed by EP-A but placed on an EP-B partition that does NOT claim it must be inlined for that instance and the body **re-partitioned** — potentially iterative (inline → re-place → maybe inline again). This interleaves inlining with the `hetero.rs` union-find placement machinery — i.e. it **touches the shared partition layer**.
6. **Capture (#443/#543).** Capture segment planning runs on the final assigned plan; it's only safe if inlining reaches a fixpoint BEFORE capture. Deferred/iterative inlining adds a new ordering invariant to protect the capture layer.
7. **Weights/name_map.** The weight `name_map` is minted at loader graph-build keyed to node outputs; deferring when function-body internal names are created shifts weight binding timing — must be re-verified.

### Size + risk
**Design (a) = L/XL.** It requires a new IR-level inliner **plus** restructuring the load→session boundary (shape-infer/validation), **plus** interleaving inlining with capability query and (for correctness in the general multi-EP case) with `hetero.rs` partitioning, **plus** a new capture-ordering invariant. It directly touches the shared **shape**, **partition**, and **capture** layers Justin named as stop-conditions. Blast radius spans loader, session build, executor build, hetero, and capture — well beyond the LinearAttention goal.

### Optional bounded middle — (b′), if we want the decision to be *explicitly* EP-owned without the deferral
Promote the shipped predicate to a first-class `ExecutionProvider` trait method, e.g. `fn keeps_function_op(&self, node:&Node, opset:u64, dtypes:&[DataType]) -> bool` with a default impl of `self.supports_op(...).is_supported()`. The session calls `ep.keeps_function_op(..)` instead of an ad-hoc closure. This makes "the EP owns the decision" explicit and overridable per-EP, while keeping the mechanism at the existing single-pass inline seam — **S/M, zero shape/partition/capture risk**, default byte-identical. It does NOT defer inlining (so it does not address the forward-looking multi-EP "different EPs claim differently" case), but it is the least-invasive way to genuinely put the choice in EP hands today.

- `function_inline.rs` defines `KeepAsOp` as a predicate over a lightweight `Node`, effective opset, and input dtypes (`crates/onnx-runtime-loader/src/function_inline.rs:70-80`). It builds a filter from merged opsets and top-level value types (`function_inline.rs:231-246`).
- When a proto node matches a model-local function, `expand_node` keeps it if `filter.should_keep(node)` is true; otherwise it calls `instantiate` to inline (`function_inline.rs:395-447`). Kept nodes still have graph-valued attributes recursively processed (`function_inline.rs:412-424`, `452-470`).
- Full inlining remains the byte-identical fallback: `inline_functions` delegates to `inline_functions_impl(model, None)` (`function_inline.rs:196-216`), which clears `model.functions` after expansion and merges opset imports (`function_inline.rs:269-276`).

### After load
- After loading, session build may apply fp16 decode rewrite (`lib.rs:701-725`) and general optimizer passes (`lib.rs:727-728`).
- `InferenceSession::from_parts` computes IO metadata and then builds the executor (`lib.rs:967-1006` and downstream executor build).
- `Executor::build` calls `build_with_cuda_requirement`, which immediately calls `place_graph` before materializing initializers or compiling kernels (`crates/onnx-runtime-session/src/executor/build.rs:419-442`).
- `place_graph` validates control-flow signatures, topological order, and single-EP support, then runs EP-scoped passes. For CUDA declines it can revert and replace the entire EP with CPU fallback (`executor/build.rs:720-756`). This is not true heterogeneous assignment; it is whole-session selected-EP-or-CPU fallback.

### Heterogeneous planner / assignment (currently separate)
- `crates/onnx-runtime-session/src/hetero.rs` is a correctness-first heterogeneous planner. It assigns every node to the highest-priority provider whose `supports_op` claims it, partitions assigned nodes into convex claims, and plans transfers (`hetero.rs:1-18`).
- `ProviderPlacement` stores per-provider identity and provider handles (`hetero.rs:59-70`); `HeterogeneousPlan` stores partitions, transfers, and `node_placement` (`hetero.rs:103-112`).
- `assign_nodes` is the actual assignment step: for each node, compute opset + shapes/dtypes/layouts and pick the first provider whose `supports_op` is supported (`hetero.rs:223-258`).
- `provider_partitions` then wraps each provider in `AssignedOracle` so `query_capabilities` only claims nodes assigned to that provider (`hetero.rs:260-296`).
- `plan` calls `assign_nodes`, builds provider partitions, orders them, and plans transfers (`hetero.rs:410-455`).
- `execute` extracts each partition into a runnable subgraph and builds a normal `Executor` for the assigned provider (`hetero.rs:462-620`).

### Control-flow / subgraph bodies
- Loader stores graph-valued attributes in `Graph.subgraphs` so validation/traversal can reach them (`graph_builder.rs:216-245`), and `convert_attribute` recursively builds subgraphs (`graph_builder.rs:389-397`, `442-445`).
- Function inlining already recurses into control-flow subgraphs before IR construction (`function_inline.rs:39-44`, `452-470`) and applies scope-aware capture renaming (`function_inline.rs:717-780`).
- At execution time, control-flow bodies are compiled lazily as child executors using the same `Arc<dyn ExecutionProvider>` as the parent (`crates/onnx-runtime-session/src/executor/control_flow.rs:9-15`, `80-126`, `520-538`). Thus today subgraph bodies are not independently hetero-partitioned; they inherit the parent executor EP and call `Executor::build` recursively.

### Confirmed order / gap
The current #594 order is:

`select one EP -> load proto -> keep/inline function calls using that one EP predicate -> build IR -> optimize -> Executor::place_graph / hetero::plan assignment (if used)`.

So the gap is real: a kept function op can survive because EP-A claimed it at load time, but a later heterogeneous assignment is allowed to choose EP-B by its own priority/support result. If EP-B does not support that fused function op, either planning rejects a graph that could have run via the function body, or a stale/mismatched placement can mis-dispatch. The loader has no assignment context and cannot make the final decision.

## 2. Chosen relocation design

### Recommendation: fusion of inline + hetero partition as a bounded fixpoint
Do not put op knowledge in the loader and do not hardcode `LinearAttention`. Add a partition-time legalization loop owned by the heterogeneous planner:

1. Preserve #594's load-time filtered keep for the common single-EP path. That keeps the existing single-EP perf win and avoids extra work for default sessions.
2. For heterogeneous planning, carry enough function metadata past load to legalize kept calls later. Concretely, introduce a small `FunctionLibrary` artifact from the loader alongside `Graph`/`WeightStore`, containing parsed `FunctionProto`s, merged function opset imports, and an IR/proto-level expansion service shared with `function_inline`.
3. Change hetero planning from one-shot `assign_nodes(graph, providers)` to:
   - assign current graph nodes by provider priority;
   - scan assigned nodes that are model-local function calls kept as ops;
   - for each such node, ask the **assigned** provider's `supports_op(node, effective_opset, shapes, dtypes, layouts)`;
   - if supported, keep it;
   - if unsupported, inline exactly that call into the graph using the shared inliner, preserving ONNX function semantics;
   - re-run shape inference for the edited region/graph;
   - repeat assignment until no assigned kept function op needs expansion.
4. Then run convex partitioning and transfer planning on the legalized graph.

This is a fixpoint rather than a blind second pass because inlining a function can expose nested function calls. Some nested calls may be claimed by an EP and kept; others must inline depending on the provider they are actually assigned to. A fixpoint makes the invariant simple: after planning, every node assigned to an EP is either not a model-local function call or is supported by its assigned EP.

### Why not a pure second pass?
A single post-assignment pass that inlines mismatches and then re-runs partition is the right phase-1 implementation. Architecturally, it should be expressed as the first iteration of a fixpoint (`assign -> legalize -> changed?`) so nested functions and newly exposed ops do not become phase-2 rework.

### Where the code should live
- Keep proto-level expansion mechanics DRY in `onnx-runtime-loader::function_inline`; extract reusable expansion primitives from `instantiate` / `inline_subgraph_attrs` rather than duplicating rename/attribute-binding logic.
- Put assignment-time policy in `onnx-runtime-session::hetero`, because only the planner knows the assigned provider.
- Add a small IR rewrite helper (likely in `onnx-runtime-ir` or loader-owned `FunctionLibrary`) that can splice one function call into an existing IR `Graph`. If initial implementation is faster at proto-level, load hetero sessions through a retained proto + function library and rebuild the graph after legalization; but the long-term API should not force every planner iteration through protobuf decode.

### Function-call identity in IR
A kept node must be recognizable as a model-local function call. Options:
- Preferred: store function library keyed by `(domain, op_type/name, overload)` and add `Node.overload` or a `model_function_key` metadata attribute at graph build. Current IR `Node` has domain/op_type/name/version/attributes; overload is not visible in the viewed lines, so this is likely a small IR metadata addition.
- Acceptable phase-1: only treat a node as legalizable if `(domain, op_type)` uniquely maps to one model-local function and no overload ambiguity exists; error with a clear diagnostic otherwise. This avoids semantic ambiguity while keeping the first slice small.

### Nested functions
The legalization loop must use the same recursion and recursion-cycle guard already in `function_inline` (`function_inline.rs:475-641`). After inlining one call, newly inserted body nodes are ordinary nodes. If any body node is itself a kept function call, the next assignment/legalization iteration handles it. True recursive functions remain rejected exactly as today.

### Subgraphs / control flow
- Top-level hetero planning must recurse through `Graph.subgraphs` and legalize each body. Today subgraphs are compiled as child `Executor`s with the parent's single EP (`control_flow.rs:520-538`), so a complete hetero design needs `ChildExecutor` to carry either (a) the provider list and legalized hetero plan for that body, or (b) the single assigned provider when the control-flow op itself executes on one provider.
- Phase-1 conservative behavior: legalize subgraphs with the same provider set and then compile child bodies with the assigned provider path that can run every body node. If no single assigned provider can run a body after legalization, mark that control-flow node/region ineligible for hetero execution and fall back to all-inlined CPU/reference for the body. This preserves correctness while deferring nested hetero execution.
- Long-term: make child execution mirror top-level hetero planning (`plan_subgraph` + `execute_subgraph`) so If/Loop/Scan bodies can split across providers too.

### Capture eligibility / device capture
Inlining a kept fused op can expand one capture-eligible leaf into multiple primitive ops, or vice versa. Therefore capture analysis must run after legalization/partitioning, not before it. If a partition is rewritten, invalidate `GraphViewCache`, kernel cache entries, capture segmentation, and any device-graph schedule keyed by old node ids. This is consistent with current executor ordering where placement precedes materialization/compile (`executor/build.rs:419-442`).

### IO/value wiring correctness
Use the existing inliner semantics as the source of truth:
- formal inputs/outputs are remapped positionally;
- internal values get globally fresh names;
- pass-through formal outputs synthesize boundary `Identity` nodes;
- `ref_attr_name` attributes bind at all depths;
- subgraph captures are renamed scope-aware and subgraph locals shadow outer names (`function_inline.rs:536-641`, `643-714`, `717-780`).
For IR-level splicing, preserve the same invariants with `ValueId` remaps rather than string remaps, and immediately run graph validation + shape inference on the rewritten graph before re-assignment.

### Generality / DRY requirements
- No per-op names, no model-specific paths, no CUDA/CPU special cases.
- All decisions are `(assigned_ep, node, opset, shapes, dtypes, layouts, function_library)`.
- A non-function op unsupported by every provider remains a normal unsupported-op error.
- A function op unsupported by its assigned provider is not an error until its inlined body also cannot be assigned anywhere.

## 3. Correctness invariant and proof plan

### Invariant
After heterogeneous legalization reaches a fixpoint:
1. Every executable node in every graph/subgraph is assigned to an EP whose `supports_op` accepts it at the effective opset and inferred shape/type/layout metadata.
2. Any model-local function call not accepted by its assigned EP has been replaced by the exact ONNX function body expansion.
3. Therefore hetero execution is semantically equivalent, and for deterministic kernels byte-identical, to the all-inlined fallback for any provider assignment.

### Proof: hetero byte-identical fallback
- Differential test each legalizing rewrite against `inline_functions(model)` / unfiltered load: run the original all-inlined graph on CPU and the hetero-legalized graph with forced provider split; compare output bytes.
- Mutation: make the fake accelerator claim the fused function at load but decline it at assigned-provider legalization; without legalization the test must fail (unsupported/misdispatch), with legalization it passes and the final graph contains primitive body ops.
- Validate graph structure after each rewrite: SSA, no producer-less outputs, topological order, inferred shapes, and no unresolved function calls except those supported by their assigned EP.

### Proof: single-EP perf preserved
- The existing single-EP load path remains #594: select EP before load, keep function call if that EP claims it (`lib.rs:626-647`). No hetero fixpoint runs for single-EP sessions.
- Add/keep a test that a `LinearAttention` model-local function call is retained as `com.microsoft::LinearAttention` when the selected EP claims it, and that the fused kernel dispatches. This guards against accidentally reverting to unconditional inlining.

Smallest safe increment that closes the correctness hole:

# Root cause: Qwen3.6-35B-A3B admission fails — PackedMultiHeadAttention "6 inputs vs 5 declared"

**Author:** Cohaagen (EP/runtime)
**Date:** 2026-08-03
**Status:** Diagnosis complete (READ-ONLY, no PR yet)
**Verdict:** **(A) mobius export bug.** onnx-genai's loader is spec-correct.

---

## TL;DR

The `vision_encoder` `com.microsoft::PackedMultiHeadAttention` node has **6 inputs**
(`query, key, value, ""(bias absent), token_offset, cumulative_sequence_length`),
which is **valid** per ORT's contract (op takes 6–7 inputs). But mobius exports a
**model-local ONNX function** fallback for `PackedMultiHeadAttention` whose formal
signature declares only **5 inputs** — it **omits the `bias` slot**. onnx-genai's
function-inliner correctly refuses to bind a call that passes more actuals (6) than
the function declares formals (5), so admission fails before load. Fix is one line of
signature in mobius; do NOT change onnx-genai.

---

## 1. The real op contract

`com.microsoft::PackedMultiHeadAttention` — ORT `docs/ContribOperators.md`:

> **Inputs (6 - 7)**
> 1. `query` (required)
> 2. `key` (optional)
> 3. `value` (optional)
> 4. `bias` (optional) — `(hidden + hidden + v_hidden)` projection bias
> 5. `token_offset` (required)
> 6. `cumulative_sequence_length` (required)
> 7. `attention_bias` (optional)

**Minimum valid arity is 6, max is 7.** Because `token_offset`/`cumulative_sequence_length`
are positional slots 5 and 6, the optional `bias` slot 4 must be *present* (as an
absent/empty input `""`) — you cannot drop it. So a **6-input** node
`(query, key, value, "", token_offset, cu_seqlens)` is the correct minimal call, and
that is exactly what mobius emits. **6 inputs is VALID.**

## 2. Where "5 declared" comes from (mobius, not onnx-genai)

onnx-genai has **no** native `PackedMultiHeadAttention` kernel, schema, or shape-inference
handler (grep of `crates/` finds zero references outside docs). Admission therefore relies
on inlining the **model-local function** that mobius ships in `model.functions`.

That function is defined in mobius and declares only **5** formal inputs (verified by
building it):

```
com.microsoft::PackedMultiHeadAttention
FORMAL inputs (5): ['query', 'key', 'value', 'token_offset', 'cumulative_sequence_length']
                                          ^^^ 'bias' is MISSING here
```

- `mobius/src/mobius/functions/packed_multi_head_attention.py:156-172` — `build_function(...)`
  inputs list `[query, key, value, token_offset, cumulative_sequence_length]` (no `bias`).
- `.../packed_multi_head_attention.py:67-74` — `body(op, query, key, value, token_offset, cumulative_sequence_length)` (no `bias` param).

Both mobius **call sites** emit **6** inputs (with `None`/absent bias in slot 4):

- `mobius/src/mobius/components/_qwen3_vl_vision.py:252-263` — `_emit_packed_mha`:
  `op.PackedMultiHeadAttention(query, key, value, None, token_offset, cu_seqlens_int32, ...)`
- `mobius/src/mobius/rewrite_rules/_packed_attention.py:169-180` — `BlockDiagonalToPackedMHA.rewrite`:
  `op.op("PackedMultiHeadAttention", q, k, v, None, token_offset, cu_seqlens_i32, ...)`

So the **call node (6 inputs) ≠ the function it resolves to (5 formals)**.

## 3. The exact onnx-genai site enforcing 5 (and why it is CORRECT)

`crates/onnx-runtime-loader/src/function_inline.rs:329-339`:

```rust
// Arity: passing *more* actuals than the function declares is illegal;
// passing fewer is allowed (trailing optionals omitted, mapped to absent).
if call.input.len() > func.input.len() {        // 6 > 5  -> reject
    return Err(LoaderError::FunctionArityMismatch {
        function: fmt_key(&key), node: node_label(call),
        kind: "input", formal: func.input.len(), actual: call.input.len(),
    });
}
```

Error text (`crates/onnx-runtime-loader/src/error.rs:170-183`, `FunctionArityMismatch`):

> "...supplies **6** input(s) but the function declares only **5**. RULES #1: a function
> call may omit trailing optional inputs but must not supply more than are declared."

This is **spec-correct ONNX semantics**: an ONNX function call may omit *trailing* optional
inputs, but must never pass *more* actuals than the callee declares formals. The "5 declared"

**Root cause (confirmed in source):** `reduce_t`
(`crates/onnx-runtime-ep-cuda/src/cudnn/mod.rs:433-468`) builds the cuDNN reduction
descriptor via `create_reduction_no_indices::<T>()`, and cudarc passes `T::DATA_TYPE` as
the reduce **compute type** (`cudarc-0.19.8/src/cudnn/safe/reduce.rs:77`). For F16/BF16
that sets `reduceTensorCompType = CUDNN_DATA_HALF/BF16`, which `cudnnReduceTensor`
**rejects** — cuDNN requires **`CUDNN_DATA_FLOAT`** compute type for half/bf16 I/O. The
F32 arm works; the F16 (mod.rs:417-419) and BF16 (mod.rs:420-426) arms do not. Meanwhile
`reduce_float` (`standard_claims.rs:799`) **claims** f16/bf16 `ReduceSum`, so the node is
placed on CUDA and then fails at execution — a claim/runtime mismatch.

**Proposed fix (single location, no PR opened per instructions):**
`crates/onnx-runtime-ep-cuda/src/cudnn/mod.rs` `reduce_t` — for f16/bf16 tensor data,
create the reduction descriptor with **f32 compute type** and pass **f32 `alpha/beta`**
(`1.0f32/0.0f32`) while keeping the f16/bf16 tensor descriptors + device buffers. cudarc's
type-coupled safe `ReduceTensor<T>`/`create_reduction_no_indices::<T>` binds comp-type to
the I/O `T`, so the fix must set comp-type independently — e.g. call
`cudarc::cudnn::result::{set_reduce_tensor_descriptor(desc, op, CUDNN_DATA_FLOAT, ...),
get_reduction_workspace_size, reduce_tensor(...)}` directly (unsafe FFI) with f16/bf16
tensor descriptors and f32 scalars. Add a GPU parity case: fp16 `ReduceSum`/`ReduceMean`
[1,5,8]->[1,5,1] vs f32 oracle.

Per task instructions I **stopped at the report** rather than landing this EP change
(each validation reload is ~30–40 min; the fix is unsafe cuDNN FFI needing review).

## What shipped

Two bugs that jointly blocked a native GPU decode throughput number for
Qwen3.6 35B-A3B, fixed together in one PR.

### BUG 1 — cuDNN reduce compute-type (primary; blocked GPU decode)

Root cause: cudnnReduceTensor rejects a half/bf16 reduceTensorCompType with
CUDNN_STATUS_NOT_SUPPORTED (reproduced on cuDNN 9.10 and 9.20). The CUDA EP
built the reduction descriptor via cudarc's create_reduction_no_indices::<T>,
which sets reduceTensorCompType = T::DATA_TYPE. For F16/BF16 that yields
CUDNN_DATA_HALF / CUDNN_DATA_BFLOAT16, which cuDNN refuses — so every f16/bf16
ReduceSum/ReduceMean placed on CUDA failed at execution, despite
standard_claims claiming f16/bf16 support (claim/runtime mismatch). Repro node:
decoder/model/layers.0/mlp/ReduceSum_node_121 (Float16 [1,5,8] -> [1,5,1]),
the MoE-router weight-normalization reduce.

Fix:
- f16: reduce through cuDNN with an f32 compute type via the raw cuDNN FFI
  (cudarc::cudnn::result::*): keep f16 tensor descriptors + device buffers, but
  build an f32 reduction descriptor and pass f32 alpha/beta. cudarc's safe
  ReduceTensor<T> couples comp-type AND alpha/beta scalar type to I/O T, so it
  cannot express "f32 comp + half I/O + f32 scalars". This is exactly ONNX
  ReduceSum/ReduceMean semantics for half (accumulate f32, cast back to half).
- bf16: cuDNN cannot reduce bf16 AT ALL — it rejects a bf16 tensor even with an
  f32 comp type (verified empirically on H200: byte-identical raw path passes
  for f16, fails for bf16). So bf16 ReduceSum/ReduceMean routes to the existing
  typed NVRTC block reduction, which already accumulates in f32. The base
  sum/mean/max/min kernel was templatized per dtype (f32/f16/bf16), reusing the
  crate's f32-widening load/store helpers. The cuDNN backend's bf16 arm is now a
  defensive guard. This also fixes a latent no-op stub that silently skipped
  non-f32 reduce when cuDNN was unavailable.
- f32 fast path unchanged.

General: routes through the shared reduce dispatch, covering all reduce ops
(Sum/Mean via cuDNN-or-typed, Max/Min via typed), not just the one repro node.

### BUG 2 — native decoder device wiring (secondary; forced CPU path)

build_native_pipeline_decoder selected the decoder device only from env
ONNX_GENAI_PIPELINE_NATIVE_DECODER_DEVICE (default CPU) and ignored
EngineConfig.native_device, so --ep cuda silently decoded on CPU. Fix: honor
config.native_device when the env var is unset; env var still wins if set
(override / back-compat). Resolution refactored into pure functions and
unit-tested.

| count | op | seam reason |
|------:|----|-------------|

## Root cause — exact code sites
`crates/onnx-runtime-ep-cuda/src/kernels/reduce.rs`:
- `ReduceKernel::capture_support` (line ~1184) declines unless `last_call_capture_safe` is set.
- `last_call_capture_safe` is **only ever set to `true` in the Int64 path** (line ~999, via the
  `ReductionMetadataCache` that caches device base/delta/axes buffers — "the seam Marsten identified",
  comment ~712). **The float paths never set it**, so every float `ReduceSum` declines capture:
  - **fp16/f32 → cuDNN branch (lines ~949–970):** computes via `cudnn().reduce(...)`, then an
    **unconditional `self.runtime.synchronize()`** (line ~969) and returns without marking capture-safe.
    `CudnnBackend::reduce_t` / `reduce_raw_f32_comp` (`cudnn/mod.rs` ~445–543) **`alloc_zeros` a fresh
    workspace every call** → device allocation is illegal during capture ⇒ fundamentally non-capturable
    as written. This is the branch the 35B fp16 MoE reduces take.
  - **bf16 / cuDNN-absent → NVRTC block branch (lines ~1003–1029):** per-call `alloc_raw` + `htod` of
    base/delta + `free_raw` + per-call `synchronize` (line ~1161) ⇒ also non-capturable, never marks safe.

Secondary (do not move the needle, but real):
- `linear_attention.rs::execute` (~330, sync ~625) declares `CaptureSupport::Supported` but **aborts
  device-graph recording on the 35B hybrid shape**, so the executor quarantines the op-type
  (`executor/capture.rs` ~552–565) → all 30 LinAttn layers become eager seams. On 27B this path captured
  (48 fused ops, 0 seams per #594). 35B-specific regression — likely a per-call alloc/host-read/sync under
  a shape/config only present here (hd256 / rank-3 mRoPE). Worth a separate bisect.
- `movement.rs` Split (~231 sync, capture_support ~527): dynamic split sizes read on host + trailing
  synchronize; would be capturable if the constant split sizes were warmed.
- Norm/gate pointwise (`Sqrt/Div/Mul/Sigmoid/ReduceSumSquare`) report warmed-signature mismatch — symptom
  that the warmup capture signature differs from steady decode for these; secondary to the reduce swarm.

## Recommended bounded lever (NOT shipped this pass — see disposition)
**Lever A — make float (fp16/bf16) `ReduceSum` capture-eligible**, mirroring the existing, tested Int64
`ReductionMetadataCache` pattern: cache device-resident reduce metadata (and, for the cuDNN branch, the
cuDNN workspace) keyed by (shape, reduce-mask, keepdims); reuse across calls; gate `synchronize()` on
`!capturing`; set `last_call_capture_safe = true` on a shape-stable call; reject a key change during
capture (as int64 already does). This collapses ~10240 of 10423 seams (30×) so the MoE runs inside the
replayed graph.
- **Estimated ceiling:** the seam swarm is ~all of the non-compute wall time; eliminating it should give
  roughly **3–5× (2725 → ~550–900 ms/tok)**, bounded *below* by dense_fallback all-256-expert fp16
  MatMulNBits compute + ~20k captured-node replay overhead.
- **Byte-exactness caveat (why it is NOT a "clean low-risk" ship):** the safe version must **keep the
  cuDNN f32-comp compute path** (not reroute fp16 → NVRTC block), since that changes reduction order and
  risks last-ULP drift vs the #616 oracle. Making cuDNN reduce capture-safe means persistent workspace
  caching + capture-safety plumbing in a **core kernel used by every norm/softmax/MoE** — real capture
  correctness risk (stale pointers, capture abort), not a byte-numeric change. Needs parity
  (greedy token-exact vs native-CPU oracle) + capture-engagement (seam-count drop) + shape-change-under-
  capture rejection tests before it is safe to land. Given the mission's scope-first, regression-sensitive

# Decision — Lever A: float ReduceSum/ReduceMean made CUDA-graph capture-eligible

- **Author:** Cohaagen (EP/runtime perf & engine)
- **Date:** 2026-08-03
- **PR:** justinchuby/onnx-genai#618 (branch `squad/leverA-reduce-capture`, off origin/main incl. #616)
- **Status:** open — routed for review (Harry), NOT self-merged

## Problem
Qwen3.6-35B-A3B native CUDA decode was host/sync-bound (~2725 ms/tok, GPU util 19–31%). CUDA-graph capture was shredded into **10424 segments / 10423 eager seams** (~1 op/segment). **98.2% of seams = fp16 `ReduceSum` (10240 = 256 experts × 40 layers)** from the dense_fallback MoE per-expert masking reduce.

Root cause in `crates/onnx-runtime-ep-cuda/src/kernels/reduce.rs` + `cudnn/mod.rs`: the cuDNN float (f32/f16) reduce path allocated its workspace per call (`alloc_zeros`), did an unconditional `synchronize()`, and never set `last_call_capture_safe` ⇒ every float reduce was a non-capturable eager seam. (The Int64 path was already capture-eligible via `ReductionMetadataCache`.)

## Fix (generalized the proven Int64 pattern to the cuDNN float path)
1. **CudnnReduceCache** — caches cuDNN descriptors + reduce workspace across calls, keyed by (op, dtype, input shape, axes, keepdims). Shape-stable decode reuses device metadata + workspace, **no per-call alloc**; repopulate happens in **eager mode only**; a cache miss **during capture returns Err** (rejects capture) instead of allocating mid-capture.
2. **`synchronize()` gated on `!capturing`** — no host sync during capture (that shredded the graph); eager keeps the sync (EP-wide eager-correctness contract).
3. **`last_call_capture_safe = true`** on shape-stable cuDNN reduces (both #616 f16 f32-comp path AND f32 path).
4. **Axes-as-input during capture** — reuse `warmed_axes` from the eager pre-capture warm call (device read of axes is illegal during capture). Int64 keeps device-validated metadata.
5. **Byte-exact:** f32 = CUDNN_DATA_FLOAT comp + f32 α/β (byte-identical to old `reduce_t::<f32>`); f16 keeps #616 f32-accumulate; bf16 stays on NVRTC (cuDNN can't reduce bf16; not a seam contributor). No per-model hardcoding — fixes all float reduce ops through this path.

## Measured (8×H200, greedy, taskset -c 1, steady median 3 runs / 2 warmups)
| metric | before (documented) | after |
| --- | --- | --- |
| decode | 2725 ms/tok | **405 ms/tok (~6.7×)** |
| captured graph | 10424 seg / 10423 seams | **184 seg / 183 seams** |
| plain fp16 ReduceSum seams | 10240 | **0** |

- Steady runs tight: 405.0 / 405.0 / 406.5 ms/tok.
- Greedy output **byte-exact/deterministic** across runs (regression-safe).
- Exceeded the estimated 3–5× ceiling (achieved ~6.7×); the dense_fallback all-256-expert compute floor was not the binding constraint here — host-sync seams were.

**Root cause (precise):**

1. The QMoE artifact is authored for the **native onnx-genai QMoE contract**, not

   `input`/`output` = FLOAT16, `fc1_scales`/`fc2_scales` = FLOAT (fp32),
   `router_probs` = FLOAT (fp32, from a `Cast`).
2. ORT 1.27's `com.microsoft::QMoE` binds **input, router_probs, scales, output
   all to one type parameter `T`**, so fp32 scales/router_probs + fp16
   activations is an invalid graph → ORT rejects it at `Session` load. This is
   an *intentional* divergence: the native kernel's mixed-precision contract is
   not ORT's QMoE contract.

   constructs an ORT `Session::new(...)` for **every** component — including the
   native decoder — via `PipelineEngine::build` (pipeline/mod.rs:715), even for
   `--backend native`. Native decode itself runs off `NativeComponentSession`

   outputs()`) and `validate_fixed_state_budget` are wired to that ORT

   the graph never gets past ORT's load-time type-check.

a silent CPU fallback — it is a hard load-time rejection.

components that `model_requires_native_backend`. That decouples native decode

# QMoE Sparse Decode — Qwen3.6-35B-A3B design & plan (Cohaagen)

**Scope:** read-only scoping pass. No product code, no PR. Author: Cohaagen (EP/runtime perf).
**Date:** 2026-08-03. **Artifact:** `/home/justinchu/qwen36-35b-a3b-artifacts/` (dense_fallback MoE, 405 ms/tok after #616/#618).

---

## 0. TL;DR — the answer that unblocks dispatch

- **The CUDA `QMoEKernel` decode path is ALREADY sparse.** For a single decode token (`rows == 1`) it reads **k=8** expert weight matrices per FC layer from HBM, **NOT E=256**. The per-token expert weight traffic is `k/E = 8/256 = 1/32` of dense.
- **Therefore work item (b) — an onnx-genai decode sparse-dispatch kernel — is NOT required.** The kernel already does top-k gather + per-route GEMV at `rows==1`. The only thing standing between us and A3B speed is the **export**: the artifact emits `dense_fallback` (per-expert `MatMulNBits` + `Equal`/`ReduceSum` masking), which computes **all 256 experts every token**.
- **Only work item (a) — the mobius export change — is on the critical path.** mobius *already has* a full `com.microsoft::QMoE` emission path and an expert-weight repacker; it is simply gated off for this model (Olive quant + unconditional per-expert unpack). Deckard's change is small and localized.

---

## 1. CRITICAL QUESTION — decode: sparse or dense today? (k vs E HBM reads)

**Sparse. k, not E.** Traced end-to-end in `crates/onnx-runtime-ep-cuda/src/kernels/qmoe.rs`:

`impl Kernel for QMoEKernel::execute` (qmoe.rs:1010):
- Expert **grouping is built only when `rows > 1`**: `let grouping_sizes = (rows > 1).then(|| …)` (qmoe.rs:1209). For decode (`rows == 1`) `grouping` is `None`.
- With `grouping == None`, execute takes the **`else` branch** (qmoe.rs:1335) which calls `launch_linear(… expert_counts = None …)` for fc1, (fc3), fc2 — the "Phase-1 per-route GEMV path" named in the file header (qmoe.rs:3-5).
- `launch_linear` → kernel `qmoe_linear_impl` (qmoe.rs:264). Its work domain is `tasks = routes * out_features` where **`routes = rows * k`** (qmoe.rs:1197). For `rows==1`, `routes = k = 8`.
- Inside the loop each task does `expert = selected_experts[route]` (qmoe.rs:291) and dequant-GEMVs **only that routed expert's weight row** `expert_row = expert*out_features + output_feature` (qmoe.rs:301, 308-320). There is **no loop over all experts**. Experts that aren't routed are never touched.
- The `expert_counts[expert] >= gemm_min_tokens` guard (qmoe.rs:292-295) only *hands large-count experts off to the grouped GEMM* in the prefill path; at decode `expert_counts` is null so the per-route GEMV owns every route.

**Quantified HBM reads at `rows==1`, E=256, k=8:**

| Stage | Expert matrices read (dense_fallback today) | Expert matrices read (CUDA QMoE) |
|---|---|---|
| fc1 (gate+up) | 256 | **8** |
| fc2 (down) | 256 | **8** |
| per layer | 512 | **16** |
| whole model (×40 MoE layers) | 20,480 | **640** |

`qmoe_grouping.rs`'s "prefill" header is accurate — the *grouping/gather* helpers (count/prefix/assign/gather + tiled `qmoe_grouped_linear_f32` in `qmoe_gemm.rs`) are the `rows>1` batched path. Decode bypasses them entirely and is already the sparse per-route GEMV. The decode path is also **capture-eligible** once warmed (`capture_support`, qmoe.rs:1393): it is a single templated kernel (`qmoe_linear_{f32,f16,bf16}`) parameterized by bits/block_size/zero-points, not per-expert-compiled — fits the #618 CUDA-graph pattern.

> **Conclusion:** switching the export to QMoE is *sufficient* to realize A3B decode. No kernel change needed. (b) is optional future optimization only.

## 2. QMoE op I/O contract our CUDA kernel expects

Source: `QMoEFactory`/`QMoEKernel` (qmoe.rs:777-1403), `MoeAttributes` (qmoe.rs:658-727), `QuantizedExperts::validate` (qmoe.rs:908). Domain `com.microsoft`, 7–21 inputs, 1 output.

**Inputs (index → name, by position):**
| idx | name | dtype | shape | notes |
|---|---|---|---|---|
| 0 | input | f32/f16/bf16 | `[rows,H]` or `[B,S,H]` | output dtype must match |
| 1 | router_probs | **float32** | `[rows, E]` | raw router logits (see routing) |
| 2 | fc1_experts_weights | **uint8** | `[E, fc1_out, H*bits/8]` | packed int, expert-major |
| 3 | fc1_scales | **float32** | `[E, fc1_out, H/block_size]` | |
| 4 | fc1_experts_bias | f32 | `[E, fc1_out]` | optional |
| 5 | fc2_experts_weights | uint8 | `[E, H, inter*bits/8]` | required |
| 6 | fc2_scales | float32 | `[E, H, inter/block_size]` | required |
| 7 | fc2_experts_bias | f32 | `[E, H]` | optional |
| 8/9/10 | fc3_experts_weights/scales/bias | | `[E, inter, H]`… | **only** unfused SwiGLU or SiLU-gated (`uses_separate_gate`) |
| 11 | fc1_experts_zero_points | uint8 | `[E, fc1_out, ceil((H/block)*bits/8)]` | optional (asymmetric) |
| 12 | fc2_experts_zero_points | uint8 | `[E, H, ceil((inter/block)*bits/8)]` | optional |
| 13 | fc3_experts_zero_points | uint8 | | optional |
| 14 | router_weights | float32 | `[rows, E]` | optional; **CUDA ignores it** (softmax-top-k on input 1); CPU gathers it |
| ≥15 | | | | reserved for FP4/FP8 modes → **hard error if present** (qmoe.rs:1032) |

**Attributes:**
- `k` (int > 0) — top-k experts per token.
- `expert_weight_bits` ∈ **{1,2,4,8}** (qmoe.rs:784). We use **4**.
- `block_size` — **power-of-two, ≥16** (qmoe.rs:790). We use **32** ✓.
- `quant_type` — string, **must be `"int"`** (integer-affine). FP4/MXFP4/IQ rejected (qmoe.rs:802-809).
- `activation_type` ∈ {relu, gelu, silu, swiglu, identity} (qmoe.rs:635) → we use **`swiglu`**.
- `swiglu_fusion` ∈ {0,1,2}, only valid with swiglu (qmoe.rs:689-699):
  - `0` = separate gate tensor via **fc3** (`uses_separate_gate`), fc1 width = inter.
  - `1` = **interleaved** gate/linear in fc1 (`[…2*f, 2*f+1]`), fc1 width = 2*inter.
  - `2` = **concatenated halves** in fc1 (`gate = fc1[..inter]`, `linear = fc1[inter..]`), fc1 width = 2*inter. **← what mobius emits.**
- `normalize_routing_weights` (bool) — renormalize selected top-k weights.
- `activation_alpha` (def 1.0), `activation_beta` (def 0.0), `swiglu_limit` (def +inf) — SwiGLU clamp/shape (qmoe.rs:418-430).
- `use_sparse_mixer=1` → **unsupported** (qmoe.rs:684).

**Dequant math (must match exactly):** `w = ((q:uint - zero_point) * scale)` per int4 nibble; default `zero_point = 1<<(bits-1) = 8` when zero_points absent (symmetric); block index `= depth/block_size` (qmoe.rs:169-239, `decode_affine_weight` / `qmoe_int4_chunk`). This is the **same affine convention as `MatMulNBits`**, so dense_fallback→QMoE is byte-equivalent given a faithful repack.

**Routing plumbing (contract mobius must honor):** pass **raw float32 logits** as `router_probs` (input 1); CUDA QMoE internally does softmax→top-k→(optional normalize) and ignores input 14. This reproduces a softmax-topk router (`Softmax(TopK(logits))`) exactly. Selection is by raw logit (monotonic). This is precisely what `TopKGate.qmoe_routing`/`SoftmaxTopKGate.qmoe_routing` already emit in `mobius/src/mobius/components/_moe.py:39-110`.

## 3. What the current dense_fallback 35B graph looks like (measured)

Op census of `decoder/model.onnx` (structure only): `MatMulNBits ×31,111`, `Mul ×41,180`, `Sigmoid ×10,390`, `Equal ×10,240`, `ReduceSum ×10,241`, `TopK ×40`, `Softmax ×40`, plus `LinearAttention ×30`, `CausalConvWithState ×30`, `RMSNormalization`, etc.

- **hidden H = 2048**, **moe_intermediate = 512**. Experts store **separate gate & up** (`MatMulNBits` K=2048,N=512) + **down** (K=512,N=2048).
- **block_size = 32, bits = 4** on every expert `MatMulNBits` ✓ (blk32 int4).
- **Per-expert weight footprint** (int4 blk32): fc1(gate+up) = 1024×2048 → ~1.05 MB packed + 0.26 MB scales; fc2(down) = 2048×512 → ~0.52 MB + 0.13 MB scales; ~2.0 MB/expert incl. zero-points.
- 256 × 40 × ~2.0 MB ≈ **19.2 GB** of routed-expert weights — i.e. **~97% of the 19.78 GB `model.onnx.data`.** The rest = shared experts, attention/linear-attn projections, embeddings, lm head, norms.

**dense_fallback per-MoE-layer structure** (from `MoELayer.forward`, `_moe.py:375-395`):
`router = Softmax(TopK(MatMul(h, gateᵀ)))`; then **for each of 256 experts**: `expert_out = MLP_i(h)` (3× `MatMulNBits` + SwiGLU), `mask = Equal(selected, i)`, `w = ReduceSum(routing*mask)`, `acc += expert_out * w`. Shared expert is a **separate always-on MLP** scaled by `sigmoid(shared_expert_gate(h))` (`Qwen2MoELayer.forward`, `moe.py:292-299`) — it stays dense and is **outside** the QMoE node.

**dense_fallback → QMoE mapping (byte-equivalent):**
- 256 per-expert `{gate,up,down}` `MatMulNBits` → one `com.microsoft::QMoE` node with expert-major `fc1_experts_weights=[256,1024,1024]`, `fc2_experts_weights=[256,2048,256]` (+scales, +optional zero_points), `k=8`, `expert_weight_bits=4`, `block_size=32`, `activation_type="swiglu"`, `swiglu_fusion=2` (gate=first 512, up=second 512). `fc1_out = 2*inter = 1024`.
- Router `Softmax(TopK(logits))` → feed **raw logits** as `router_probs`, `normalize_routing_weights` per gate (`TopKGate` uses softmax-of-topk; verify vs HF Qwen3.6 router — softmax gate, low risk).
- `Equal`/`Mul`/`ReduceSum` masking + weighted sum → **absorbed inside QMoE** (combine kernel, qmoe.rs:515-541).
- Shared expert + sigmoid gate → **unchanged** (kept as dense MLP + `Sigmoid`/`Mul`/`Add`).

## 4. Weight repack plan (Olive q4_k_m MatMulNBits blk32 → QMoE ABI)

**Is blk32 already QMoE-compatible?** Yes for the *quant scheme*: block_size 32 is power-of-two ≥16 ✓, bits 4 ✓, quant_type integer-affine ✓, same `(q - zp)*scale` dequant as MatMulNBits ✓. **No requantization; no accuracy loss** — this is a pure *layout* transform.

**What changes is layout, expert-majorness, and the un-split:**
- MatMulNBits stores each projection **per-expert, separately**, as `weight=[N, n_blocks, blob_size]` uint8, `scales=[N, n_blocks]`, `zero_points=[N, ceil(n_blocks*bits/8)]` (see `preprocess_olive_weights`, `_weight_utils.py:709-804`, `blob_size = group_size*bits/8 = 16`).
- QMoE wants **expert-major fused 3-D** tensors: `fc1_experts_weights=[E, fc1_out, H*bits/8]`, flattening the `(n_blocks, blob_size)` inner dims into one packed axis, with **gate and up concatenated** along `fc1_out` (fusion=2), and down as `fc2`.

**Mechanics (already implemented in mobius):**
- `pack_qmoe_expert_weights` (`_weight_utils.py:592-633`) maps `experts.gate_up_proj.{weight,scales,zero_points}`→`fc1_*` and `experts.down_proj.*`→`fc2_*`, and `flatten(-2)` collapses `[…, n_blocks, blob_size]`→`[…, n_blocks*blob_size]` = the QMoE packed inner axis. `MoELayer._init_qmoe_parameters` (`_moe.py:293-339`) declares exactly these shapes incl. the `ceil(...*bits/8)` zero-point width.
- **Nibble/pack order:** ORT MatMulNBits and QMoE share the same little-endian nibble packing (low nibble = element `2i`), verified by the CUDA decode (`qmoe_int4_chunk`, qmoe.rs:220-238) and `decode_affine_weight` — no nibble swap needed. Transpose: none beyond the existing MatMulNBits `[N, …]` output-major layout, which QMoE also expects (rows = output features).
- **Zero-point convention:** q4_k_m is asymmetric → carry `fc1/fc2_experts_zero_points` (uint8, packed 2/byte). If a projection is symmetric, omit zero_points and the kernel defaults zp=8 (must match how Olive dequantized — verify per-tensor; symmetric-vs-asymmetric mismatch is the one real accuracy trap).

**Accuracy gate:** because scheme is identical, the QMoE node must match the dense_fallback graph **to fp32 rounding**. Validate with a byte/near-exact oracle: same packed weights fed to (dense per-expert MatMulNBits path) vs (QMoE node) must agree within int4-dequant fp32 tolerance on identical inputs. Lock a golden logits fixture. No "justified-more-accurate" case expected — this is a faithful re-layout, so hold **byte-exact vs the dense_fallback oracle**.

**The actual gap for Qwen3.6 (why it exported dense):** `Qwen35MoECausalLMModel.preprocess_weights` (`qwen35.py:369-386`) **unconditionally** un-fuses `experts.gate_up_proj`/`down_proj` into per-expert `experts.{i}.*` tensors → forces the `MLP`-list dense path. And `_supported_qmoe_quantization` (`_moe.py:398-409`) only accepts `quant_method ∈ {gptq, awq}` — **Olive (`quant_method="olive"`) is excluded**, so even fused weights wouldn't hit QMoE. DeepSeek already shows the correct pattern (`deepseek.py:448-484`): a `use_qmoe` guard that *keeps* the fused expert-major tensors and calls `pack_qmoe_expert_weights`.

## 5. Realistic decode ceiling (HBM-weight-bound estimate + honest caveats)

**Weight-traffic model (MoE is ~97% of bytes):**
- Dense_fallback reads **all** experts every token: ~19.2 GB expert weights + ~0.6 GB non-MoE ≈ **19.78 GB/token**.
- QMoE sparse reads k=8/256: `8×~2.0 MB×40 ≈ 0.64 GB` expert + ~0.6 GB non-MoE ≈ **~1.2 GB/token** → **~16.5× less total** weight traffic (32× on the MoE fraction alone).

**But decode is not bandwidth-saturated today.** 19.78 GB / 405 ms ⇒ ~49 GB/s effective — an order of magnitude under any datacenter GPU roofline (A100 ~2 TB/s, H100 ~3.3 TB/s). So the 405 ms is dominated by **dense_fallback overhead**, not HBM: per token it launches 256 per-expert `MatMulNBits` GEMVs **plus** ~256×(`Equal`+`Mul`+`ReduceSum`) elementwise masking **per layer ×40** — tens of thousands of ops and full-expert compute that QMoE collapses into **one fused node doing only k=8 GEMVs**.

**So the QMoE switch wins on both axes simultaneously:** 32× less expert weight traffic **and** ~256→8 GEMVs + elimination of the masking op storm.

**Ceiling estimate (be honest, must be measured):**
- Pure-roofline for 1.2 GB/tok: ~0.4 ms (H100) / ~0.6 ms (A100) — an unreachable lower bound.
- Realistic batch=1 caveat: the decode GEMV assigns one CUDA block per `(route, out_feature)` = `k*fc1_out + k*H = 8*1024 + 8*2048 ≈ 24.6k` blocks/layer, each a memory-bound `in_features`-length reduction. Good parallelism and capture-eligible, but **rows=1 GEMVs do not saturate HBM** (latency/occupancy-bound, poor arithmetic intensity), so expect to land well above the roofline.
- **Defensible target: ~25–60 ms/tok (≈7–16× e2e)** after (a), gated by attention + linear-attention state updates + KV + the always-on shared expert + small-GEMV efficiency. Best case toward the low end if non-MoE is cheap and the per-route GEMV occupies well.
- **Caveat/HARD RULE:** these are estimates from static byte counts + code reading. The **405 ms baseline and the post-switch number must be measured on an origin/main GPU worktree** (local main is stale; do not trust local perf). Treat §5 numbers as sizing, not commitments.

## Decision

Invert the default of `ONNX_GENAI_WEIGHT_OFFLOAD_ASYNC_PAGEIN`:

## Why — measured A/B (the data)

qwen3-0.6b-int4, native CUDA, weight-offload engaged, eviction/thrash regime (small device budget so every admit evicts):

| Config (device budget 96 MiB) | tok/s |
|---|---|
| async page-in ON  | 12.16 |
| async page-in OFF (sync) | **15.84** |

| term | ms |
|---|---|
| materialize (int4 canonical-bytes staging/dequant prep) | 791 |
| pinned host-buffer alloc + copy | 792 |
| raw H2D copy | 46 |
| eviction compute-stream drain | 15 |
| fence wait | 7 |

The transfer (H2D) the async path tries to overlap is ~3% of the cost. Materialize + pinned-staging co-dominate (~48% each) and sit on the critical path; when every admit evicts, the eviction drain re-serializes, so async cannot overlap anything and only adds the non-overlappable pinned-staging alloc. Async becomes a net win only once a warm-host materialize cache keeps pinned canonical bytes warm (removes both dominant terms from the per-page-in critical path).

### 2026-08-06: cohaagen-cuda-fp16-topk
**By:** Unknown
**What:** # Decision: CUDA fp16 TopK — kernel already merged (#445); added router-scale conformance parity

**Author:** Cohaagen (EP/runtime perf)
**Date:** 2026-08-03
**Branch/PR:** squad/cuda-fp16-topk

## Context
Qwen3.6-35B-A3B (and any `dense_fallback` MoE decoder) has a 256-expert/top-8 router
whose gate `TopK` runs in fp16. The CUDA EP previously rejected fp16 TopK
(`input 0 ('X') dtype Float16 unsupported; expected Float32`) for all 40 router
nodes, forcing a whole-session CPU fallback.

## Finding
The fp16 (and bf16) TopK kernel + claim gate were **already implemented and merged**
on `origin/main` via **PR #445 "feat(cuda): support fp16 router TopK"** (commit
`d2333664`). The kernel upcasts each compared value to f32 (`static_cast<float>`),
reuses the existing total-order `before()` compare (equivalent to `f32::total_cmp`),
and writes back the original raw fp16/bf16 element — so selection is byte-identical
to the CPU/ORT oracle (fp16→f32 widening is lossless; the round-trip preserves the
element, including sign-of-zero). The claim gate now uses
`require_one_of(input_dtypes, 0, CUDA_FLOAT_DTYPES, "X")`
(`CUDA_FLOAT_DTYPES = [Float32, Float16, BFloat16]`).

## What this PR adds (the remaining task-mandated gap)
PR #445's conformance test covered only a small final-axis ties case. This PR extends
`tests/indexing_gpu.rs` with the coverage the task explicitly required:
- **Router-scale byte-parity:** fp16 `[2,256]` top-8 (the real 35B router shape) with
  a `%37` tie-heavy pattern, asserting GPU == CPU byte-for-byte + distinct/in-range
  selected experts.
- **Non-final axis:** fp16 axis-0 oracled against the proven f32 GPU kernel.
- **Claim-regression guard** (`cuda_ep_claims_fp16_topk_router_nodes`): asserts the EP
  now CLAIMS fp16/bf16 TopK via `supports_op` (and still claims f32).

## Verification
- Decoder `qwen36-35b-a3b-artifacts/decoder/model.onnx`: **40 TopK nodes, all input0
  elem_type=10 (Float16)** — confirms the exact op gap.
- `cargo test -p onnx-runtime-ep-cuda --features cuda --test indexing_gpu`: 15/15 pass
  (incl. the 3 fp16 TopK cases) on H200.
- Coverage-of-coverage (`every_covered_op_has_a_conformance_entry`): pass.
- `cargo clippy -p onnx-runtime-ep-cuda --features cuda -- -D warnings`: clean;
  `cargo fmt --all --check`: clean.

## Pre-existing issue observed (OUT OF SCOPE — flagged, not fixed)
The **CPU EP** `TopK` writes **non-final-axis** outputs in push order
(`outer, inner, k`) whereas the **CUDA kernel and ONNX** use k-major
(`outer, k, inner`) — the layout asserted by the existing `topk_non_final_axes_*`
GPU test. They therefore disagree byte-for-byte for a non-final axis with `inner>1`
and `k>1`. This is **independent of dtype** (affects f32 identically) and predates
this work. Recommend a separate fix to `crates/onnx-runtime-ep-cpu/src/kernels/selection.rs`
(TopK) to place outputs by tensor strides. This PR sidesteps it by oracling the
fp16 non-final-axis case against the f32 GPU path.

closed (EP claims the 40 fp16 router nodes; standalone fp16 TopK runs byte-correct on
CUDA at router scale).

## Why Tile declines / syncs today (cite)

`TileKernel::execute` (movement.rs:1082) does **two** per-call host syncs:
1. `host_ints(&self.runtime, &inputs[1], "Tile")` (movement.rs:1091) reads the
   `repeats` tensor device→host via a blocking `dtoh` (movement.rs:190) — a
   per-call sync that is *illegal mid-capture*.
2. `launch_metadata` (movement.rs:205) does `alloc_raw` + `htod` + `synchronize()`
   + `free_raw` every call; the `synchronize()` (movement.rs:252) only guards the
   immediate `free_raw`.

`capture_support` therefore returns `Unsupported` with the exact reason
"Tile reads repeats on the host, allocates per-call metadata, and synchronizes
the stream" (movement.rs:1126).

## The fix (same PersistentMetadata pattern as Transpose/Expand + warmed repeats)

Key observation: the `tile_bytes` kernel metadata is `[output.shape, input.shape,
input_strides]` — it **never uses `repeats`**. `repeats` is read *only to validate*
that `output[i] == input[i] * repeats[i]`. Because the executor allocates the
output buffer from shape inference on the same `repeats`, a fixed
`(dtype, input_shape, output_shape)` signature mathematically fixes `repeats`
(`repeats[i] = output[i] / input[i]`). So:

- Add `PersistentMetadata` + `warmed_signature: Option<{dtype, input_shape,
  output_shape}>` to `TileKernel` (mirrors Transpose/Expand exactly).
- Read+validate `repeats` via `host_ints` **only on the unwarmed eager path**
  (first sight of a signature) — preserving the original validation precisely.
  Once warmed, skip the device→host read entirely (steady decode + capture).
- Replace `launch_metadata` with `launch_persistent_metadata` (cached buffer, no
  per-call alloc/htod/sync/free). Metadata bytes are **identical**.
- Guard: error on signature change mid-capture; `capture_support` → `Supported`
  once warmed. `metadata` built from `output.shape` (== the previously-validated
  `expected`), so byte-identical launch.

**Byte-exact:** same `tile_bytes` kernel, identical metadata bytes; only the
metadata-buffer lifecycle and the *timing/gating* of the repeats validation change.

## Q2 — MULTI-COMPONENT pipeline decode loop, and the EXACT reason capture is off

Pipeline decode drives the decoder component through:
`pipeline/decoder_component.rs:239 step()` → `session.decode_with_step_inputs(...)`
(`native_decode/mod.rs:438`) → `decode_cuda` (`native_decode/cuda.rs`).

The decoder component's decoder declares an `inputs_embeds` port (embedding output) plus
routed ports (e.g. `per_layer_inputs`), so `has_eager_step_inputs()` (cuda.rs:490) is
**true**. In `decode_cuda`, cuda.rs:394-414:

```rust
if self.has_eager_step_inputs() {
    let capture = token_ids.len() == 1
        && self.cuda.as_ref().is_some_and(|state| state.capture_step_inputs); // <-- gate
    if capture { return self.decode_cuda_captured_step_inputs(...); }         // Inc3c: CAPTURES
    return self.decode_cuda_eager_step_inputs(...);                           // default: NO capture
}
```

**Exact reason capture does not happen:** `state.capture_step_inputs` is **false by
default**. It is set at cuda.rs:1403-1404:

```rust
let capture_step_inputs =
    graph_enabled && !captured_step_inputs.is_empty() && capture_step_inputs_enabled();
```

and `capture_step_inputs_enabled()` (cuda.rs:250-258) reads env
`ONNX_GENAI_NATIVE_DECODER_CAPTURE_STEP_INPUTS`, **defaulting to `false`**. The in-code
comment (cuda.rs:1398-1402) is explicit: *"enable the captured per-step-input path only
when (a) the operator opted in … Off by default keeps the eager owned path
byte-identical."*

## Problem

`crates/onnx-runtime-session/src/hetero.rs` (`plan` + `execute`) is a complete,
CPU-tested per-op heterogeneous planner/executor, but it has **zero non-test
callers** (`grep` confirms: only `pub mod hetero;` in `lib.rs`). The default
session build path never touches it:

- `SessionBuilder` selects ONE EP (`lib.rs::select_execution_provider`).
- `Executor::build → place_graph` (`executor/build.rs`) does **whole-session**
  CUDA→CPU fallback: `cuda_fallback_report` finds *any* uncovered node and the
  ENTIRE graph is restored to `graph_before_ep_passes` and re-placed on a fresh
  CPU EP (`*graph = graph_before_ep_passes; *ep = auto_detect_cpu_ep()`). A model
  with a handful of CUDA-unsupported ops silently loses CUDA for *everything* —
  a catastrophic perf cliff, emitted only as a `[onnx-genai-warning]`.
- #602's legalization fixpoint + `function_has_attribute_parameters` fail-closed

## Load-bearing questions

### (a) Does cross-EP tensor movement at the seams already exist? — **YES (host-staged), for the standalone executor only.**

`hetero::execute` (hetero.rs) already realizes cross-EP movement: it walks
partitions in topological order, `extract_subgraph`s each into a standalone
`Graph`, builds a **fresh single-EP `Executor` per partition** on that
partition's provider, and threads boundary tensors through a host-side
`HashMap<ValueId, Tensor>` (`values`). Every cross-partition value is
materialized on the host between partition runs — the "correctness-first
synchronous transfer phase" (module docs §5.2). `plan_transfers` computes the
minimal deduplicated `Transfer{value, from, to}` set (H2D/D2H/D2D), but the
actual data motion in `execute` is the implicit host round-trip via `Tensor`
(host-resident), not device-resident residency/fences (explicitly deferred).

**Caveat that shapes the increment:** this movement exists **only** in the
standalone, stateless `hetero::execute`. It is NOT integrated with the session's
long-lived, stateful `Executor` (KV cache, CUDA-graph capture, decode-memo,
control-flow subgraph execs). `hetero::execute` rebuilds sub-`Executor`s on every
call, so it is sound for one-shot stateless graphs but cannot serve the stateful
decode loop as-is. So from the **default session path's** perspective, integrated
per-op *execution* does **not** yet exist — only planning + a standalone
stateless executor.

### (b) Where does per-node placement hook in, and how does it compose?

Two candidate seams:
- **`hetero::plan`** already owns partition-time placement (per-node
  `assign_nodes` over priority-ordered providers + convex partitioning reusing
  `OrtGraphView::query_capabilities`). No new placement logic is needed.
- **`place_graph`** is the seam where the whole-session fallback happens today,
  and is therefore where the default path must consult the planner. It is
  **CUDA-gated**: `cuda_fallback_report` returns `None` unless
  `ep.device_type() == Cuda`, so the mixed branch is only reachable on CUDA
  builds with partial coverage.

Composition:
- With **#594's single-EP `keep_as_op`** path: untouched. That path never enters
  the mixed CUDA-fallback branch (either the single EP covers the graph, or
  `reject_unsupported_operators` rejects on a terminal CPU EP). The new logic is
  strictly additive inside the `if let Some(report) = …` fallback branch and is
  gated behind an **opt-in env flag** (`ONNX_GENAI_HETERO`, default OFF), so with
  the flag off the fallback is byte-for-byte the current behavior.
- With the **whole-session fallback**: when the flag is off, unchanged. When on,
  the planner runs first; a genuinely homogeneous graph returns
  `SingleProvider` and the existing fallback proceeds; a genuinely mixed graph
  **fails closed** (see increment) rather than silently dropping the whole
  session.

### (c) CPU-testable via fake providers? — **YES.**

`hetero/tests.rs` already drives `plan`/`execute` on CPU via an `AcceleratorEp`
fake provider (host-backed, advertises `DeviceType::Mlx`, restricted op set) and
asserts **byte-identical** output vs a single-EP reference. The new classifier
and fail-closed guard are exercised the same way — no GPU required. The
`place_graph` call site is CUDA-gated so it is not reachable on CPU CI, but the
guard *logic* is extracted into a pure `hetero` function and unit-tested directly
with fake providers (both `SingleProvider→Ok` and `Heterogeneous→Err`).

## First increment (this PR) — planner on the default path + fail-closed scaffold

Integrated stateful per-op **execution** genuinely does not exist yet, and the
task rule is *do not fake movement / never emit wrong bytes*. So this increment
moves per-op **placement** from latent→real on the default path and ships a
sound fail-closed scaffold for **execution**:

1. `hetero::classify_placement(graph, providers) -> PlacementDecision`
   (`SingleProvider(EpId)` | `Heterogeneous(Box<HeterogeneousPlan>)`): runs the
   Phase-1 `plan` and collapses it — homogeneous iff no cross-device transfers
   and ≤1 distinct assigned EP.
2. `hetero::placement_summary(plan, graph, providers)`: actionable per-op
   diagnostic — partition/transfer counts, per-EP node counts with device names,
   and the exact op classes forced onto the non-primary (fallback) EP.
3. `hetero::guard_heterogeneous_fallback(graph, providers, enabled)`: when
   enabled, classify; `SingleProvider ⇒ Ok` (caller's path untouched);
   `Heterogeneous ⇒ Err(SessionError::HeterogeneousExecutionUnsupported{summary})`.
4. `place_graph` mixed branch (behind `ONNX_GENAI_HETERO`, default OFF) calls the
   guard with `[primary(EpId 0), cpu_fallback(EpId 1)]` **before** the
   whole-session fallback. Flag OFF ⇒ guard is a no-op ⇒ existing fallback
   byte-identical.
5. New `SessionError::HeterogeneousExecutionUnsupported` variant (+ capi mapping
   to `OrtErrorCode::Fail`). Message names the CPU-bound ops and states that
   integrated per-op execution is deferred to #603, with the remediation
   (unset the flag for whole-session fallback, or extend CUDA coverage).

### What is implemented vs fail-closed-scaffolded

- **Implemented (real, de-latented):** per-op placement classification on the
  default build path; the standalone `hetero::execute` per-op host-staged
  execution is proven byte-identical to a single-EP reference on CPU
  (classifier composed with real execution in tests).
- **Fail-closed scaffold:** integrated per-op **execution inside the stateful
  session `Executor`** (decode/KV/capture/control-flow). Rather than run the
  whole session on CPU silently, the opt-in path returns an actionable error
  naming the offending ops. No wrong bytes are ever produced.

### Byte-identity of the #594 single-EP default path

- Default `ONNX_GENAI_HETERO` is OFF ⇒ `guard_heterogeneous_fallback` returns
  `Ok(())` on its first line ⇒ zero change to `place_graph`.
- The new code lives **only** inside the `if let Some(report) = …` CUDA-fallback
  branch — unreachable unless `ep.device_type() == Cuda` AND CUDA fails to cover
  the graph AND `!require_cuda`. The zero-config/default path is CPU-only
  (`select_execution_provider`), so it never enters this branch at all.
- Mutation argument: deleting the guard call, or forcing `enabled=false`, leaves
  the existing loader/session tests green and the fallback bytes unchanged; the
  new tests are the only coverage that fails, proving the guard is the sole
  behavioral delta and it is scoped to the opt-in mixed case.

**Why:** ONNX permits (mandatory pre-IR-4, still legal IR>=4) an initializer to
also appear in `graph.input`. Both ORT's `Session` (GetInputCount) and this
repo's native graph loader (`onnx-runtime-loader::graph_builder`, §2) exclude
those. Without the exclusion, `GraphIoMetadata.inputs()`/`input_names()` leaked
weight tensors, which would (1) trip the decode float-rank>=3 native-load guard
in `decode/resolved_io.rs::from_structure`, falsely rejecting a valid decoder,
and (2) route leaked weights as spurious unroutable ports in
`pipeline/routing.rs::build_step_bindings`. Fix is general — no op/model
special-casing. Resolves Harry's [MAJOR] rejection on PR #625.
