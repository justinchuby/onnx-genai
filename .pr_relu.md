## What this is

`relu_f32_simd` and `clip_f32_simd` in `dense_elementwise.rs` dispatch to a
hand-written NEON kernel on aarch64 and to a **scalar loop everywhere else**:

```rust
#[cfg(not(target_arch = "aarch64"))]
{
    for (d, &s) in dst.iter_mut().zip(src.iter()) {
        *d = if s < 0.0 { 0.0 } else { s };
    }
}
```

Every other activation in this crate acquired an AVX2 kernel over #1218, #1227,
#1235, #1240 and #1243. These two did not, and `Relu` at 1 Mi is the only
large-tensor case in the benchmark grid still slower than ORT's own CPU EP —
which runs MLAS's vectorised `MlasComputeRelu` there.

Both are now eight lanes wide on x86-64, four vectors per iteration, with an
8-wide remainder and a scalar tail. `is_x86_feature_detected!("avx2")` at the top
of the dispatcher, the same shape as `simd_activations`. No new dependency, no
feature gate, **no MLAS** — this is the pure-native path.

## The operand order is the correctness argument

`vmaxps` is not a general `max`. Intel defines it as

```
IF SRC1 > SRC2 THEN DEST := SRC1 ELSE DEST := SRC2
```

and it returns **SRC2** whenever either operand is NaN. So with the zero vector
as SRC1 and the data as SRC2, `_mm256_max_ps(zero, x)` reproduces
`if x < 0.0 { 0.0 } else { x }` exactly — including the two cases that make Relu
awkward:

| x | scalar | `max(zero, x)` | `max(x, zero)` |
|---|---|---|---|
| `NaN` | `NaN` (because `NaN < 0.0` is false) | `NaN`, payload intact | **`+0.0`** ✗ |
| `-0.0` | `-0.0` (because `-0.0 < 0.0` is false) | `-0.0` | **`+0.0`** ✗ |

Written the other way round — the way anyone would write it first — both become
`+0.0`, which is a different function. Clip is the same argument twice:
`clamp_nan_propagating` is a `max` against the lower bound then a `min` against
the upper, each written so NaN falls through, and `vminps` has the matching
`IF SRC1 < SRC2 THEN SRC1 ELSE SRC2` / SRC2-on-unordered rule.

## Tests

Three, comparing against the scalar form **by bit pattern** — `f32` equality
would hide both failures above, since `-0.0 == 0.0` and `NaN != NaN`.

The value set is both zeros, both infinities, `f32::MIN`/`MAX`/`MIN_POSITIVE`,
the smallest positive and negative subnormals, a quiet NaN, a *second* quiet NaN
with a distinct payload, a negative quiet NaN, a signalling NaN, and ±1e±30,
padded to 114 elements.

* `relu_f32_avx2_is_bit_identical_to_the_scalar_form` — every length from 0 to
  114, so the 32-wide body, the 8-wide remainder and the scalar tail each see
  special values rather than only padding.
* `clip_f32_avx2_is_bit_identical_to_the_scalar_form` — the same, across eight
  bound pairs including `(-0.0, 0.0)`, `(±Inf)`, an **inverted** pair
  (`min > max`, which ONNX leaves to the implementation), and NaN as each bound.
* `the_dispatched_relu_and_clip_agree_with_their_scalar_forms` — drives
  `relu_f32_simd`/`clip_f32_simd`, not the kernels, so a wrong `#[cfg]` arm or a
  missing `return` cannot pass.

**Falsifier, run:** swapping the `_mm256_max_ps` operands fails both Relu tests
at lane 1 with `0.0 (0x00000000)` against `-0.0 (0x80000000)`.

`cargo test --release -p onnx-runtime-ep-cpu --lib` — **1420 passed, 0 failed**.
clippy `--all-targets` and fmt clean.

## Measurements

Host AVX2/FMA, no AVX-512. `taskset -c 8-15`, one thread, interleaved
(A,B,A,B,…) against `origin/main` `c55a3fab3`, **five rounds**, ratio = ours/ORT,
lower is better, each column the median of the five. "drift" is ORT's own p50
across the two arms — the control.

**1 Mi, 200 iterations after 30 warmup:**

| case | before p50 | after p50 | before p90 | after p90 | drift | rounds won |
|---|---|---|---|---|---|---|
| `relu_f32_1m` | 1.035 | **1.024** | 1.036 | **1.019** | −0.2 % | 4/5 |

132.1 µs → 130.0 µs. Real, and in the right direction at both percentiles, but
**small** — and it should be, because at 1 Mi this op moves 8 MiB at ~63 GB/s on
one core. It is bandwidth-bound; the arithmetic was never the limit. Every other
1 Mi case in the same run moved within ±1 % with 0/5–3/5 round-win counts, i.e.
noise, which is the drift control for this table.

**4 Ki, 400 iterations after 50 warmup** (see the second commit — Relu had no
4 Ki case before this PR):

| case | before p50 | after p50 | before p90 | after p90 | drift | rounds won |
|---|---|---|---|---|---|---|
| `relu_f32_4k` | 1.642 | 1.638 | 1.655 | 1.657 | 0.0 % | 2/5 |

**No effect, and that is the finding.** At 4 Ki the whole op is 3.5 µs of which
the kernel is ~0.27 µs; the rest is per-`Run` dispatch. 1.64x is the *worst*
ratio in the 4 Ki grid — worse than `tanh` (1.36) or `erf` (1.38) — precisely
because Relu is the cheapest op, so ORT's own time is smallest and our fixed
overhead is the largest share of it. That is a dispatch problem, and it is what
#1244, #1246 and their successors address; this PR does not claim it.

## What this is and is not

It is: a strictly-better, bit-identical vector kernel closing an asymmetry where
aarch64 had one and x86-64 did not, worth ~1.6 % where the op is bandwidth-bound
and more where it is not.

It is not: a fix for `Relu` at small sizes. That number is dispatch overhead and
is tracked separately.
