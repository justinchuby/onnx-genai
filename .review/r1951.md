### 4. Two hypotheses I falsified — recorded so nobody spends the evening on them

Both looked like real defects from reading. Both are fine. I am reporting the negative results because an unreported falsification gets rediscovered.

**"`scheduler.complete()` on the workflow path is untested."** Your body lists the missing reservation lifecycle as one of four consequences, and no battery arm covers the release, and every test that reaches `workflow_api.rs:228` asserts a refusal. I was confident. It is wrong:

`generate_with_callbacks` → `generate_interpreted` → `generate_with_pipeline_callbacks`, so #1904's release test lands on that exact line. My error was stopping the call-graph trace one hop early — I read `generate_interpreted` in the branch list and assumed it was a peer of this function rather than a caller of it. The line is covered, and after your fix it is covered for tensor-bound requests too, since they now reach the same line.

**"Workflow and native session ids collide in the shared scheduler."** This one is specific to your change and I still think it was worth checking. Before this PR the workflow branch was **unreachable on a decode-core runtime** (prompt-only took the early return above, `!prompt_only` took the one you deleted). After it, a tensor-bound request on a decode-core runtime mints `workflow_session_counter` into the same scheduler where `native_session_counter` ids live — and both counters start at 0, so their first ids are both `1`. A colliding `complete()` would release another sequence's reservation and over-commit the budget.

It cannot happen: every path admits and completes inside a single `&mut self` call (`runtime.rs:1279` admit → `:1368` complete), so two reservations from the two counters are never live at once, and the exclusive borrow rules out interleaving. Safe for the reason the borrow checker gives you, not by construction of the id space — worth a sentence somewhere if that invariant ever loosens, but nothing to do here.

### 5. On the fix itself

Deleting the early return rather than patching the callback is the right shape: the budget cap, the clamp, the reservation release and `budget_cap` in the result all arrive as consequences of rejoining the one admit → signal → run → complete sequence, instead of as four separate patches that could each be got wrong. `on_admitted()` now sits after `admit_interpreted_generate_request(...)?`, so the refusal path cannot reach it — which is the property your M3 arm pins.

Dropping the `interpreted_prompt_token_count` tokenizer fallback in `0b0422735` was correct and the reason recorded for it is the useful part: it converted a door-failure into a deep failure inside the PR whose argument is that the door should answer first.
