`construction_gpu` fails intermittently with `CUDA_ERROR_STREAM_CAPTURE_INVALIDATED` when the test binary runs its tests in parallel, which is the default. It passes consistently with `--test-threads=1`.

Found while verifying #623. I initially took it for my own regression, so I measured both branches before concluding otherwise.

## Evidence

Six consecutive runs of `cargo test -p onnx-runtime-ep-cuda --test construction_gpu --features cuda`, RTX 4060:

| branch | runs containing failures |
| --- | --- |
| `main` | 2 / 6 |
| `feat/cuda-device-allocator` (#623) | 0 / 6 |

`--test-threads=1`: 22/22 pass, every time, on both.

The failures land on the graph-capture tests, and the failing ones vary between runs:

```
expand_warmed_metadata_captures_and_matches_eager
tile_warmed_metadata_captures_and_matches_eager
split_static_even_num_outputs_matches_eager_bytes

cuda_ep: launch split_chunk_bytes: CUDA driver error:
  DriverError(CUDA_ERROR_STREAM_CAPTURE_INVALIDATED,
  "operation failed due to a previous error during capture")
```

So it is pre-existing and roughly a one-in-three chance of a red run, not caused by #623.

## Why this is worth more than a flake ticket

Parallel tests are the cheap version of the real scenario: **several sessions using the device at once.** If activity on one thread can invalidate a graph capture on another, then in production one session's memory traffic can kill another session's capture, and CUDA graphs are exactly what decode wants. The test suite is telling us something about the runtime, not about the tests.

This is also directly why the `DeviceAllocator` contract is documented as concurrent (#623): one allocator serves every session on its device, so overlapping calls are the normal case.

## Mechanism: not established

My hypothesis was that `cuMemFree` on another thread implicitly synchronizes the device and so invalidates an in-flight capture on a different stream. It fits the shape of the evidence, but **I could not confirm it.**

I wrote a standalone driver-level repro — one thread capturing, another churning `cuMemAlloc`/`cuMemFree`. It reported 40/40 captures invalidated, which looked like confirmation. Then the control run *without* the second thread also reported 40/40, which means the harness was broken and proved nothing. I have deleted it rather than quote a number produced by my own bug.

Two facts that any real diagnosis has to fit:

- `graph.rs:165` already uses `CU_STREAM_CAPTURE_MODE_THREAD_LOCAL`, not `GLOBAL`. So the plain "another thread made an unsafe call" rule does *not* apply — that restriction is thread-scoped in this mode. Whatever is happening is subtler than the default-mode footgun.
- Each EP builds its own stream, and there is no process-wide runtime cache, so the tests are not obviously sharing a capture stream. All EPs do share the CUDA *primary* context.

## Suggested next steps

1. Get a repro that has a passing control. Without one, any fix is a guess.
2. Check whether anything on the capture path calls `allocate`/`deallocate` *during* capture on the capturing thread — that would be a THREAD_LOCAL violation by us and would need no cross-thread explanation at all. This is the cheapest thing to rule out and should come first.
3. Only then consider cross-thread mechanisms.

If (2) turns out to be the cause, the fix is the device arena behind `DeviceAllocator` (#623): serving a request without entering the driver makes capture-time allocation legal. That would make the arena a correctness fix, not only a speed one.
